# 建模细则（对象 / 属性 / 关系 / 接口 / 动作）

这份文件是 `ontology-builder` 的参考：判定标准与常见错的写法。**先看结论再看例子。**

## 1. 对象类型（= 平台里的「类」）

**是**：业务里能单独指认的那种东西 —— 客户、专线产品用户、产品、订单、设备、工单。
**不是**：某个对象的字段（状态、等级）、一次查询的结果、一段配置。

三条自检：

1. 它有自己的标识吗（业务里的编号，不是"第几行"）？
2. 业务会把它的标识写进别人的单据里吗（外键意义上被引用）？
3. 它有一段时间里的状态变化吗（创建 → 变更 → 失效）？

三条都否 → 它多半是属性。

**粒度**：两个候选如果永远一对一、同时创建同时删除、也没有各自独立的生命周期，就该合并成一个。
反过来，"专线产品用户"和"客户"虽然一对多，但各自有独立标识与生命周期，必须分开。

**命名**：业务名词、单数、不加系统前缀。`专线产品用户` ✅ / `TB_MK_GRP_LINE_LIST_DAY` ❌ / `用户表` ❌。

## 2. 属性

| 数据形态 | dataType | 易错点 |
| --- | --- | --- |
| 名称、编码、号码 | `TEXT` | 别把数字型编码塞 `INTEGER`（前导 0 会丢，`371` 与 `0371` 是两回事） |
| 计数、数量 | `INTEGER` | |
| 金额、费率 | `DECIMAL` | 用 `TEXT` 存金额会让排序与比较失效 |
| 是否类 | `BOOLEAN` | 用 `TEXT` 存 `Y/N` 也可以，但要统一 |
| 日期 / 带时间 | `DATE` / `DATETIME` | Oracle 的 `DATE` 常带时分秒，按口径选 |
| 多值 | `TEXT_ARRAY` | 别用逗号拼接字符串装多值 |
| 结构化片段 | `JSON` | 只在结构真的不固定时用 |

- `required`：业务上必然有的。写上就要保证数据真有，否则发布被拦。
- `unique`：能唯一标识对象的列。主键列必须写。**长文本不要 unique**（> 8KB 会被拦）。
- `indexed`：会被筛选、检索、按它取数的属性。
- 属性的 `name` 与数据列的关系：`name` 是机器名，`sourceField` 是列名。两者不一致时（中文名对英文列）
  用 `displayName` 补中文，别把列名写成中文。

## 3. 关系类型

- 方向必须是业务方向：`客户拥有专线产品用户`（客户 → 用户），反向的查询由图库的入边支持，
  不需要再建一条反着的关系类型。
- 关系上的属性只放"这条关系自己的事实"：`订购时间`、`角色`、`份额`。
  放到对象类型上会造成"同一对对象只能有一条关系"的错觉。
- 自环关系（起点 = 终点）合法：`员工汇报给员工`。
- 一条关系类型只能表达一层含义：`客户拥有用户并订购产品` 这种复合语义要拆成两条。

## 4. 接口（唯一的抽象机制）

用接口当"可以被同一套应用按同一形状消费"的契约。**不要用接口做字段复用**，也不要用「父类 / 继承」描述它 ——
平台里对象类型之间没有继承关系。

判据（必须都能回答）：

1. 谁按这个接口消费？（某个应用 / 某个动作 / 某个查询）
2. 至少两个实现方吗？只有一个实现方的接口是过度抽象，先不建。
3. 契约里有什么？同名必填属性 + 必填关系约束。别的都不进接口（接口不绑数据、不能被实例化）。

反例：给"客户"和"专线产品用户"都建"有名称"的接口 —— 那只是命名巧合，不是消费契约。

## 5. 动作与规则

- 动作定义在**某个对象类型**上（`scopeEntityTypeId`）。所以"系统里通用的一个动作"这种说法是不成立的：
  先回答"这个动作作用在哪种对象上"。
- 三类写操作覆盖了绝大多数场景：
  `CREATE_ENTITY`（新建，给 alias）、`SET_PROPERTY`（改属性）、`CREATE_RELATIONSHIP`（连关系）。
- 规则是**动作上的闸门**，不是数据质检：
  - `BLOCK`：条件命中就不许执行，要给人看原因（"这个用户已经是停机状态"）。
  - `WARN`：提示但放行。
  - `HIDE`：动作在满足条件的对象上**不出现**；只能看主对象自身的属性（执行前还没有入参）。
- 规则条件可以沿一条关系跳到邻域再比对（`subject.relationshipTypeId` + `direction`），
  语义是"任一邻域对象命中即命中"。

## 6. 概念分组

- 分组是**展示层**的归类（业务域），不进图库、不参与推理、不影响权限。
- 一个对象类型最多归一个分组；不归组也可以（图谱里会散着画）。
- 不要用分组表达生命周期（草稿/已发布）或权限（谁能看）。

## 7. 数据来源

- 绑定写在**对象类型**上：一个对象 = 那张表里的一行。
- 主来源给身份与标题；补充来源按主键逐列对齐补属性（key 数量必须与主键一致、顺序一一对应）。
- 同一张表别在一个对象类型上挂两次。
- 来源坐标 + 列映射 ≠ 取数脚本：**平台不从绑定里自动取数**，绑定用来回答"这个对象的这些属性从哪来"。

## 8. 交付前的"反模式"自查

| 反模式 | 后果 | 正确做法 |
| --- | --- | --- |
| 把状态/等级做成对象类型 | 图上节点爆炸，查询要两跳 | 做成属性 |
| 把中文名当属性 `name` | 与列名脱节，列映射写不了 | `name` 用列名，中文放 `displayName` |
| 只建对象类型不建关系类型 | 图谱是一堆孤岛 | 把业务里的稳定关系建出来 |
| 给长文本写 unique | 发布被拦（> 8KB） | 去掉 unique，改用别的稳定键 |
| 动作不选作用对象类型 | 发布被拦：动作必须定义在某个对象类型上 | 选 `scopeEntityTypeId` |
| 接口只有一个实现方 | 过度抽象，改一次要动两处 | 先不建接口 |
| 关系属性挂到对象上 | 同一对对象的多次关系无法区分 | 属性放到关系类型上 |
| 编造表名 / 列名 | 导入后绑定全空，用户以为系统坏了 | 材料里没有就写"待确认" |
## 9. 平台会怎么体检你的方案（规则码）

平台有一层**建模体检**（本体草稿页头「建模体检」；外部 Agent 可以调 MCP 工具 `review_model`）。
它**不挡发布**，只把值得回头看一眼的地方分两档列出来：`该改` / `可以更好`。
出包前照着这张表自查一遍，能省一轮返工 —— 下面每条都对应体检里的一个规则码。

| 规则码 | 档次 | 说的是什么 |
| --- | --- | --- |
| `ENTITY_NO_PROPERTIES` | 该改 | 对象类型一个属性都没有（空壳） |
| `ENTITY_DISPLAY_PROPERTY_MISSING` | 该改 | 展示属性指向了不存在的属性 |
| `ENTITY_SOURCE_UNMAPPED` | 该改 | 绑了表，但没有任何属性映射到列 |
| `ENTITY_PRIMARY_KEY_UNMAPPED` | 该改 | 主键列没有属性接住（对象身份拿不到值） |
| `ENTITY_REQUIRED_PROPERTY_UNMAPPED` | 该改 | 必填属性没有映射列 |
| `ENTITY_ORPHAN` | 该改 | 孤悬：没绑数据、不连任何关系类型、也没有动作作用在它身上 |
| `ENTITY_DUPLICATE_NAME` | 该改 | 对象类型重名（只是大小写或空格不同） |
| `RELATION_DUPLICATE_NAME` | 该改 | 关系类型重名 |
| `GROUP_DUPLICATE_NAME` | 该改 | 概念分组重名 |
| `ENTITY_GROUP_MISSING` | 该改 | 指向了一个不存在的概念分组 |
| `RELATION_ENDPOINT_MISSING` | 该改 | 关系类型的起点或终点还没选对象类型 |
| `INTERFACE_EMPTY` | 该改 | 接口既没有属性也没有关系约束（空契约） |
| `ACTION_DUPLICATE_CODE` | 该改 | 动作标识重复（对外是工具名，调用方会选错） |
| `RULE_WITHOUT_CONDITION` | 该改 | 规则没有任何条件，对所有对象无条件生效 |
| `RULE_EMPTY_MESSAGE` | 该改 | 拦人或提示时没给用户看的原因 |
| `RULE_ACTION_MISSING` | 该改 | 规则绑定的动作已经不在本体里 |
| `ENTITY_NO_DISPLAY_PROPERTY` | 可以更好 | 没指定展示属性，界面只能用主键值当标题 |
| `NAMING_MIXED_STYLE` | 可以更好 | 对象类型命名风格混着来（中文 / 下划线 / 驼峰） |
| `PROPERTY_TYPE_CONFLICT` | 可以更好 | 同名属性在不同对象类型里类型不一致 |
| `RELATION_SELF_LOOP` | 可以更好 | 起点和终点是同一个对象类型（层级 / 转派语义下是对的） |
| `RELATION_DUPLICATE_PAIR` | 可以更好 | 同一对对象类型之间有多条关系类型 |
| `RELATION_NAME_COLLIDES` | 可以更好 | 关系类型和某个对象类型同名 |
| `RELATION_NO_DESCRIPTION` | 可以更好 | 关系类型没写说明 |
| `INTERFACE_UNUSED` | 可以更好 | 接口没人实现、也没被继承 |
| `GROUP_EMPTY` | 可以更好 | 概念分组下面还没有对象类型 |
| `ACTION_WITHOUT_EDIT` | 可以更好 | 动作没有任何写操作 |
| `ACTION_NO_DESCRIPTION` | 可以更好 | 动作没写说明 |

体检**不查真实表结构**："绑的那张表里到底有没有这一列"要连库去比，属于「数据资源」那侧的活；
它只保证**定义内部自洽**。
