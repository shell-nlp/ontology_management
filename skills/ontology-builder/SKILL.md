# 本体建模方案设计

## 输入

- 首选：`ontology-requirement` 产出的 `01-需求澄清.md`。
- 也可以直接吃业务材料，但要把上一节的判定标准走一遍（对象类型 / 属性 / 关系的区分最容易错）。

## 输出

1. `02-建模方案.md` —— 给人评审：每个对象类型的属性表、关系类型表、接口、动作、规则、以及"为什么这么建"。
2. `*.blueprint.json` —— **结构化清单**初稿（格式见 `ontology-bundle/references/blueprint-format.md`）。
   初稿允许有未定稿的地方（例如还没选表、还没定数据来源），引用一律写**名字**、不写 UUID ——
   出包那一步由 `ontology-bundle` 的编译脚本把清单变成真正的包。

## 建模顺序（按依赖走，别跳）

1. **概念分组**（业务域）先定：后面的对象类型都要归到一个域。分组只影响展示，不用纠结完美。
2. **对象类型**：名称、说明、概念分组、属性、展示属性。
3. **关系类型**：起点 → 终点 + 自带属性（关系上的属性只放"这条关系自己的事实"）。
4. **接口**：先定契约（必填属性 + 必填关系约束），再让对象类型 `implements` 它。
5. **动作**：定义在某个对象类型上（`scopeEntityTypeId`），配参数与写操作。
6. **规则**：挂在动作上（`actionId`），条件 + 处置 + 给用户看的原因。
7. **数据来源绑定**：给每个对象类型挂主来源（表 / 视图 + 主键列 + 标题列），再逐属性填列映射。

## 每个字段怎么写

### 对象类型

| 字段 | 怎么写 | 注意 |
| --- | --- | --- |
| `name` | 业务名词，**单数**、无前缀（`专线产品用户`，不是 `tb_user`） | ≤ 100 字符；同名会互相覆盖读者的理解 |
| `description` | 一句话说清"这个对象代表业务里的什么" | ≤ 500 字符；不要写技术说明（表名放来源里） |
| `displayProperty` | 图上/列表里展示给人看的那一列（通常是名称列） | 必须是自己属性里的名字 |
| `groupId` | 所属概念分组 id；不归组就留空串 | 引用必须存在 |
| `properties` | 属性清单，见下 | 至少要有能当主键与标题的属性 |
| `sources` | 数据来源，见「数据来源绑定」 | 只建模不接数据时可以是空数组 |
| `implements` | 实现了哪些接口 | 声明了就要满足接口的必填项 |

### 属性

- `name`：**机器名**，与数据列对齐（`SERV_NUMBER` 或 `serv_number` 都行，但在一个本体里保持一致）；
  写进图库、列映射、接口都靠它，发布后改名会牵动多处。
- `displayName`：给人看的中文名（`服务号码`）。留空就退回 `name`。
- `description`：这个属性是什么、口径怎么算（`号码归属地市编码，前 3 位为地市`）。
- `dataType`：只能取
  `TEXT` / `INTEGER` / `DECIMAL` / `BOOLEAN` / `DATE` / `DATETIME` / `TEXT_ARRAY` / `JSON`。
  金额用 `DECIMAL`，日期用 `DATE`，带时间的用 `DATETIME`，不要用一个 `TEXT` 装所有东西。
- `required`：业务上必须有的。写成 `true` 就必须在数据里真的非空，否则发布前校验会拦。
- `unique`：能唯一标识一个对象的列才写（主键列一定写）。**不要给长文本写 unique**：超过 8KB 的值会被拦下来。
- `indexed`：会被频繁筛选/检索的属性（地市、状态这类）。
- `sourceField`：这个属性的值来自哪个列；`sourceId` 指向哪一份来源（默认主来源，不用填）。

### 关系类型

- `name` 用**动词短语**（`客户拥有专线产品用户`），一句话能读通：`<起点> <谓语> <终点>`。
- `sourceEntityTypeId` / `targetEntityTypeId` 都必须是对象类型，且方向要符合业务（A 拥有 B ≠ B 属于 A）。
- `properties`：只放这条关系自己的事实。`订购时间` 属于"用户订购产品"这条关系，
  不属于用户或产品；这类属性千万别挂到对象类型上。

### 接口

接口是**唯一**的抽象机制（平台没有父类/继承这一说法，别用「父类」描述它）。只在满足下面两条时建：

1. 至少两个对象类型要以同一种形状被消费（同样的属性 + 同样的关系）；
2. 你能说出"谁按这个接口消费"（某个应用、某个动作、某个查询）。

- `properties[].required = true` 的，实现方必须有**同名**属性（同名映射，不另建映射表）。
- `linkConstraints[]` 描述"实现方必须有一条从我出去、指向目标（对象类型或接口）的关系类型"；
  `required = true` 时会挡发布。`cardinality` 只做建模提示，图库不强制基数。
- 接口不能绑数据、不能被实例化。
- 一个对象类型可以实现多个接口，接口也能继承接口（`extends`）。

### 动作与规则

- 动作**定义在某个对象类型上**（`scopeEntityTypeId`），表示"这个动作只在这个类型的对象上执行"。
  对象类型的每个对象都能用它，也在平台里用规则（HIDE）控制"这个对象上出不出现"。
- `params`：`kind` 要么是 `ENTITY_REF`（要选对象类型）要么是 `VALUE`（字面量参数）。
- `edits` 的三种写法：`CREATE_ENTITY`（新建对象，给 `alias` 供后续引用）、
  `SET_PROPERTY`（改主体属性）、`CREATE_RELATIONSHIP`（连关系）。
- 规则 `effect` 三档：`BLOCK` 拒绝执行、`WARN` 只提示、`HIDE` 让动作在这个对象上不出现；
  `HIDE` 必须绑定具体动作，且条件只能看主对象自身属性。

## 数据来源绑定

- `sources[0]` 是**主来源**：对象身份（`primaryKey`）与标题（`titleField`）以它为准。
- 后续来源是**补充来源**（Palantir 的 column-wise MDO）：按主键列逐列对齐连接，只往对象上补属性。
  写补充来源时要写 `primaryKey`，列数与主来源一致、顺序一一对应。
- 只建模、还没接数据：`sources: []` 完全可以，发布前只会给"还没选表"的提示（WARN），不挡发布。
- 但**给某个属性填了 `sourceField` 却没挂来源**，会提示"这个映射落不了地"。
- 技能里只写**连接坐标**（kind / host / port / 数据库 / 模式），**绝不写账号密码** ——
  平台按坐标去匹配本机已登记的数据资源，匹配不上就留空并点名。

## 自检清单（出 JSON 前逐条过）

- [ ] 所有 id 都是 **UUID**（`xxxxxxxx-xxxx-4xxx-8xxx-xxxxxxxxxxxx`），不是中文、不是序号。
- [ ] `groupId` / `implements` / `sourceEntityTypeId` / `targetEntityTypeId` / `scopeEntityTypeId` /
      `linkConstraints[].targetId` / `rules[].actionId` 每一个引用都指得到东西。
- [ ] 关系的两端类型与业务方向一致；没有把关系写反。
- [ ] 实现接口的对象类型：接口里 `required` 的属性都有**同名**属性；`required` 的关系约束都有一条满足它的关系类型。
- [ ] 动作都选了 `scopeEntityTypeId`；入参 `code` 不重复；`ENTITY_REF` 参数选了对象类型；
      `CREATE_ENTITY` 都有 `alias`；赋值的属性在目标类型上存在。
- [ ] 规则都有条件；绑定动作的规则 `actionId` 指得到；`HIDE` 规则有动作。
- [ ] 名称没有重复（对象类型 / 关系类型 / 接口 / 动作各自内部不能重名）。
