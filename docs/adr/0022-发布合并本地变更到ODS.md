# 发布合并本地变更到 ODS

状态：Accepted  
日期：2026-10-20

## 背景

草稿中的手工 CRUD 和动作 CRUD 以稀疏覆盖层保存。发布后，变更必须进入 ClickHouse ODS，而不是写回 Oracle 等业务源库；覆盖层在成功合并后清空。

本文记录逐项访谈中已经确认的口径和仍待确认的问题。

## 决策

### D1：所有含本地 CRUD 的对象类型必须有 READY ODS

- 发布前检查草稿覆盖层涉及的对象类型。
- 只要任一对象类型没有已配置、已启用且状态为 `READY` 的 ODS 镜像，就阻止发布。
- 错误提示必须指出缺失的对象类型、数据资源、模式和源表。
- 提示必须提供跳转到对应 ODS 配置的入口。
- 不允许把未合并覆盖层继续留在 PostgreSQL，也不允许发布后继续依赖查询时叠加。

### D2：版本切换只隔离本地 CRUD

- 所有版本共享当前 ODS 基础镜像；源业务数据变化后，各版本都会读到最新值。
- 每个版本只隔离手工 CRUD、动作 CRUD 和本地关系变更。
- 不把“普通版本切换”解释成源业务数据的历史时点回放；历史时点能力需要独立的时间切片机制。

### D3：发布的是版本级稀疏变更集，不复制完整 ODS

- 不直接修改 ODS 基础镜像，因为基础镜像被所有版本共享，改写后会破坏版本切换。
- 发布时把草稿覆盖层转换成 ClickHouse 中与版本绑定的稀疏变更集。
- ODS 逻辑上由“基础镜像 + 当前版本变更集”组成，满足“最终数据落到 ODS 层”，且不产生整份版本副本。
- 对象变更集与关系变更集分开保存，均使用版本 id 隔离。

### D4：每个版本保存相对基础镜像的累计有效变更

- 新草稿默认继承上一发布版本的累计对象变更集和关系变更集。
- 新版本的 CRUD 在上一个版本累计结果上继续修改。
- 每个版本保存自己的累计有效变更，不保存父子 delta 链；任意版本都可以一次读取，不依赖逐级重放。

### D5：发布是两阶段、可重试流程

1. 校验并生成待发布变更清单。
2. 按发布批次把变更集幂等写入 ClickHouse 暂存区。
3. 校验写入数量、主键、创建/更新/删除分类和版本 id。
4. 原子提交该版本的变更集。
5. 更新 PostgreSQL 版本状态与发布指针。
6. 发布成功后清空 PostgreSQL 草稿覆盖层。

任一步失败都保留草稿覆盖层，不切换发布版本。若变更集已提交但版本状态更新失败，重试必须幂等；若版本已发布但覆盖层清理失败，后台清理即可，不影响查询口径。

### D6：所有发布查询共享一个“有效版本数据”语义

- 对象实例查询、关系子图查询、`run_query` 必须读取同一份“ODS 基础镜像 + 当前发布版本变更集”。
- 发布后的查询不得再次合并 PostgreSQL 草稿覆盖层。
- 草稿预览仍读取 PostgreSQL 覆盖层，且必须显式指定草稿版本。
- 有本地变更的对象类型若来源读取路径为 `DIRECT`，发布必须阻止；否则发布后会绕过版本变更集。

### D7：对象 CRUD 语义

- CREATE：对象可以没有源表行；在版本变更集中保存完整对象属性。
- UPDATE：保存对象的累计有效属性，保证查询不必逐版本重放。
- DELETE：写删除墓碑，不物理删除基础 ODS 行；查询按版本隐藏。
- 手工 CRUD 和动作 CRUD 都只修改草稿；发布后再进入版本变更集。
- 动作必须补齐对象删除能力；动作执行不再提供任何直接写业务源库的选项。

### D8：关系 CRUD 与对象 CRUD 同事务发布

- 现有手工关系 CRUD 继续保留，并进入版本关系变更集。
- 动作当前支持创建关系；后续若增加关系修改/删除，也必须进入同一版本关系变更集。
- 对象与关系变更集在同一发布流程中校验和提交，禁止只发布其中一半。

### D9：ODS 基础同步不清理版本变更集

- 全量/增量 ODS 同步只更新基础镜像。
- 版本变更集独立存储，不参与基础镜像的 `EXCHANGE TABLES`。
- 删除本体版本时，同步删除该版本的变更集和发布清单。

### D10：源业务库永远只读

- 删除动作“写回业务库”接口、执行器和界面入口。
- 发布、手工 CRUD、动作 CRUD 都不得 UPDATE / INSERT / DELETE 源业务库。
- 审计记录必须区分“草稿写入”“发布提交”“版本覆盖提交”，并记录创建、更新、删除数量。

## 实现落点

- ClickHouse 版本对象/关系变更集与契约：`src/lib/infrastructure/ods/clickhouse.ts`、`types.ts`。
- 发布就绪校验和发布提交：`src/lib/instance/ods/publish-readiness.ts`、`version-publication.ts`。
- 草稿继承与发布后快照还原：`src/lib/instance/ods/published-changes.ts`。
- 对象服务、关系子图和 `run_query` 的有效版本读取：对象服务 edit overlay、ODS logical query 与实例 API。
- 发布失败提示和 ODS 跳转：`src/components/ods-publish-blockers.tsx`。
- 动作对象删除与源库写回移除：`src/lib/instance/action-engine.ts`、`snapshot-editing.ts`、动作 API/UI。
- 版本删除与本体存储删除同步清理 ClickHouse 变更集。

## 剩余边界

- 外键式关系的本地关系变更暂时阻止发布；目前只有连接表式关系支持版本关系变更集。
- 发布后的对象列表、关键词检索、关系子图和本体 SQL 已合并版本变更；对象服务在“被覆盖属性”上的高级筛选/排序仍 fail-closed，需继续改为 ODS 有效视图下推，当前不能把源表排序结果冒充完整版本结果。

## 关键约束

直接把发布版本的本地 CRUD 覆盖进唯一的 ODS 基础镜像并清空全部变更记录，会破坏版本切换：旧版本再次查询时也会看到新版本修改。

若要求版本切换隔离本地 CRUD，同时避免每个版本复制整份 ODS，则需要至少保留版本级的**稀疏已发布变更集**。建议把“清空活性覆盖层”解释为：

- PostgreSQL 草稿覆盖层在发布成功后清空；
- 发布变更集写入 ClickHouse，作为与该版本绑定的不可变数据；
- 查询时使用“当前版本绑定的基础镜像口径 + 该版本变更集”；
- ODS 基础表重新校准不得删除版本变更集。

## 版本策略（已确认）

- 版本切换只隔离各版本的本地 CRUD，不隐式保存来源业务数据的历史时点。
- 所有版本共享当前 ODS 基础镜像；切换版本只切换定义和该版本绑定的稀疏变更集。
- 每个版本建议保存“相对 ODS 基础镜像的累计有效变更集”，而不是父子版本 delta 链。这样任意版本切换都能一次读取，不依赖逐级回放。
- 创建新草稿时默认继承上一发布版本的累计变更集；后续修改形成新版本自己的变更集。
- 如果需要源业务数据的历史精确回放，单独建设时间切片快照，不能和普通版本切换混为一体。
