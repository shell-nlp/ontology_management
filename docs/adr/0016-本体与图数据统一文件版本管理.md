# ADR 0016：本体与图数据统一文件版本管理

## 状态

已采纳。

## 决策

一个版本不再只包含实体类型和关系类型定义，而是包含完整、不可拆分的快照：

- `definition.json`：实体类型、关系类型、端点契约和属性规则。
- `nodes.csv`：实体稳定 ID、Label 和属性 JSON。
- `relationships.csv`：关系稳定 ID、起止实体稳定 ID、关系类型和属性 JSON。
- `manifest.json`：格式版本、目标、版本号、实体/关系数量、更新时间和 SHA-256 内容哈希。

版本索引与状态（版本号、状态、数量、哈希、发布时间）保存在同一目录的 `manifest.json` 中；快照文件是该版本实例数据与版本状态的唯一事实来源。默认目录为项目下 `.data/ontology-versions`，可通过 `ONTOLOGY_VERSION_DIR` 指向持久化目录。PostgreSQL 只保存账号、连接目标与审计记录。

> 后续修订见 [ADR 0017](0017-图数据库抽象层与Apache-Jena支持.md)：版本落地改由各图数据库适配器实现，并要求整图替换具备原子性。

生产环境若运行多个应用实例，`ONTOLOGY_VERSION_DIR` 必须指向所有实例可读写的同一个持久卷。不能把各实例的本地临时目录作为版本仓库。

## 生命周期

1. 创建草稿：优先复制当前发布版本的快照；系统升级后的首个版本会从当前 Neo4j 真实数据导出。
2. 编辑草稿：类型、实体、关系、属性和画布位置只修改草稿文件。写操作必须携带草稿 `versionId`。
3. 校验草稿：同时检查类型定义、必填/唯一属性、实例类型、关系类型、端点引用和端点契约。
4. 发布草稿：在单个 Neo4j 写事务中清除现有图并分批创建快照实体与关系；任一批失败时整个图替换回滚。
5. 激活历史版本：读取历史快照并执行同一发布流程。当前存在草稿时禁止切换历史版本。

发布成功后才更新 PostgreSQL 版本状态。平台同时对账自身创建的 `ontology_*` 约束和索引，移除不属于目标版本的规则。

## 稳定标识

Neo4j `elementId()` 在重新导入后会变化，不能写入历史文件作为长期引用。快照为实体和关系分配 UUID，关系通过实体 UUID 连接。发布时 UUID 只在事务内临时用于连接端点，完成后从 Neo4j 节点移除，不污染业务属性。

## 兼容边界

升级前已经归档的旧版本没有实例快照，系统不能使用当前 Neo4j 数据伪造其历史状态，因此这些旧版本不可激活。当前发布版本和现有草稿会在首次使用时从真实 Neo4j 数据生成快照；此后的版本都具备完整切换能力。

Cypher 工作台只允许只读语句。所有平台内写入必须经过草稿快照和发布流程，防止绕过版本边界。
