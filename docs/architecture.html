01 · How to read

先看怎么读这张图

按顺序读三遍：第一遍认角色，第二遍认层次，第三遍认扩展点。

1
Upstream ｜ 先认上游：谁在调这个平台界面用户、外部 Agent 客户端、系统集成方。它们一律通过 HTTP 接口进入。
2
Six layers ｜ 再认六层：请求往里走接入 → 界面 → 接口 → 领域服务 → 扩展点 → 存储与外部系统。箭头方向就是调用方向。
3
Extension points ｜ 最后认扩展点：换中间件改哪里图存储、数据资源、检索索引、对象来源各有一个扩展点，换后端不动上层。

Reading the arrows ｜ 图里的箭头只有两种含义

  • 实线箭头：同步调用，调用方等结果。
  • 可选依赖：图引擎是二选一，不是必须两个都有。
  • 方向：一律「谁调谁」，不做数据流向的猜测。

What this is ｜ 平台的一句话定位

它是一个 单体 Web 应用：浏览器里跑界面，服务端承载全部接口与领域逻辑；本体定义与对象索引落在平台库，本体图落在图引擎，业务事实从外部库按需读取。

Two roles ｜ 它同时是上游和下游

对界面用户与外部 Agent 而言，它是被调用的服务端；对平台库、图引擎、业务数据源与大模型而言，它是发起调用的客户端。所以下面把两侧分开讲。

一个进程，两类身份

同一进程内，接口层负责接收上游请求，领域服务层负责向依赖方发起请求；扩展点存在的意义，就是让"换依赖"这件事不扩散到上游。

All inbound over HTTP ｜ 上游一律走 HTTP

界面与 MCP 客户端只是两种调用形态，鉴权都落在同一套会话与令牌机制上。

Only the graph engine is optional ｜ 只有图引擎可选

内置引擎与 Apache Jena 二选一，由"图引擎连接"配置决定，上层接口不变。

Read-only outward ｜ 对外只读

问答与 MCP 的工具集全部只读；写入业务数据的唯一入口是动作。

05 · Extension Points

四处扩展点：换中间件不动上层

这是这套架构最重要的决定。接口层、界面层与智能问答只依赖抽象，不依赖具体中间件。

Extension 1

Graph Store ｜ 图存储

契约：本体图的读写与查询。

现有实现：内置引擎、Apache Jena。

能力声明：是否支持结构视图、强约束、整图原子替换。

Extension 2

Data Source Connector ｜ 数据资源连接

契约：列结构、试连、取数、DDL。

现有实现：Oracle、PostgreSQL、MySQL。

安全口径：只读事务 + 语句校验，写入一律拒绝。

Extension 3

Object Index ｜ 检索索引

契约：对象索引的写入、检索、过滤、分页与统计。

现有实现：平台库索引表，支持全文与模糊匹配。

可替换：换成独立搜索引擎时上层不变。

Extension 4

Object Source ｜ 对象来源

契约：一个对象从哪来 —— 索引还是业务库。

现有策略：索引、回源、自动。

影响：决定查询的延迟与覆盖面，不改变对外的对象语义。

Adding a backend ｜ 接入一个新后端要动的地方

  • 按契约实现一个后端适配器，独立目录隔离。
  • 在后端类型枚举里登记新类型。
  • 在扩展点注册表里增加一行。
  • 上层无需改动：对象服务、界面、智能问答都只认抽象入口。

Why ｜ 为什么要这么分

  • 换存储不换语义：接口行为保持一致，不会出现"换了库结果就变"。
  • 能力可降级：后端声明自身能力，界面据此决定哪些功能可用。
  • 边界可验证：契约测试跑在真实后端上，新实现照抄同一套用例。
06 · Key Chains

三条关键链路：一次请求怎么走

前面是静态结构，这一页把最常用的三条链路按顺序走一遍。

01

Modeling → Publish ｜ 建模到发布

把对象类型、关系类型、接口与动作建好，校验通过后发布为一个版本；发布同时写图引擎、写检索索引、记审计。

1
画布与表单编辑可视化建模
2
存草稿并校验POST /api/ontology/[versionId]/validate
3
发布版本POST /api/ontology/[versionId]/publish
4
写图引擎 → 写索引 → 记审计发布流水线
02

Reasoning ｜ 智能问答

提问后由工具循环驱动：模型自己决定查什么，平台只提供只读、确定性的事实工具，引用到的真实对象会回收到证据里。

1
提问（可带图片）问答界面
2
流式运行POST /api/reasoning/stream · SSE
3
工具循环模型规划 + 工具执行
4
本体工具查事实图引擎 / 索引 / 业务库
03

External Agent via MCP ｜ 外部 Agent 查本体

外部客户端按 MCP 协议接入，复用问答那同一套工具，因此不会出现"界面上查得到、MCP 里查不到"的漂移。

1
建立会话、列出工具POST /api/mcp · initialize / tools/list
2
发起工具调用POST /api/mcp · tools/call
3
复用同一套只读工具与问答同源
4
返回事实与证据图引擎 / 索引 / 业务库
一份工具，两个入口

平台内的智能问答与对外的 MCP 服务共用同一套只读工具；模型负责规划，工具负责事实，写入业务数据的唯一入口是动作。

07 · Deployment & Boundary

部署形态与运行边界

这张图决定"哪些东西属于这个平台、哪些属于外部环境"。分清楚这一条，部署与排障才有共同语言。

Deployment ｜ 部署形态

  • 编排里只跑平台本体一个服务，镜像自带运行时依赖。
  • 平台库、图引擎、业务数据源都不进编排，按各自的既有方式运行。
  • 本地开发与容器部署共用同一套配置口径，行为一致。

Network & Ports ｜ 网络与端口

  • 对外只暴露一个 HTTP 端口，宿主机端口可配置。
  • 容器访问宿主机上的依赖走宿主机别名，不写死回环地址。
  • 已登记的图引擎端点若指向回环地址，会在容器内按别名自动改写。

State & Persistence ｜ 状态与持久化

  • 本体定义在平台库，已发布版本的本体文件在版本快照目录。
  • 快照目录是状态不是缓存：容器重建不丢，换机器必须一并带过去。
  • 同一平台库上的多套部署，必须指向同一个快照目录。

Security & Credentials ｜ 安全与凭据

  • 统一会话登录，接口按角色区分可写与只读。
  • 数据源与图引擎的连接凭据加密存储，不在界面明文回显。
  • 对业务库一律只读事务 + 语句校验；写业务数据只能通过动作。
  • 关键操作全部留痕，可在审计记录里追溯。
平台职责本体建模 · 版本发布 · 对象检索 · 智能问答 · 动作与审计
→
外部环境职责平台库 · 图引擎 · 业务数据源 · 大模型端点
→

一句话边界

平台负责"本体是什么、版本发到哪、问题怎么答"；存储与算力由外部环境提供。换掉任何一个外部依赖，都只影响对应的扩展点，不影响平台的对外语义。

Why in Platform DB ｜ 索引为什么放平台库

当前只有一种索引实现，抽象已经就位：换搜索引擎时只替换扩展点，对象服务与界面不动。

Why a separate directory ｜ 快照为什么单独放

本体定义在库里、已发布文件在目录里，两者是同一份状态的两半，缺一个都读不到已发布版本。

Credentials ｜ 凭据怎么存

数据源与图引擎的连接凭据加密后入库，界面不明文回显；对业务库一律只读。
