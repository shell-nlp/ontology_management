# 第 2 章 · 安装、部署与初始化

## 2.1 部署前要知道的三件事

平台运行时依赖三类外部系统，职责不能混：

| 系统 | 是否必需 | 作用 | 由谁部署 |
| --- | --- | --- | --- |
| PostgreSQL 平台库 | 必需 | 存本体台账、版本定义与实例快照、用户角色、审计、对象索引、列画像 | 你现有的 PostgreSQL |
| 图存储 | 内置图开箱可用；Jena/Fuseki 可选 | 存发布后的本体投影，供实例读写和 SPARQL 查询 | 用 Jena 时自行部署 Fuseki，否则不用 |
| 业务数据源 | 按需 | 对象与关系的真实数据来源，平台只读访问 | 你现有的 Oracle / PostgreSQL / MySQL |

Docker Compose 默认**只部署平台本体**（`app` 容器）。PostgreSQL、Fuseki 和业务库都不进编排；这意味着你可以复用现有数据库和中间件，不必把生产数据库搬进平台。

## 2.2 环境要求

| 项目 | 开发环境 | 容器部署 |
| --- | --- | --- |
| Node.js | 建议与镜像一致：Node 24 | 镜像自带 `node:24-bookworm-slim` |
| 包管理器 | pnpm 11（`packageManager` 已锁定） | 构建阶段由 Corepack 启用 |
| PostgreSQL | 11+，建议 14+ | 外部已有实例 |
| 可选扩展 | `pg_trgm`、`pgvector` | 同左；缺扩展时相关检索能力降级，不影响平台启动 |
| Oracle 客户端 | 连 11g 及更早服务端时需要 Thick 模式 | 镜像已内置 Linux Instant Client |
| 浏览器 | 支持 localStorage、SSE、现代 ES 语法 | 同左 |

> 平台库可以先建空库；首次访问时自动创建 `ontology_platform` Schema。不需要手工执行建表脚本。

## 2.3 环境变量

### 必填变量

| 变量 | 说明 | 注意 |
| --- | --- | --- |
| `DATABASE_URL` | 平台库连接串，例如 `postgresql://user:pass@host:5432/ontology` | 平台自动使用 `ontology_platform` Schema |
| `TARGET_ENCRYPTION_KEY` | 32 字节 Base64 密钥，用于加密数据资源凭据和 MCP 访问令牌 | 生成：`openssl rand -base64 32`；**换掉会导致已有密文解不开** |
| `AUTH_SECRET` | 至少 32 个字符，用于签名平台会话 JWT（HS256） | 换掉会让所有已登录会话失效 |

### 首次初始化变量

| 变量 | 说明 |
| --- | --- |
| `BOOTSTRAP_ADMIN_EMAIL` | 平台库里没有任何用户时，创建首个管理员的邮箱 |
| `BOOTSTRAP_ADMIN_PASSWORD` | 首个管理员的初始密码 |

首次访问平台时自动建 Schema 并创建首个管理员。库中已有用户时不会覆盖密码，也不会因为改了环境变量而重置账号。`POST /api/bootstrap` 只作为旧调用方的兼容入口保留；在自动初始化完成后再调用会返回 `409`。

### 可选变量

| 变量 | 默认 / 说明 |
| --- | --- |
| `LLM_BASE_URL` | OpenAI 兼容的聊天端点；不配则智能问答明确提示“模型未配置” |
| `LLM_API_KEY` | 上述端点的密钥 |
| `LLM_MODEL` | 模型名；三项必须同时配置 |
| `MCP_API_TOKEN` | 外部 MCP 客户端的只读兜底令牌；生产更推荐在平台里生成可撤销的令牌 |
| `GRAPH_ENDPOINT_HOST_ALIAS` | Jena 端点主机名改写。容器默认把 `localhost` 改成 `host.docker.internal`；远端服务可直接登记真实地址 |
| `ORACLE_CLIENT_LIB_DIR` | Oracle Instant Client 目录；容器镜像已内置，一般不用改 |
| `ONTOLOGY_VERSION_DIR` | 旧部署的磁盘快照目录，只在一次性迁移历史版本时读取；新部署不需要 |
| `APP_PORT` | Docker 映射到宿主机的端口，默认 3000 |
| `NPM_REGISTRY` | 镜像构建用的 npm 源；国内网络建议保留镜像源 |
| `NODE_IMAGE` | 构建镜像名；拉不动 Docker Hub 时换成镜像站 |

### 密钥管理原则

- `TARGET_ENCRYPTION_KEY` 和 `AUTH_SECRET` 不要写进仓库，不要用示例值直接上线。
- 备份平台库时，**必须同时备份当前使用的密钥**；否则恢复后数据资源凭据和 MCP 令牌解不开。
- 多实例部署时所有实例必须使用相同的 `DATABASE_URL`、`TARGET_ENCRYPTION_KEY`、`AUTH_SECRET`。

## 2.4 开发环境启动

```bash
# 1. 准备环境变量
cp .env.example .env.local
# 编辑 .env.local，至少填 DATABASE_URL / TARGET_ENCRYPTION_KEY / AUTH_SECRET / BOOTSTRAP_ADMIN_*

# 2. 安装依赖
pnpm install

# 3. 启动开发服务器（会先生成 OpenAPI，再启动 Next.js）
pnpm dev
```

打开 `http://localhost:3000`，用 `BOOTSTRAP_ADMIN_EMAIL` / `BOOTSTRAP_ADMIN_PASSWORD` 登录。

第一次启动时会自动完成：

1. 在平台库中创建 `ontology_platform` Schema 与所需表；
2. 执行数据库迁移；
3. 如果用户表为空，创建首个管理员；
4. 创建默认的内置图存储选项。

如果要配置智能问答，把 `LLM_BASE_URL`、`LLM_API_KEY`、`LLM_MODEL` 三项填好；否则“智能问答”和“MCP 调试”页会明确显示模型未配置或工具不可用，而不是静默失败。

## 2.5 Docker Compose 部署

### 准备配置

```bash
cp .env.docker.example .env.docker
# 编辑 .env.docker：DATABASE_URL 用 host.docker.internal 指向宿主机或外部 PostgreSQL
```

Docker 环境里最容易踩的坑：

1. **容器里的 `localhost` 是容器自己。** 连宿主机的 PostgreSQL 要用 `host.docker.internal`；compose 已经加了 `host.docker.internal:host-gateway`，Linux 上也能这样写。
2. **Jena 端点若登记为 `http://localhost:3030/...`**，容器默认会通过 `GRAPH_ENDPOINT_HOST_ALIAS` 改写成宿主机地址。远端 Jena 请直接登记可达地址。
3. **`.env.docker` 既给容器注入变量，也给 compose 做变量替换。** `APP_PORT` / `NODE_IMAGE` 也写在这个文件里；手动执行 `docker compose up` 时要带 `--env-file .env.docker`。

### 启动与常用命令

```bash
pnpm docker:up      # docker compose --env-file .env.docker up -d --build
pnpm docker:logs    # 跟平台日志
pnpm docker:down    # 停止并删除平台容器
pnpm docker:config  # 打印合并后的编排，排查变量问题
```

平台数据都在 PostgreSQL 平台库里，`docker compose down` 不会删除本体定义和版本快照。图存储中的数据是发布投影，真的丢客户端也能从已发布快照重新发布恢复。

### 健康检查

compose 给 `app` 容器配了健康检查：请求 `http://127.0.0.1:3000/`，返回 2xx 即为健康。你可以用：

```bash
docker compose --env-file .env.docker ps
docker compose --env-file .env.docker logs --tail=200 app
```

排查时优先看三类信息：平台库能否连接、迁移是否执行成功、应用是否进入了 `NEXT` 的监听状态。

## 2.6 升级与数据迁移

### 正常升级

1. 备份平台库（至少备份 `ontology_platform` Schema）。
2. 拉取新代码，重新构建镜像或重新安装依赖。
3. 启动应用；服务端自动执行增量迁移。
4. 检查“设置 → 图引擎配置”的连接测试，检查“数据资源”的连通性。
5. 打开任意本体，确认版本记录和已发布状态正常。

### 旧磁盘快照迁移

旧部署可能把版本快照放在 `.data/ontology-versions`。当前版本已经把定义与实例快照统一放进平台库 `ontology_platform.ontology_versions`：

- 服务端第一次访问版本数据时，会把磁盘上的历史版本迁进平台库，然后删除磁盘副本；
- 只有旧机器上还有未迁移目录、且你要换机器时，才需要挂载或指定 `ONTOLOGY_VERSION_DIR` / `VERSION_SNAPSHOT_DIR`；
- 全新部署不需要该目录，也不需要多实例共享它。

### 数据库迁移组件

平台库使用 TypeORM 迁移管理表结构。迁移文件位于 `src/lib/platform/db/migrations/`，包括：

| 迁移 | 内容 |
| --- | --- |
| `0001-platform-schema` | 平台基础 Schema：用户、角色、本体台账、图引擎连接、审计等 |
| `0002-audit-version-column` | 审计记录增加版本维度 |
| `0003-column-profiles` | 列画像缓存表 |
| `0004-rbac-roles-and-permissions` | RBAC 角色与权限点 |
| `0005-ontology-versions` | 版本记录统一进平台库 |
| `0006-table-and-column-comments` | 表与字段注释 |

> 业务代码不写裸 SQL；需要新增表或字段时，通过迁移和实体定义完成。运维只需要保证应用有权限执行迁移。

## 2.7 备份与恢复建议

| 数据 | 重要性 | 备份方式 | 恢复后的动作 |
| --- | --- | --- | --- |
| `ontology_platform` Schema | 最高 | PostgreSQL 逻辑备份 / 物理备份 | 直接还原平台库 |
| `TARGET_ENCRYPTION_KEY` | 最高 | 密钥管理系统或离线保管 | 与平台库一起恢复；不一致时重新登记凭据 |
| `AUTH_SECRET` | 高 | 密钥管理 | 恢复后所有旧会话失效，重新登录即可 |
| 图存储数据 | 中 | Jena 数据集备份可选 | 丢客户端可从已发布快照重新发布 |
| 业务库 | 不由平台负责 | 按业务库自身策略 | 平台只读访问，不承担业务库备份责任 |
| 技能目录 | 低 | 随代码仓库管理 | 容器镜像已内置；源码运行时确保 `skills/` 存在 |

**推荐的最低备份集**：`ontology_platform` Schema + `TARGET_ENCRYPTION_KEY` + `AUTH_SECRET`。有这三样，平台的主要定义、版本、账号和审计就能恢复；图存储和对象索引都是可重建的派生数据。

## 2.8 常用命令

| 命令 | 用途 |
| --- | --- |
| `pnpm dev` | 开发服务器；先刷新 OpenAPI，再启动 Next.js |
| `pnpm dev:only` | 不刷新 OpenAPI，直接启动 Next.js（调试用） |
| `pnpm build` / `pnpm start` | 生产构建与启动 |
| `pnpm test` | Vitest 全量单测，默认并行 |
| `pnpm typecheck` | TypeScript 检查 |
| `pnpm lint` | ESLint |
| `pnpm openapi` | 强制重新生成 OpenAPI 与 Swagger 静态资源 |
| `pnpm test:object-index` | 对象索引契约测试（需要平台库） |
| `pnpm test:version-store` | 版本记录契约测试（需要平台库） |
| `pnpm test:schema-comments` | 表/字段注释契约测试（需要平台库） |
| `node scripts/import-ontology.mjs <文件.json>` | 命令行导入本体包 / bkn；支持 `--dry-run`、`--name`、`--publish` |

## 2.9 上线检查清单

- [ ] PostgreSQL 平台库连接可用，账号有建 Schema、建表和迁移权限。
- [ ] `TARGET_ENCRYPTION_KEY` 与 `AUTH_SECRET` 已使用高强度随机值，并纳入密钥管理。
- [ ] 首个管理员已创建并能登录；随后按最小权限原则建立编辑者 / 查看者账号。
- [ ] 数据资源连接一试就通；Oracle 旧服务端已确认走 Thick 模式。
- [ ] 图引擎连接已测试；Jena 的命名图隔离符合“一个本体一个命名图”的要求。
- [ ] 智能问答的 `LLM_*` 已配置，`/api/reasoning/status` 返回模型已配置。
- [ ] 反向代理已开启 HTTPS；需要外部 MCP 时已生成平台访问令牌。
- [ ] 已建立平台库与密钥的备份计划。
- [ ] 已确认当前版本不存在草稿未发布、历史版本误激活等状态残留。
