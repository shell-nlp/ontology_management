第一次使用本体管理平台，不需要先懂数据库、编程或图数据库。

这份指南只回答三个问题：这个平台能帮你做什么、进入系统后先看哪里、遇到一个任务应该怎么开始。

1. 用一句话理解这个平台#

这个平台把公司业务里分散的“客户、订单、设备、线路、区域”等对象整理成一张业务地图，让业务人员能看懂、能查询，也让 AI 能按照同一套业务规则回答问题和执行操作。

可以把它想成三步：

  1. 先告诉平台业务里有什么：客户、订单、设备分别是什么，有哪些属性。
  2. 再告诉平台这些对象之间怎么关联：客户属于哪个区域，订单属于哪个客户。
  3. 最后把业务数据接进来：从公司数据库读取真实数据，在对象页、图谱和智能问答中使用。

平台不是单纯的报表工具，也不是一个直接给 AI 开放数据库的聊天框。它先建立一层统一的业务语义，再围绕这层语义提供查询、问答、规则和外部集成能力。

2. 先用业务语言认识几个名词#

你在界面看到的词 可以先这样理解 例子
本体 一套完整的业务世界说明书 客户、订单、设备以及它们之间的关系
对象类型 一类东西的定义，类似一张业务表或一个分类 客户、订单、专线、设备
对象 这类东西里的一个具体实例 客户“张三”、订单“A1001”
属性 对象上有哪些信息 客户名称、客户编号、状态、所在城市
主键 用来区分“这是哪一个对象”的字段 客户编号
关系类型 两类对象之间有什么关系 客户 ↔ 专线
关系 两个具体对象之间的一条连接 张三 ↔ 专线 A1001
数据资源 平台连接公司业务数据库的配置 Oracle / PostgreSQL / MySQL 连接
数据来源绑定 某个对象类型从哪张表、哪些列取数据 客户对象类型绑定 CUSTOMER 表
草稿 正在编辑、还没有正式生效的内容 还在修改中的客户对象类型
版本 / 发布 把草稿正式保存成一套可供用户和 AI 使用的版本 发布“客户网络 v1”
对象索引 / 物化 把业务数据搬到平台的检索副本里，查询通常更快 把客户和专线先整份物化
动作 平台允许你在对象上执行的操作模板 开通专线、关闭工单
规则 动作执行前的限制、提醒或显示条件 已开通的专线不允许重复开通

最重要的理解是： 对象类型是“定义”，对象是“具体数据”；草稿是“正在改”，发布后才对问答和外部 Agent 正式生效。

查看具体客户、订单、设备 对象页按类型浏览、搜索、查看属性和关系 本体实例 → 对象

用自然语言问业务问题 智能问答、工具轨迹、证据和历史会话 能力验证 → 智能问答

左侧导航按使用目的分成几组。第一次使用不需要把所有页面都点一遍。

导航区域 你在这里做什么 第一次建议

本体模型 → 本体技能 下载建模方法技能或查看技能 MCP 新手可以先不看

本体实例 → 对象 按对象类型浏览真实对象、搜索、编辑、跑动作 最常用的查数入口

看不到某个菜单，通常不是系统坏了，而是当前账号没有对应权限。请联系管理员确认角色。

5. 一次完整使用是怎么走通的#

登录平台
  → 新建或打开一个本体
  → 建对象类型和关系类型
  → 连接业务数据库并绑定数据
  → 校验、发布
  → 在对象页和实例图谱查看数据
  → 用智能问答提问
  → 需要业务操作时定义动作和规则
  → 修改后发布新版本

记住两条最重要的规则：

  1. 编辑先进入草稿，正式使用要发布。 草稿不会影响当前已经发布的版本。
  2. 平台查询定义和数据，不等于修改业务库。 当前动作结果写的是平台草稿快照，不会直接写回生产业务库。

这些内容仍然在系统说明书里保留，但应放到“需要时查阅”的位置，而不是让第一次使用者从这里开始。

这是一条完整的入门教程。建议第一次使用时按顺序操作，先做一个很小的例子，不要一上来就搭完整业务模型。

教程不需要写 SQL，也不需要部署系统；你只需要有平台账号、一个可用的业务库连接信息，以及对应的查看/编辑权限。

1. 我们先做一个什么例子#

假设公司想在平台里管理“客户”和“服务专线”。

业务事实是：

  • 每个客户有一个客户编号和客户名称。
  • 每个客户有自己的状态。
  • 每个客户可以拥有多条服务专线。
  • 每条专线也有自己的编号、名称和状态。

最终想达到的目标：

  1. 能查看客户和专线对象。
  2. 能看到客户与专线之间的关系。
  3. 能搜索某个客户。
  4. 能用自然语言问：“目前有哪些正常状态的服务专线？”
  5. 以后可以给“开通专线”这样的业务操作定义动作和规则。

真实项目的数据通常更复杂。第一次先用一小部分字段跑通，确认流程没问题，再逐步补齐属性、关系和规则。

2. 开始前准备这四样东西#

准备项 说明 去哪里获取
平台地址和账号 能登录系统 管理员提供
账号权限 至少能查看本体和对象；要编辑需有编辑草稿权限 管理员确认角色
业务库连接信息 类型、主机、端口、库/服务名、模式、用户名、密码 数据库管理员或实施人员
目标表信息 客户表、专线表的表名、字段名、主键 数据库管理员或数据工程师

如果没有编辑权限，可以先做到“查看对象和智能问答”；不要在没有权限的情况下反复点保存。

3. 第一步：登录并确认当前本体#

入口：打开平台登录页。

操作：

  1. 输入管理员给你的邮箱和密码。
  2. 登录后进入“总览”。
  3. 看一下页面当前打开的是哪个本体。
  4. 如果还没有本体，不要急着点其他菜单，先进入下一步。
  5. 如果需要切换本体，在总览里选择目标本体卡片。

做完后你应该看到： 页面能显示本体列表或当前本体状态，左侧导航可见。

如果看不到：

  • 看不到菜单：检查账号权限。
  • 看不到总览：确认账号没有登录失效。
  • 页面提示 403：这是权限不足，不是密码错误。

4. 第二步：新建一个本体#

入口：总览 → 新建本体。

操作：

  1. 点“新建本体”。
  2. 填写一个业务人员看得懂的名称，例如“客户服务网络”。
  3. 填写说明，说明这个本体解决什么业务问题。
  4. 第一次建议先使用平台提供的内置图存储。
  5. 如果管理员已经配置了外部图引擎，再按管理员的说明选择。
  6. 保存后进入这个新本体。

做完后你应该看到： 总览里出现“客户服务网络”，当前本体已经切换到它。

先不要做的事：

  • 不要先建几十个对象类型。
  • 不要直接修改图库或数据库。
  • 不要跳过草稿机制直接发布。

5. 第三步：登记业务数据库连接#

入口：平台 → 数据资源。

这一步是把平台接到“业务数据真正存放的地方”。平台默认只读访问，不会因为连接了业务库就自动改生产数据。

操作步骤#

  1. 点“新建数据资源”。
  2. 选择数据库类型：PostgreSQL、MySQL 或 Oracle。
  3. 填写连接信息：
    • 主机；
    • 端口；
    • 数据库或服务名；
    • 模式（如果管理员要求填）；
    • 用户名；
    • 密码。
  4. 先点“试连”。
  5. 试连成功后保存。
  6. 在资源卡片上点“浏览表 / 视图”或“刷新结构”。
  7. 找到客户表和专线表。
  8. 打开其中一张表，确认能看到字段名和几行预览数据。

做完后你应该看到： 数据资源列表里出现新的连接，能看到目标表和字段。

这一步最重要的判断： 不是“保存成功”就算完成，必须能看到表、字段和预览数据。

常见问题#

问题 先检查什么
试连失败 主机、端口、库名、用户名、密码、网络是否可达
能连上但看不到表 模式是否正确，账号是否有该表的读取权限
表字段和业务人员说的不一样 先确认表结构，再到对象类型里做显示名
不想暴露生产密码 使用平台支持的只读账号，不要使用管理员账号

6. 第四步：创建“客户”对象类型#

入口：本体模型 → 本体建模 → 对象类型。

对象类型可以先理解成“客户这类东西的定义”。它不等于某一条客户数据，而是告诉平台：客户有哪些信息、用哪个字段区分不同的客户。

6.1 先创建基本信息#

  1. 进入“本体建模”。
  2. 在画布上点“新建对象类型”，或进入“对象类型”标签后点新建。
  3. 名称填“客户”。
  4. 说明填“公司服务的客户”。
  5. 保存后，右侧或编辑弹窗里会出现详情与“编辑”按钮。

6.2 添加属性#

先只添加四个属性，不要一次把所有列都加进来。

属性显示名 数据类型建议 说明
客户编号 文本或整数 客户唯一身份
客户名称 文本 页面展示的标题
客户状态 文本 正常、停用等
所在城市 文本 业务分析常用

操作顺序：

  1. 打开“客户”对象类型的编辑。
  2. 进入属性区域。
  3. 添加“客户编号”。
  4. 添加“客户名称”。
  5. 添加“客户状态”。
  6. 添加“所在城市”。
  7. 保存草稿。

页面上的中文显示名可以和数据库英文列名不同。例如数据库叫 CUSTOMER_NAME，界面显示名可以叫“客户名称”。这样业务人员不需要记表结构。

6.3 绑定业务数据#

这是让对象真正有数据的关键步骤。

在“客户”对象类型的编辑里找到数据来源：

  1. 选择刚才登记的数据资源。
  2. 选择客户表或视图。
  3. 从表字段中选主键，例如 CUSTOMER_ID。如果一条客户由多个列共同决定，就选多列组成复合主键。
  4. 选择展示属性，例如客户名称。
  5. 把“客户编号”映射到 CUSTOMER_ID。
  6. 把“客户名称”映射到 CUSTOMER_NAME。
  7. 把“客户状态”映射到 STATUS。
  8. 把“所在城市”映射到 CITY。
  9. 保存草稿。

做完后你应该看到： 对象类型详情里能看到来源表、主键、展示属性和属性映射。

6.4 如果还没有数据源#

也可以先只建对象类型，不绑定数据。这样可以先让业务人员评审定义，但要注意：

  • 对象页可能没有数据；
  • 智能问答无法从业务库取数；
  • 实例图谱不会有真实对象；
  • 发布前最好补齐主键和来源。

7. 第五步：建立“客户 ↔ 专线”关系类型#

入口：本体建模 → 关系类型，或在画布上从一个对象类型拖到另一个对象类型。

先重复上一节的做法，创建“专线”对象类型，至少包含：

  • 专线编号；
  • 专线名称；
  • 专线状态。

然后建立关系。

7.1 设置关系名称和两端#

  1. 新建关系类型。
  2. 名称填“客户拥有专线”。
  3. 起点选“客户”。
  4. 终点选“专线”。
  5. 页面会用双向关系表示：客户和专线两个方向都可以查看。

7.2 选择数据来源方式#

最简单的方式是外键式：

  • 专线表里有一个客户编号列；
  • 这个列指向客户的主键。

那么：

  • 客户编号这一端是“被引用方”；
  • 专线表里的客户编号是“外键方”；
  • 平台可以用专线表的客户编号把专线挂到客户下面。

如果关系数据在第三张中间表里，则选择连接表式，并指定中间表和两端连接列。

7.3 填写键映射#

  1. 起点键映射：填写客户端的业务键。
  2. 终点键映射：填写专线端的业务键。
  3. 如果需要，填写关系本身的属性，例如生效日期。
  4. 选择数量关系，例如一个客户可以有多条专线。
  5. 保存草稿。

注意： 关系类型是双向的，不要为正反方向各建两条关系类型。两条不同的关系类型应该代表两个不同的业务事实。

8. 第六步：做一次建模检查和发布校验#

入口：本体建模页头 → 建模体检 / 校验。

推荐顺序#

  1. 点“建模体检”。
  2. 先看提醒，不需要一次消灭所有提醒。
  3. 优先修正会影响业务理解或查询的提醒。
  4. 点“校验”。
  5. 处理“违规”项，违规会阻止发布。
  6. 再点“发布”。

第一次最值得检查的五件事#

检查项 为什么要看
对象类型有没有主键 没有主键就无法稳定识别对象
对象类型有没有绑定来源 没有来源时对象页没有真实数据
展示属性是否正确 它决定列表和图谱上显示什么标题
关系两端和键映射是否正确 配错时图上看不到边
必填和主键规则是否合理 规则太严会导致取数或编辑失败

发布后：

  • 草稿变成当前发布版本；
  • 智能问答和外部 MCP 只读取这个正式版本；
  • 旧发布版本进入历史记录；
  • 平台会重建概念索引并同步发布快照。

9. 第七步：查看对象是否真的有数据#

入口：本体实例 → 对象。

操作：

  1. 选择对象类型“客户”。
  2. 选择查看口径：
    • “业务库 / 实时取数”用于确认源数据；
    • “已物化对象”用于查看平台索引数据；
    • 不确定时先用默认模式。
  3. 在搜索框搜索一个客户名称或客户编号。
  4. 点开一条客户，查看属性、主键和关系。
  5. 再选择“专线”，确认专线对象也能读出来。
  6. 在客户详情里查看一跳关系，确认能看到客户拥有的专线。

做完后你应该看到： 对象页能读到真实客户和专线，详情里有属性和关系。

如果想看图谱#

入口：本体实例 → 实例图谱。

如果图谱是空的，通常不是本体被删了，而是：

  • 对象和关系还没有物化；
  • 当前筛选类型没有数据；
  • 两端对象没有同时出现在当前画面；
  • 关系类型的键映射还没有配置正确。

到对象页里的“索引与物化”查看对象类型和关系类型的完成状态，必要时按提示逐个物化。

10. 第八步：用智能问答问一个业务问题#

入口：能力验证 → 智能问答。

先确认：

  1. 本体已经发布。
  2. 账号有智能问答权限。
  3. 管理员已经配置 LLM。
  4. 需要用到的工具已开启。

可以尝试的问题：

  • “客户有哪些主要字段？”
  • “状态正常的客户有哪些？”
  • “客户和服务专线之间是什么关系？”
  • “哪些专线当前不是正常状态？”

提问后不要只看最终答案，还要看：

  • 工具轨迹：模型调用了哪些工具。
  • 依据：答案引用了哪些对象、关系、对象类型或指标。
  • 页脚信息：模型、耗时、上下文、输出和累计 token。
  • 警告：工具结果是否被截断，是否没有引用已定义的指标。

如果回答不对：

  1. 先检查本体是否已经发布。
  2. 再检查对象类型是否绑定数据源。
  3. 再检查字段显示名和业务含义是否准确。
  4. 最后再看问答配置和工具开关。

11. 第九步：修改一个对象，并让修改正式生效#

对象编辑遵循“先取进草稿，再修改，最后发布”的流程。

  1. 进入“对象”。
  2. 找到目标客户或专线。
  3. 点“取进草稿”。
  4. 修改需要的属性。
  5. 保存。
  6. 回到本体建模，查看草稿状态。
  7. 运行校验并发布新版本。
  8. 重新打开对象页，确认修改已经出现在新版本视图里。

要记住： 业务库对象本身不会因为在平台修改就自动回写。平台当前写的是本体草稿快照，正式生效依赖发布流程。

12. 第十步：导出一份给同事或别的环境#

入口：总览 → 本体卡片 → 导出，或“本体建模”页头。

导出得到的是 .ontology.json 本体包，里面包含：

  • 对象类型；
  • 关系类型；
  • 接口和指标；
  • 动作和规则；
  • 数据资源坐标。

不包含：

  • 业务库密码；
  • 真实对象实例；
  • 关系实例；
  • 平台内部的版本数据。

同事导入后：

  1. 先在草稿里检查对象类型和关系。
  2. 按提示补数据资源绑定。
  3. 重新校验和发布。
  4. 对象数据仍需要从各自环境的数据资源读取或物化。

13. 这条教程完整做完的检查清单#

  • 我能说清楚本体、对象类型、对象、关系类型的区别。
  • 我能新建一个本体。
  • 我能登记数据资源并试连成功。
  • 我能创建对象类型并设置主键、展示属性和属性映射。
  • 我能建立一条有明确业务含义的关系类型。
  • 我能运行建模体检和发布校验。
  • 我能发布一个版本。
  • 我能在对象页查到真实对象。
  • 我能在关系页或对象详情里看到关系。
  • 我能用智能问答问一个业务问题并查看依据。
  • 我知道修改后要发布新版本。
  • 我知道本体包不带实例数据和密码。

这一页不讲底层原理，只按“我现在想完成什么”给操作步骤。

第一次使用建议先完成新手指南和从零跑通第一个本体，再回来按任务查。

任务 1：我要登录并确认自己现在在哪个本体#

入口： 登录页 → 总览

  1. 输入管理员提供的邮箱和密码。
  2. 登录后进入“总览”。
  3. 查看当前本体卡片，确认名称是否正确。
  4. 如果当前不是目标本体，在总览里点击要使用的本体。
  5. 确认左侧导航是否完整。看不到菜单时，联系管理员检查账号权限。

完成后： 页面标题、总览和左侧导航都指向同一个目标本体。

容易混淆： 没有权限不等于密码错误。密码错误通常无法登录；权限不足通常能登录，但某个菜单、按钮或数据看不到。

任务 2：我要新建一个对象类型，例如“客户”#

入口： 本体模型 → 本体建模 → 对象类型

开始前准备： 先写出对象类型名称、最少五个业务属性、主键字段、显示名称字段。

  1. 进入“本体建模”。
  2. 点“新建对象类型”。
  3. 填写业务人员看得懂的名称，例如“客户”。
  4. 填写说明，说明这个对象类型代表什么。
  5. 保存。
  6. 打开“客户”的编辑弹窗。
  7. 添加属性：客户编号、客户名称、状态、所在城市等。
  8. 为每个属性填写显示名、类型和说明。
  9. 指定主键和展示属性。
  10. 保存草稿。

完成后： 画布上出现“客户”节点，对象类型清单里能看到属性和主键。

新手建议：

  • 先只建 3～6 个属性，不要一次搬完整张表。
  • 中文显示名和数据库英文列名分开表达。
  • 主键不能随便选。它必须能唯一区分一条业务对象。

任务 3：我要连接公司的业务数据库#

入口： 平台 → 数据资源

开始前准备： 数据库类型、主机、端口、库/服务名、模式、只读账号和密码。

  1. 点“新建数据资源”。
  2. 选择类型：PostgreSQL / MySQL / Oracle。
  3. 填写连接信息。
  4. 点“试连”。
  5. 试连成功后保存。
  6. 点“刷新结构”或“浏览表 / 视图”。
  7. 搜索目标表，例如 CUSTOMER。
  8. 打开表，确认字段名、类型和几行预览数据。
  9. 记住表名和关键字段，后面绑定对象类型时要用。

完成后： 能稳定看到目标表和预览数据。

注意：

  • 平台默认只读访问业务库。
  • 试连失败时先检查连接信息和网络，不要反复保存错误配置。
  • 没有权限的账号看不到全部表是正常的。

任务 4：我要让对象类型读到真实数据#

入口： 本体建模 → 对象类型 → 编辑 → 数据来源

  1. 打开目标对象类型。
  2. 选择数据资源。
  3. 选择表或视图。
  4. 选择主键列。可以多选组成复合主键。
  5. 选择展示属性列。
  6. 把每个业务属性映射到来源列。
  7. 保存草稿。
  8. 运行发布校验。
  9. 发布新版本。
  10. 到对象页选择这个对象类型，确认能看到真实数据。

完成后： 对象页列表和详情出现真实对象。

如果对象页没数据： 检查来源是否为空、表是否选对、主键是否映射、账号是否有读取权限。

任务 5：我要建立两个对象类型之间的关系#

入口： 本体建模 → 关系类型，或在画布上从一个节点拖到另一个节点

先想清楚： 要表达的是哪一个现实关系？不要为正反方向各建一条。

外键式关系#

适用于：一张表里已经有一个字段指向另一张表。

  1. 新建关系类型，例如“客户拥有专线”。
  2. 起点选“客户”，终点选“专线”。
  3. 选择外键式来源。
  4. 指定外键长在哪一端，例如专线表里有客户编号。
  5. 填写两端键映射。
  6. 填写数量关系，例如一个客户可以有多条专线。
  7. 保存草稿。
  8. 校验并发布。

连接表式关系#

适用于：两张表通过第三张中间表建立多对多关系。

  1. 新建关系类型。
  2. 指定起点和终点。
  3. 选择连接表式来源。
  4. 选择连接表和数据资源。
  5. 填写“连接表列 → 起点对象属性”。
  6. 填写“连接表列 → 终点对象属性”。
  7. 保存、校验、发布。

完成后： 对象详情或关系页能看到关系；如果看不到，检查键映射和关系物化状态。

任务 6：我要查看对象、搜索对象和看图谱#

入口： 本体实例 → 对象 / 实例图谱

查看对象#

  1. 进入“对象”。
  2. 选择一个对象类型。
  3. 在搜索框输入名称、编号或属性值。
  4. 点开对象，查看属性和关系。
  5. 在“已物化”和“业务库”之间切换，对比索引数据和实时源数据。

查看图谱#

  1. 进入“实例图谱”。
  2. 选择要显示的对象类型。
  3. 搜索一个节点并定位。
  4. 展开邻居，查看关系。
  5. 调整筛选和显示数量，避免一次加载太多节点。

如果图谱为空：

  • 对象类型和关系类型可能还没物化；
  • 关系类型可能没配键映射；
  • 两端对象可能不在当前画面；
  • 当前版本可能还没发布。

任务 7：我要让查询更快，使用对象索引#

入口： 对象页 → 索引与物化

“物化”可以理解为：把业务库里的对象和关系先搬到平台的检索副本里。以后查询优先读平台索引，速度通常更快，也能支持图谱和全文检索。

  1. 进入“对象”。
  2. 打开“索引与物化”。
  3. 查看哪些对象类型和关系类型是可读取的。
  4. 选择一个类型或多个类型。
  5. 点“物化”或“一键物化全部可读取”。
  6. 等待后台任务完成。
  7. 查看任务状态、扫描行数、对象数和告警。
  8. 物化完成后，回到对象页或实例图谱查看结果。

注意：

  • 对象物化不等于关系也物化，关系类型要单独处理。
  • 两端对象都要物化，图上才能画得出边。
  • 主键重复会导致多个源行折叠成一个对象，平台会报出折叠数量。
  • 中断、取消或失败后，可以从断点继续。
  • 清除物化不会删除业务库数据。

任务 8：我要修改一个对象，并让它正式生效#

入口： 本体实例 → 对象

  1. 找到目标对象。
  2. 点“取进草稿”。
  3. 修改属性。
  4. 保存。
  5. 回到“本体建模”，确认当前草稿包含这次修改。
  6. 运行校验。
  7. 发布新版本。
  8. 重新打开对象页，确认正式版本里能看到修改。

注意： 业务库对象不是直接在平台修改后就回写源库。平台当前写的是本体草稿快照。

任务 9：我要定义一个业务动作，例如“开通专线”#

入口： 本体建模 → 动作

  1. 先确认“专线”对象类型已经存在，并且有“状态”属性。
  2. 新建动作，名称填“开通专线”。
  3. 选择作用对象类型：“专线”。
  4. 添加参数。如果没有参数，可以先留空。
  5. 添加编辑步骤。
  6. 选择 SET_PROPERTY。
  7. 主体选择当前主对象。
  8. 属性选择“状态”。
  9. 新值填“已开通”。
  10. 保存草稿。
  11. 进入“运行”阶段，选择一条测试专线。
  12. 先做“干跑”，检查会产生什么修改。
  13. 确认无误后再正式执行。
  14. 查看“决策”记录。
  15. 发布新版本，让动作进入正式版本。

完成后： 可以在对象上运行“开通专线”，并看到决策记录。

注意： 当前动作写入平台草稿快照，不会直接修改生产业务库。

任务 10：我要给动作加规则#

入口： 本体建模 → 规则，或动作编辑页的“规则”阶段

先决定这条规则要做什么：

目标 选择处置 例子
不允许执行 BLOCK 已经是“已开通”状态时不能重复开通
允许执行，但要提醒 WARN 客户有欠费，仍允许开通
条件不满足时干脆不显示动作 HIDE 已注销的专线不显示“开通”

配置步骤#

  1. 新建规则。
  2. 选择绑定动作。
  3. 填写规则名称和给用户看的提示消息。
  4. 选择处置：BLOCK / WARN / HIDE。
  5. 添加条件，例如“主对象状态 = 已开通”。
  6. 保存草稿。
  7. 回到动作的“运行”阶段测试。
  8. 用干跑验证规则是否命中。
  9. 校验并发布。

完成后： 不满足条件时会阻止、提醒或隐藏动作，并在决策记录中留下原因。

任务 11：我要用智能问答问业务问题#

入口： 能力验证 → 智能问答

开始前确认：

  1. 目标本体已经发布。
  2. 管理员已配置 LLM。
  3. 你的账号有智能问答权限。
  4. 需要用到的查询工具已经打开。

操作：

  1. 在提问框输入自然语言问题。
  2. 如果需要，先附上图片。
  3. 点发送。
  4. 查看运行状态和最终答案。
  5. 展开“工具轨迹”，看模型查了什么。
  6. 展开“依据”，核对对象、关系或指标。
  7. 需要停止时点“停止”；切页或刷新不会停止运行。
  8. 使用“新对话”开启新话题，不会中断上一轮运行。

好的问法通常包含：

  • 对象类型：客户、专线、订单；
  • 业务条件：状态正常、欠费、最近一周；
  • 想看结果：列表、数量、关系、趋势；
  • 时间范围：今天、上月、2026 年第三季度。

如果回答不准： 先检查发布版本、字段显示名、对象绑定和工具开关，不要直接怀疑模型。

任务 12：我要导入别人给的本体包#

入口： 总览 → 导入

  1. 拿到 .ontology.json 本体包或 bkn 知识网络文件。
  2. 在总览点“导入”。
  3. 上传文件。
  4. 查看导入预览和提示。
  5. 确认对象类型、关系类型、接口、指标和动作。
  6. 保存后系统会创建新本体并停在草稿。
  7. 按提示补齐缺失的数据资源绑定。
  8. 运行校验。
  9. 处理违规项。
  10. 发布。

注意： 本体包不带实例数据，也不带数据库密码。导入后对象数是 0 是正常现象，需要从本环境数据资源重新读取或物化。

任务 13：我要导出一份本体给同事#

入口： 总览 → 本体卡片 → 导出，或本体建模页头

  1. 确认当前发布版本是想要交付的版本。
  2. 点击导出。
  3. 保存 .ontology.json 文件。
  4. 把文件交给同事。
  5. 同事在目标环境导入。
  6. 同事按本环境的数据资源重新绑定和发布。

导出包含： 结构定义、关系、接口、指标、动作、规则和数据资源坐标。

导出不包含： 实例数据、关系数据、数据库密码、MCP 令牌。

任务 14：我要删除草稿或历史版本#

入口： 本体建模 → 页头右侧“版本记录”

版本删除由“删除版本”权限控制，内置角色默认只有管理员拥有。自定义角色需要在“设置 → 用户与角色”里显式授予。

  1. 打开“版本记录”。
  2. 找到要删除的草稿或历史归档。
  3. 点该行的“删除”。
  4. 确认删除。草稿删除后未发布修改会丢失；历史版本删除后不能再激活。
  5. 版本列表会自动刷新。

不能删除： 当前生效版本。要替换当前版本，先发布新版本，或先激活另一个有实例快照的历史版本。

删除不会影响： 图库当前投影、业务库数据和对象索引。

任务 15：我要给外部 Agent 或 MCP 客户端使用#

入口： 能力验证 → MCP 调试

这一项通常由管理员或集成人员操作。

  1. 确认本体已经发布。
  2. 打开 MCP 调试。
  3. 选择平台级或本体级接入地址。
  4. 为本客户端单独生成访问令牌，并选好它代表哪个账号（默认是你自己；查数据用的是那个账号的权限）。 如果你的客户端支持 OAuth（较新的 Agent / IDE 大多支持），也可以跳过这一步：它连上后会自己注册、 并把浏览器打开到授权同意页，你登录后点「允许」即可 —— 平台里不用预先配任何东西。
  5. 按客户端类型复制配置。
  6. 在 MCP 调试页测试工具。
  7. 如果某个工具不可用，到工具开关里按全局或按本体打开。
  8. 需要审计时在“设置 → 审计记录”查看问答与查询记录。

注意：

  • 一个客户端一条令牌，不要多人共用。
  • 令牌代表一个账号：那个账号被停用或改了角色，令牌立刻跟着失效（这是刻意的，不用等令牌过期）。
  • 走 OAuth 接进来的客户端，代表的是在同意页点「允许」的那个人；他要能看到的数据，客户端才看得到。
  • 已注册的 OAuth 客户端在「MCP 调试 → MCP 接入 → OAuth 客户端」里查看，不认识的直接删（删了会连它的令牌一起作废）。
  • 外部 MCP 默认只读。
  • 草稿不会作为外部 Agent 的正式读源，先发布版本。

任务 16：我要新增用户或调整权限#

入口： 设置 → 用户与角色

需要用户管理权限。

  1. 进入“用户与角色”。
  2. 点新建用户。
  3. 填写邮箱和初始密码。
  4. 选择角色：管理员、编辑者、查看者或自定义角色。

  9. 修改角色后，旧令牌也会立即按新权限生效。

注意： 平台不会允许删除、停用或降级最后一个能管理用户的账号。

第一次使用平台，请先看新手指南和从零跑通第一个本体。本章用于建立整体认识，不需要按技术顺序背下来。

1.1 系统是什么#

本体管理平台是一套面向企业数据与 AI 应用的本体（Ontology）建模、版本管理和能力验证平台。它把“业务世界由哪些对象与关系组成、这些对象的数据从哪里来、对它们可以做什么操作”固化成一份可版本化、可发布、可被模型和外部 Agent 使用的定义。

平台的重点不是提供一个孤立的图数据库，而是提供一条完整链路：

业务定义（对象类型 / 关系类型 / 接口 / 指标）
        ↓
绑定业务数据（数据资源、表/视图、主键与列映射）
        ↓
草稿校验 → 发布为版本快照 → 图存储中的已发布视图
        ↓
实例图谱 / 对象 / 关系 / 动作与规则
        ↓
智能问答 / MCP / 外部 Agent 只读消费

可以用三句话概括：

  • 本体模型回答“这个业务世界里有什么”：对象类型、属性、关系类型、接口、指标、概念分组。
  • 本体实例回答“现在实际有哪些对象和关系”：实例图谱、对象页、关系页，以及对象索引与回源读法。
  • 动作与规则回答“允许对它做什么”：动作是唯一的业务写入口，规则挂在动作上负责拦截、提示和隐藏。

1.2 分层架构#

理解这套架构只需要抓住一条主线：

平台库是定义和版本的权威存储；图存储是发布后的投影；业务库是对象事实的来源。三者职责不同，不能混着理解。

1.3 核心术语#

术语 一句话解释 常见误读
对象类型（Object Type） 一组对象的定义：属性、主键、展示属性、接口、数据来源 不是“一张表”；表只是它的数据落地方式之一
对象（Object） 对象类型的一个具体实例，例如“张三”“某条专线” 不等于图里一个孤立节点；身份通常是“对象类型 + 主键”
关系类型（Link Type） 两个对象类型之间关系的定义，一条定义、两个端点、双向可用 不是“关系实例”；也不需要为正反方向各建一条
关系（Link） 两个具体对象之间的一条边 关系实例的数据来源可以来自中间表，也可以来自外键
属性（Property） 对象类型或关系类型上的一个字段定义，含类型、必填、主键、枚举、来源列等规则 属性可以来自不同数据来源，不一定来自同一张表
接口（Interface） 一组属性、关系和动作约束组成的抽象契约；对象类型可以实现多个接口 不是父类继承；平台里没有父子继承，抽象机制只有接口
指标（Metric） 一条业务口径：作用对象类型、聚合方式、固定过滤、可用维度、单位 指标不是查询结果，也不存数
概念分组 对象类型的业务域归类，只影响画布分组、检索与工具呈现 不参与图推理，不改写本体定义
动作（Action） 定义在对象类型上的一组写操作模板，是业务写入的唯一入口 不是任意脚本；参数、编辑步骤和规则都由平台校验
规则（Rule） 挂在动作上的 BLOCK / WARN / HIDE 条件与提示 规则不是独立写入通道，必须依附动作语义
数据资源 外部业务库的只读连接，例如 Oracle / PostgreSQL / MySQL 不是本体存储，也不是平台库
图引擎连接 / 本体存储 本体发布后投影到哪个图库：内置类型图或 Jena/Fuseki 不是业务数据源；删图数据不等于删版本快照
版本（Version） 一份不可拆分的完整快照：定义 + 对象节点 + 关系边 + 内容哈希 + 状态 不只是“类型定义的历史”
本体包（Bundle） 单文件 .ontology.json，携带结构定义与数据资源坐标，不含实例和凭据 不是平台内部版本快照的替代品

1.4 三条生命周期#

本体定义的生命周期#

新建/导入本体
  → 创建草稿（复制当前发布版或从空白开始）
  → 在可视化画布或各清单里编辑
  → 建模体检（建议）/ 发布校验（门禁）
  → 发布（整图替换）
  → 历史版本激活（有草稿时禁止切换）

对象数据的生命周期#

业务库中的一行数据
  → 对象类型绑定数据来源（主来源 + 可选补充来源）
  → 按主键形成对象身份
  → 对象服务：优先读对象索引，缺失则回源业务库
  → 需要编辑/跑动作时，把业务对象“取进草稿快照”
  → 动作执行成功后写入草稿快照
  → 发布新的本体版本，形成新的已发布视图

能力验证的生命周期#

发布一份可信的本体版本
  → 平台内智能问答使用只读工具查询定义与数据
  → 外部 MCP 客户端用会话或访问令牌接入
  → 工具按全局默认 + 本体覆盖的开关决定模型能看到什么
  → 问答运行、工具调用和关键平台操作进入审计

1.6 典型使用场景#

场景一：从零建一个本体#

  1. 在“总览”新建本体，选择内置图存储或已登记的 Jena 连接。
  2. 进入“本体建模 → 可视化建模”，先落对象类型，再从节点拉出关系类型。
  3. 在对象类型里补属性、主键、展示属性、枚举值与接口实现。
  4. 如已有外部数据，先在“数据资源”登记连接，再回到对象类型绑定主来源和补充来源。
  5. 用“指标”把关键业务口径固化下来。
  6. 先跑“建模体检”优化，再“校验”并“发布”。
  7. 在“对象/实例图谱”确认数据能读出来，在“智能问答”用自然语言验证。

场景二：把已有本体交给外部 Agent#

  1. 确认本体已发布，且工具开关按需要打开。
  2. 进入“MCP 调试 → MCP 接入”，选择平台级或本体级地址。
  3. 在“访问令牌”里为本客户端生成一条令牌；不要多个客户端共用一条。
  4. 复制对应客户端的配置片段，填入客户端。
  5. 让 Agent 先用 list_ontologies / search_schema 确认概念，再查类型、表结构和数据。

场景三：从别人的环境接收一份本体#

  1. 拿到 .ontology.json 本体包或 bkn 知识网络。
  2. 在“总览 → 导入”上传；大文件用 scripts/import-ontology.mjs 命令行导入。
  3. 导入后一定停在草稿，按提示补齐没接上的数据资源绑定。
  4. 运行“校验”，处理硬性违规；体检建议可按优先级处理。
  5. 发布后，实例数据仍需从数据资源物化或回源读取，包里不会带对象数据。

1.8 系统边界#

以下内容是明确的边界，不是“还没写文档”：

  • 本体定义与实例快照在平台库，图库只存发布后的投影。 不要直接改图库并指望平台把它当成新版本。
  • 智能问答与 MCP 全部只读。 业务数据写入只能通过动作；动作也作用在草稿快照上，需要发布才进入新版本视图。
  • 本体包不带实例数据。 statistics.objects 只是导出端的计数，接收端导入后对象数是 0。
  • 平台没有父子继承。 需要表达“多个类型共享一套形状”时用接口。
  • 表只能通过对象类型到达。 智能问答不提供 list_tables / search_columns 这类直接枚举数据源表的工具。
  • 对象索引是派生数据。 它坏了可以从已发布快照重建，不影响本体版本的正确性。
  • 当前没有 embedding 提供方。 PostgreSQL 的向量列和索引可以建，但没有模型生成向量，向量检索暂不可用。

第一次建模请先跟着从零跑通第一个本体操作。本章是对象类型、关系类型、接口和指标的详细参考。

4.1 本体模型由什么组成#

平台把本体模型拆成六类可独立维护、又互相引用的对象：

组成 作用 是否参与发布
概念分组 把对象类型按业务域归类，决定画布分组框与检索视图 是，随版本发布
对象类型 定义对象有哪些属性、主键、展示属性、接口与数据来源 是
关系类型 定义两个对象类型之间的业务关系、连接键、数据来源与数量关系 是
接口 定义“实现我的对象类型必须满足什么属性、关系和动作约束” 是
动作 定义在某个对象类型上的写操作模板 是
规则 挂在动作上的拦截、提示、隐藏条件 是
指标 把一条业务口径固化下来，供模型和程序引用 是

平台里没有父子继承。entityTypes[].parents、class-hierarchy、父类/子类这类概念已经删除。要表达“多个类型共享同一套形状”，用接口。

4.2 建模入口与草稿机制#

入口：左侧 本体模型 → 本体建模。

页面顶部是一排标签，顺序固定：

可视化建模 · 概念分组 N · 对象类型 N · 关系类型 N · 接口 N · 指标 N · 动作 N · 规则 N

默认进入“可视化建模”。页头右侧始终显示版本状态：

  • 当前发布版本：当前版本 vN；
  • 存在草稿时并列显示草稿版本；
  • 可创建草稿、查看版本记录、激活历史版本。

搜索建模内容#

标签栏右侧有一个「搜索本体模型」输入框。它不只看当前标签，而是同时搜索概念分组、对象类型、关系类型、接口、指标、动作和规则； 匹配范围包括名称、说明、属性名、数据来源、动作 code、关系两端和指标口径等。输入后页面切换为分组结果列表：

  • 点对象类型或关系类型的结果会直接打开对应编辑入口；
  • 点接口、指标、动作、规则或概念分组的结果会切到对应标签；
  • 清空搜索后回到原来的标签页。

对象类型、关系类型、指标、动作和规则多起来以后，用这里找，不用逐排滚动。

草稿机制#

  • 第一次编辑会自动创建草稿；草稿优先复制当前发布版本；
  • 所有编辑只改草稿，不影响正在被问答和 MCP 读取的已发布版本；
  • 画布增删改、属性编辑、关系端点调整、指标编辑都立即写平台库草稿；
  • 校验通过后才能发布；发布后草稿状态变为 PUBLISHED，旧发布版本变为 ARCHIVED；
  • 存在草稿时不能激活历史版本，必须先发布或删除草稿。

删除本体#

删本体（DELETE /api/ontologies/{id}，需要「编辑草稿」权限）会连带清掉它名下的一切，不是只删一行记录：

一起清掉的 说明
图存储记录 + 命名图 这个本体独占的隔离空间
版本与实例快照 ontology_versions
概念检索索引 ontology_concepts（按版本派生的那份）
对象索引 / 边索引 / 物化清单 ClickHouse 三张表（派生数据，本来就能重建）
物化任务历史 materialization_jobs
问答会话与消息 这个本体下的对话

审计不删："谁在什么时候删了哪个本体"必须留痕。级联清单在 purgeTargetData() 一处维护 —— 以后新增任何"按本体存"的数据，都要加进那一处，否则又会攒孤儿。

编辑权限#

操作 需要权限
查看模型、版本记录、导出 ontology.read
编辑草稿、绑定数据源、导入 ontology.write
校验、发布、激活、清图 ontology.publish

4.3 可视化建模#

可视化建模是默认工作区，适合从整体结构开始搭模型。

常用操作#

  • 接口节点用紫色虚线圈和 ◇ 标签表示；
  • “实现接口”一定是紫色虚线；接口承接的关系不是虚线，用青绿色实线区分；
  • 选中实现方对象类型时，它从接口继承来的关系类型会临时挂到实现方身上，让“这个类型实际有哪些关系”一眼可见；
  • 不选中任何对象时，接口承接的关系挂在接口节点上，不会重复画成两条平行线；
  • 被提取成接口的原对象类型作为影子节点保留，但画布隐藏影子节点，显示紫色接口节点与实现边。

4.4 概念分组#

概念分组是对象类型的业务域归类，例如“客户域”“产品域”“资源域”。

  • 先新建分组，再在对象类型详情或编辑对话框里选择归属；
  • 未归组的对象类型显示为“未归组”；
  • 分组只影响画布分组布局、颜色框、检索面和工具呈现，不进图库、不参与推理、不改写对象类型本身；
  • 智能问答可用 list_concept_groups 查看分组，按分组找类型；
  • bkn 导入会带上概念域分组。

4.5 对象类型#

对象类型是本体建模的核心。它回答“这一类对象由什么组成、怎么识别、标题怎么显示、数据从哪里来”。

4.5.1 基本字段#

字段 是否必填 说明
名称 是 业务与技术通用名；在界面、工具、本体包里都使用它作为主要引用

主键 发布前建议必填 由主来源的表/视图列定义；支持复合主键
展示属性 否 对象在列表和图谱上的标题；留空时按属性、主键或 id 回退
概念分组 否 所属业务域
实现的接口 否 可多选；实现后必须满足接口约束
属性 发布前建议完整 对象的字段定义
数据来源 按使用场景 主来源 + 可选补充来源；纯建模阶段可以暂时留空

4.5.2 属性类型#

支持以下数据类型：

类型 说明
TEXT 文本
INTEGER 整数
DECIMAL 小数 / 定点数
BOOLEAN 布尔
DATE 日期
DATETIME 日期时间

JSON JSON 原始结构

每个属性还可以配置：

配置 说明

说明 属性口径、单位、业务含义；上限 2000 字

4.5.3 数据来源绑定#

绑定写在对象类型上，而不是逐个对象上，符合 Palantir 的模型：

对象类型 ≈ 数据集，对象 ≈ 一行，属性 ≈ 一列。

平台支持多来源对象类型（column-wise MDO）：

  • sources[0] 是主来源，决定对象身份（主键）和标题；
  • 后面的来源是补充来源，通过“主表主键列 → 本表对应列”的键映射补齐属性；
  • 属性通过 sourceId 指回来源，通过 sourceField 指向具体列；
  • 老快照里的单来源 source 字段会自动折成 sources[0]，不会丢绑定。

绑定规则分两档：

情况 处理
补充来源选了表却没有连接键、连接键列数和主键对不上、属性指向已不存在的来源 拦发布，属于自相矛盾的配置
主来源尚未选表 / 未指定主键、补充来源未选表、同一张表挂两次 只提醒，不拦发布；允许先搭结构后补数据

具体操作见第 8 章“数据资源与列画像”。

4.5.4 从无数据源对象类型提取为接口#

在满足条件时，可以把一个没有数据源的对象类型“提取为接口”：

  • 原对象类型与底层关系保留为兼容影子；
  • 新增接口记录 promotedFromEntityTypeId 指向原对象类型；
  • 原对象类型上的关系转成接口的关系约束；
  • 画布隐藏影子节点，显示紫色接口节点与实现边；
  • 不会根据关系另一端自动推断谁实现了接口；实现关系必须显式声明。

这样做只是把类型层投影成接口，不是删除实例数据。

4.6 关系类型#

关系类型回答“两个对象类型之间是什么关系、数据上怎么连、走一次会不会放大行数”。

4.6.1 关系类型是双向的#

一条关系类型只有一个定义、两个端点；建好之后两个方向都能走。

  • 不配置正向/反向名字；
  • 不要为正反方向各建一条关系类型；两条并列关系类型表示的是两个不同的现实关系；
  • 界面用 ↔ 表示双向；
  • 多跳遍历默认不分方向，可以收窄为 forward / backward；
  • 接口关系约束按双向判定，实现方在这条关系的任一头都算满足。

Palantir 的 link type 也是这个语义；平台与它对齐。

4.6.2 端点与键映射#

配置 说明
起点对象类型 / 终点对象类型 这条关系连接哪两个对象类型
起点键映射 连接表列 / 外键属性 → 起点对象类型的属性；多行就是复合键
终点键映射 连接表列 / 外键属性 → 终点对象类型的属性；多行就是复合键
关系属性 关系本身也可以有属性，例如生效日期、权重、来源系统
数据来源 关系实例从哪里读：中间表式或外键式
数量关系 ONE_TO_ONE / ONE_TO_MANY / MANY_TO_ONE / MANY_TO_MANY，空串表示未标注

4.6.3 两种数据来源#

模式 适用场景 配置要点
JOIN_TABLE 多对多关系，有一张中间表 两端的键映射分别写“中间表列 → 对象类型属性”
FOREIGN_KEY 一对一 / 多对一，外键长在某一端对象类型的表上 外键那一端填外键属性，另一端填被引用的属性；view 留空时用外键所在端的主来源表

不配置数据来源不算错：这种关系类型只在类型层声明业务语义，暂时读不出关系实例。发布前校验不会因此拦你。

两端键映射空着会一直被提醒（2026-10-12）：键映射是选填的，不填不挡发布 —— 但代价是读不出关系实例。 选填项的代价不能只写在文档里，所以提示摆在三个不靠用户自己找的地方：

位置 提示
「关系类型」标签的清单 每行一个状态牌：配好了显示 键映射 CUST_ID → 客户标识（悬停给出取数走哪张表、哪种模式），没配显示 键映射 未填 · 读不出边（悬停给出具体原因）；清单抬头标「N 条读不出实例（缺键映射 / 连接表）」
关系类型编辑器 顶部一条黄色提示，按 planLinkSource 的结论分两档：没填 →「两端的键映射还空着 —— 这条关系类型读不出实例」；填了但读不出 →「键映射填了，但这条关系类型还读不出实例」+ 具体原因（如"还没选数据资源"、"判断不出外键长在哪一端"）。两档都带一个跳到键映射区块并高亮的按钮；键映射区块标题挂红字牌「还没填 · 图上看不到边」
编辑对话框页脚 主按钮禁用时自己灰化（opacity:.45 + cursor:not-allowed，主按钮底色写死，浏览器不会替我们灰），并在按钮旁写明不能保存的原因（如「名称是空的，填上名称才能保存」）＋「去填名称」把该字段滚回视野并聚焦；保存中写明正在做什么（建草稿 → 写定义 → 重载，2～5 秒）并禁用「取消」
画布右栏 选中这条关系类型时一句提醒：读不出实例、图上看不到边、也整份物化不了
对象页「索引与物化」 关系类型那段的表尾按条数汇总：还有几条读不出、共几条、为什么、去哪儿补（见 06）

4.6.4 数量关系与聚合安全#

数量关系描述的是起点端 → 终点端走一次会放大几倍，只用于判断聚合是否会重复计数：

数量关系 含义
ONE_TO_ONE 一个起点最多对应一个终点
ONE_TO_MANY 一个起点可能对应多个终点，按起点聚合会放大
MANY_TO_ONE 多个起点对应一个终点，按起点聚合安全
MANY_TO_MANY 两端都可能多个，聚合默认拒绝

它不是正反向名字，也不改变关系双向性。反方向查询时平台会自动翻转数量关系来评估。

查询 DSL 的聚合查询遇到可能放大行数的关系会默认拒绝执行，属于 fail-closed：宁可拒查，也不静默算错。

4.7 接口#

接口（Interface）是平台唯一的抽象机制，语义对齐 Palantir 的 interface。

4.7.1 接口能声明什么#

约束 说明
属性 实现方必须提供这些属性；可以要求必填、类型等
关系约束 实现方必须有一条符合形状的关系；接口说“应该连什么”，具体关系类型由实现方决定
动作约束 实现方必须有一个动作能完成这件事，并映射到自己的动作 id
接口继承 一个接口可以继承多个接口；实现方要同时满足本接口和继承来的约束
说明 接口的用途与适用场景

4.7.2 对象类型如何实现接口#

对象类型在 implements 里声明实现哪些接口，并可以配置显式映射：

  • 接口属性 name 可以映射到实现方自己的属性名，不要求同名；
  • 没写映射的接口属性按同名匹配；
  • 接口动作约束名映射到实现方自己的动作 id，动作必须作用在实现方身上；
  • 发布前校验会检查：required 属性是否有映射、关系约束是否满足、动作约束是否映射。

一个对象类型可以实现多个接口，分别服务不同应用场景。

4.7.3 画布、工具与右栏三处口径#

实现接口 = 继承接口的关系类型，这个语义必须三处一致：

位置 行为
画布 默认接口承接的关系挂在接口节点上；选中实现方时，临时改挂到实现方，让“A 实际有哪些关系”可见
智能问答工具 interfaceDerivedLinks() 把接口约束算成实现方的边；get_object_type 放在 one_hop.via_interfaces，traverse_object_types 把接口边打上 via_interface
关系类型右栏 若关系端点落在接口影子上，写明“由接口 X 承接”，并提供“编辑接口”入口，不需跳转到接口标签

如果三处只改一处，用户就会看到“接口有关系、实现方却显得孤立”之类的断层。

4.7.4 接口编辑#

接口按“对象类型那套方式”编辑：

  • 右栏只放详情与“编辑”按钮；
  • 点“编辑”打开接口对话框，壳与“编辑对象类型”一致；
  • 对话框左栏是表单，右栏是画布预览，底部是“取消 / 保存修改”；
  • 可改名称、说明、继承的接口、属性、关系约束、动作约束，并勾选谁实现了它（写回对象类型的 implements）。

接口标签页保留作为完整视图（继承关系、实现缺口），但不是唯一编辑入口。

4.8 指标#

指标把业务口径从列注释搬到定义层。一条指标说清“这个数怎么算”，但不存数、不返回查询结果。

4.8.1 指标字段#

字段 说明
名称 指标名，例如“互联网专线条数”
说明 口径边界、统计范围、注意事项
作用对象类型 这条指标算的是哪个对象类型
聚合方式 SUM / COUNT / COUNT_DISTINCT / AVG / MIN / MAX
被聚合属性 聚合作用在哪个属性上；COUNT 不填属性表示数行数
固定过滤 口径的一部分，例如“只看互联网专线”“排除红冲”
可用维度 可以按哪些属性分组看，例如地市、产品、月份
时间维度 按哪个属性看趋势；留空表示不是时序指标
单位类型 / 单位 原样保留外部定义与业务单位
状态 draft（未定稿）/ verified（已验收）
负责人 / 标签 出数有疑问找谁；便于检索和治理

4.8.2 指标的校验口径#

发布前检查由 metrics.ts 统一收口：

情况 处理
指标重名 拦发布
作用对象类型不存在 拦发布
聚合属性、过滤属性、可用维度、时间维度指向不存在的属性 拦发布
没有选作用对象类型 提醒，不拦发布
SUM / AVG / MIN / MAX 用在非数值属性上 提醒，不拦发布

4.8.3 模型如何看到指标#

  • list_metrics：列出指标定义；
  • get_object_type：返回该对象类型上的指标；
  • 系统提示词的概念清单里会带一行“指标：…”；
  • 概念检索 search_schema 会检索指标名称、说明和口径。

只加定义、不加这几处，模型看不到指标，就还会去猜口径。

4.9 建模体检与发布校验#

平台把“建得好不好”和“能不能发布”分成两层。

建模体检#

建模体检是离线质量规则，只给建议，不挡发布：

级别 含义 例子
WARN 该改，影响可用性或一致性 空壳对象类型、孤悬类型、主键列没有属性接、命名打架、接口没人实现
INFO 可以更好，可选优化 属性缺少说明、分组策略可以整理

它只检查定义内部自洽，不连业务库比对真实列。体检结论带稳定规则码，界面、MCP 工具、技能文档都引用它。

发布校验#

发布校验管“能不能发布”，拦不住的都算 bug。它会检查：

  • 对象类型、关系类型、接口引用的 id 是否存在；
  • 关系端点是否合法，端点契约是否满足；
  • 必填/主键属性规则是否自相矛盾；
  • 接口实现的属性、关系、动作约束是否满足；
  • 补充来源的连接键是否完整、属性是否指向存在的来源；
  • 动作定义：作用对象类型、参数、编辑步骤、别名引用是否合法；
  • 规则是否绑定了有效动作、条件是否完整、HIDE 是否只依赖主对象；
  • 指标的硬性违规；
  • 数据源绑定的硬性矛盾。

校验结果分为违规（阻断）和提醒（不阻断）。发布前建议先跑“建模体检”清掉 WARN，再跑发布校验。

4.10 建模最佳实践#

  1. 先定对象，再定关系。 对象类型是稳定骨架，关系类型是对象之间的连接语义；不要先画一堆连线再回头拆对象。
  2. 主键先落。 没有主键的对象类型可以发布，但对象身份、回源取数、对象索引和关系实例都会受影响。
  3. 命名用业务词。 界面显示名给业务看，机器名给代码和数据列用；两者不要混用。
  4. 能写枚举就写枚举。 码值口径写进定义层，模型和问答应答都会更稳定。
  5. 关系类型保持双向语义。 需要反向名称时优先在应用层表达，不要新建第二条反向关系类型。
  6. 抽象用接口。 不要再引入父子继承；接口属性支持显式映射，不需要强行同名。
  7. 指标只写口径。 不把某个时点的查询结果写进指标描述，也不把固定过滤写成可选项。
  8. 先体检再校验再发布。 体检提升质量，校验负责安全；发布永远走平台流程，不要直接改图库。
  9. 绑定来源前先登记数据资源。 结构缓存和列画像都建立在资源连接和对象类型绑定之上。
  10. 改完同步说明书。 如果改变协议、语义或安全边界，同一交付里更新本章及对应章节。

4.11 当前限制#

  • 没有父子继承，只有接口。
  • 关系类型不配置正反向名字；方向由查询时的 direction 决定。
  • 关系实例目前支持中间表式和外键式两种来源；更复杂的支撑方式暂未覆盖。
  • 指标只描述口径，不存数；实际数值仍由查询 DSL / SQL 按对象类型绑定的源表计算。
  • 纯建模阶段允许主来源、主键暂时为空，但发布后对象服务可能读不到对象；界面会用提醒而非硬拦截。
  • 画布位置是浏览器本地状态；只有草稿实例位置写入版本快照。
  • 清单类数据默认给全；只有按分数排序的检索结果才按上限截断，并且必须回传总数与省略数。

如果你还不熟悉“草稿、校验、发布、导出”，先看常见任务教程的对应任务。本章详细解释版本与交付机制。

5.1 版本是什么#

平台里的一个版本不是“只存类型定义的历史”，而是一份不可拆分的完整快照：

内容 说明
本体定义 对象类型、关系类型、接口、指标、动作、规则、概念分组
实例快照 对象节点、关系边与画布位置
版本元数据 版本号、状态、对象数、关系数、内容哈希、发布时间
概念检索索引 从定义拍平出来的一行行概念，供 search_schema 检索

版本记录统一存在平台库 ontology_platform.ontology_versions：

  • definition 是 jsonb，一行一个版本的完整定义；
  • snapshot 是 jsonb，一行一个版本的实例快照，历史激活时用它整图回滚；
  • 版本元数据在同行其它列；
  • 图库（内置图或 Jena）里存的是发布后的投影，不是定义本身；
  • 磁盘上不再有本体版本数据；旧部署的 .data/ontology-versions 只在一次性迁移时读取。

5.2 版本状态与生命周期#

版本有三种状态：

状态 含义
DRAFT 草稿，可编辑；同一时间一个本体存储最多存在一个草稿
PUBLISHED 当前已发布版本，问答和 MCP 只认它
ARCHIVED 历史版本，可查看、可激活（前提是它有实例快照）

标准生命周期：

创建草稿
  → 编辑草稿（定义 + 对象 + 关系 + 画布位置）
  → 建模体检（建议）
  → 发布校验（门禁）
  → 发布：整图替换 + 版本状态切换
  → 需要回滚时：激活历史版本

创建草稿#

  • 优先复制当前发布版本；没有发布版本时复制空白定义；
  • 从图库导出当前数据形成实例快照；
  • 此后所有写操作都要求携带草稿的 versionId。

编辑草稿#

  • 类型、对象、关系、属性、画布位置的修改只影响这条草稿记录；
  • 发布之前，已发布版本继续对问答、MCP 和只读查询生效；
  • 草稿可以反复保存、校验、查看体检结果，不要求一次成型。

校验#

校验同时检查定义和实例：

  • 必填 / 主键属性；
  • 实例类型与关系类型的端点契约；
  • 关系两端引用是否合法；
  • 补充数据来源的连接键；
  • 接口的属性、关系、动作约束；
  • 指标与动作规则的硬性错误。

校验结果分“违规”和“提醒”；违规会阻断发布，提醒只提示。

发布#

发布由后端图存储适配器执行整图替换，要求原子：

  • 成功：新版本整体生效，旧发布版本归档；
  • 失败：图数据保持发布前的状态，版本仍是草稿；
  • 图库失败但索引已经写入：平台会把版本留在草稿，并给出“重新发布以恢复一致”的提示。

发布成功后，平台会：

  1. 将新版本状态改为 PUBLISHED，记录发布时间；
  2. 将旧发布版本改为 ARCHIVED；
  3. 重建概念检索索引；
  4. 同步对象索引（按发布快照物化）；
  5. 对账平台创建的约束和索引。

激活历史版本#

  • 只有存在实例快照的历史版本可以激活；
  • 存在草稿时禁止激活历史版本，必须先发布或删除草稿；
  • 激活走与发布相同的整图替换流程；
  • 旧归档版本若没有实例快照，不能用当前图数据伪造历史状态，会明确报错。

删除版本#

  • 版本删除由 ontology.version.delete 权限控制；内置角色里默认只有管理员拥有，编辑者即使能发布、激活也不能删除。自定义角色如需该能力，必须显式授予。
  • 草稿可以删除，用来放弃这次未发布的修改；删除后草稿里的对象、关系、画布位置和定义都会一起消失。
  • 历史归档可以删除；删除会连同该版本的定义、实例快照和概念检索索引一起删除，之后不能再激活。
  • 当前生效版本（PUBLISHED）不能直接删除。需要先激活另一个有实例快照的历史版本；重置整份版本记录同样需要“删除版本”权限。
  • 删除版本不会清空图库当前投影，也不会删除业务库数据；它只删除平台库里的这一份版本记录。

5.3 发布的原子性与并发#

GraphStore.replaceGraph() 有硬性契约：失败时图数据必须保持替换前的状态，由 capabilities.atomicReplace 声明能力。

后端 原子替换实现
Apache Jena 单个 SPARQL Update 完成“清空 + 插入”；超过 5000 条三元组时先写影子命名图，再用一个请求 CLEAR + ADD + DROP 原子切换
内置类型图 PostgreSQL 单行 UPSERT 原子替换发布视图；Graphology/N3.js 视图按需重建

同一个本体存储的发布在两层串行：

  1. 进程内发布队列；
  2. PostgreSQL advisory lock。

因此多实例部署时也不会出现两个实例同时替换同一个本体存储。

发布过程会写三条审计：

审计动作 时机
VERSION_PUBLISH_STARTED 发布开始，含后端类型与 atomicReplace 能力
VERSION_PUBLISHED / VERSION_ACTIVATED 发布/激活成功
VERSION_PUBLISH_FAILED 发布失败，含 graphReplaced，用于判断图是否已被改动

5.4 稳定标识#

  • 图库的 elementId() 在重新导入后会变化，不能作为长期引用；
  • 快照为对象和关系分配稳定 UUID；
  • 发布时 UUID 只在事务内用于连边，完成后从节点属性中移除，不污染业务属性；
  • 对象身份在对象服务层优先使用“对象类型 + 业务主键”；
  • 导出到本体包时所有 id 会重新分配，不要用 id 做跨环境引用。

5.5 本体包：导出与导入#

版本快照是平台内部形态，id 都是本机 UUID。要在人和环境之间传播，使用本体包：一个单文件 .ontology.json。

5.5.2 三条不变量#

  1. definition 就是平台内部的 OntologyDefinition。 不另造一套形状，避免“两份定义各说各话”。
  2. 包里绝不写凭据。 数据资源只记连接坐标（类型 / 主机 / 端口 / 库 / 模式），导入端按坐标匹配本机已登记的资源。
  3. 导入一定停在草稿。 别人的文件不能绕过版本边界；校验和发布仍走平台流程。

5.5.3 导出#

入口：总览 → 本体卡片 → 导出，或“本体建模”页头。

  • 导出当前已发布版本的结构定义；
  • 输出单文件 .ontology.json；
  • 不包含实例数据，不包含业务库账号密码。

5.5.4 导入#

入口：总览 → 导入，支持平台本体包与 bkn 知识网络。

导入时平台会做三件事：

步骤 行为
换 id 包里的 UUID 全部重发新号，接口与实现、关系端点、动作作用域、规则条件一起改写
接回数据资源 按 kind + host + port + 库 + 模式 五项全等匹配；只差模式时放宽一次并提醒；找不到就留空并点名是哪个对象类型需要重新选表
建本体 + 写草稿 本体名可改；标识被占用就自动加序号；导入后对象数是 0，因为实例不在包里

导入不会静默丢绑定。接不上的来源会在弹窗里列出，用户到对应对象类型里重新选表即可。

5.5.5 bkn 知识网络导入#

导入入口同时识别 bkn-foundry 导出的知识网络（module_type: knowledge_network）。服务端先把它转成标准本体包，再走同一条导入路径。

转换能搬的都搬：

  • 对象类型、关系类型、概念域分组、指标；
  • 属性带 display_name（中文名）与 comment（说明）；
  • primary_keys 落到来源绑定的主键上；
  • 没有数据来源的对象类型，主键记在属性自己的「主键」标记上（勾多个就是复合主键），并给提醒。

装不下的会逐条列出，不会静默丢，例如：

  • 关系的连接规则 mapping_rules；
  • 平台不认识的属性类型；
  • bkn 只写 SCHEMA.TABLE、不带数据库连接的来源——导入后需要自己选一次数据资源。

5.5.6 命令行导入#

大文件（几十个对象类型、上千个属性）建议用命令行，避免浏览器上传超时或内存压力。

# 先干跑：只解析、不落库，看清文件里有什么、会丢什么
node scripts/import-ontology.mjs "你的文件.json" --dry-run --email admin@example.com --password '******'

# 正式导入：默认停在草稿
node scripts/import-ontology.mjs "你的文件.json" --storage-target "内置类型图" --name "客户账务网络 v6"

# 一步到位：导入并发布（会真正重建图数据）
node scripts/import-ontology.mjs "你的文件.json" --publish

常用参数：

参数 说明
--dry-run 只解析和规划，不落库
--email / --password 登录账号；也可用环境变量 ONTOLOGY_EMAIL / ONTOLOGY_PASSWORD
--token 直接给平台会话令牌，跳过登录
--storage-target 指定本体存储名；省略时若只剩一个未占用存储会自动使用
--name 导入后的本体显示名
--publish 导入后直接发布；默认不发布

导入响应带有 timings（解析 / 规划 / 绑定 / 建快照），慢的时候能一眼看出慢在哪。

三种输入都支持：bkn 知识网络、平台 ontology.bundle、技能工具导出的本体包。

5.6 版本与包的边界#

问题 答案
本体包能替代版本快照吗？ 不能。包只带结构；版本快照还包含实例、画布位置和内容哈希
导出的包能在另一台机器直接发布吗？ 可以导入并发布，但数据资源必须在本机重新绑定；实例数据不会带过去
历史版本能回滚实例吗？ 有实例快照的历史版本可以激活并整图替换；没有快照的旧归档版本不行
删除版本会删图库或业务数据吗？ 不会。只删除平台库中的版本定义、实例快照和概念索引；图库是投影，业务库数据也不受影响
删图库数据会删版本吗？ 不会。图库是投影，版本与快照在平台库
发布失败会留下半成品吗？ 后端声明 atomicReplace=true 时不会；不支持的旧后端会明确提示风险
两个实例同时发布同一本体存储会怎样？ 进程内队列 + PostgreSQL advisory lock 串行化，不会并发替换
导入时会保留原 id 吗？ 不会，全部重发新 id；跨环境引用一律用名字或重新查 id

5.7 操作手册摘要#

发布一个新版本#

  1. 打开本体建模，确认页面显示当前版本与草稿状态。
  2. 编辑模型；每次改动自动保存到草稿。
  3. 点“建模体检”，按 WARN / INFO 逐条处理。
  4. 点“校验”，处理所有违规。
  5. 点“发布”，等待图重建和索引同步完成。
  6. 到实例图谱、对象页、智能问答分别验证。
  7. 在“设置 → 审计记录”确认发布记录。

回滚到历史版本#

  1. 确认当前没有未发布草稿；有草稿先发布或删除。
  2. 打开版本记录，选择目标历史版本。
  3. 确认它有实例快照。
  4. 点“激活”，等待整图替换完成。
  5. 用对象页和问答验证；激活记录写审计。

删除草稿或历史版本#

只有拥有“删除版本”权限的账号能看到并执行“删除”按钮；内置角色默认只有管理员拥有。

  1. 打开本体建模页头右侧的“版本记录”。
  2. 找到要删除的草稿或历史归档。
  3. 点该行的“删除”并确认。
  4. 删除后版本列表立即刷新；草稿删除后可以重新创建草稿，历史归档删除后不能再激活。

当前生效版本不能删除。要替换当前版本，先发布新版本，或激活另一个有快照的历史版本。

导出与交付#

  1. 在本体卡片或建模页头点“导出”。
  2. 得到 .ontology.json。
  3. 在目标环境导入，停在草稿。
  4. 处理数据资源绑定提醒。
  5. 校验、发布、验证。

5.8 当前限制#

  • 一个本体存储同时只能有一个草稿。
  • 历史激活不是“合并”，而是用历史快照整图替换；不会保留当前实例的增量修改。
  • 本体包不携带实例数据，也不携带凭据；跨环境迁移实例需要另行物化或从业务库回源。
  • 旧归档版本如果没有实例快照，无法激活。
  • 当前生效版本不能删除；版本删除使用独立的 ontology.version.delete 权限，内置角色默认只给管理员。
  • 版本快照内容哈希用于完整性校验；如果快照被外部改写，读取或激活会失败。
  • 发布过程中的对象索引同步失败不会回滚已替换的图数据，而是把版本留在草稿并提示重新发布，以确保数据最终一致。

6.1 实例层的三个入口#

左侧“本体实例”分组有三个页面：

页面 用途 主要操作
实例图谱 看对象与关系构成的图 按类型筛选、搜索节点、展开邻居、拖动布局、只读查询

写入操作只作用于草稿快照，需要 instance.write；只读操作需要 instance.read。如果当前没有草稿，编辑动作会先提示或自动建草稿。

6.2 对象身份：对象类型 + 主键#

对象服务用一层统一口径识别对象：

对象身份 = (对象类型, 主键值)
对象引用 = 对象类型名/主键串

主键来自对象类型的主来源 sources[0].primaryKey。支持复合主键：

  • 主键值统一转成字符串参与比较和哈希；
  • 复合主键按 列=值&列=值 的形式表达；
  • 主键值缺失、超长或为非标量时，该对象不构成稳定身份；
  • 对象索引里的唯一键是对象键 (对象类型, 主键)，没有主键时退回 id:<objectId>，但这不是业务身份。

对象身份的好处是：

  • 对象从索引读还是从业务库回源读，身份一致；
  • “取进草稿”天然幂等，同一个对象取两次不会造出第二份；
  • 动作、问答、MCP 引用对象时都用同一套引用格式。

6.3 对象服务：索引优先，缺失回源#

对象服务（Object Service）是平台唯一的“按对象类型 + 主键取对象”入口：

界面 / 智能问答 / MCP
        │  (本体, 对象类型, 主键)
        ▼
   对象服务
        ├─ auto（默认）：先查索引，索引里没有就回源
        ├─ index：只读对象索引
        └─ source：只从业务库回源读取

三种来源模式：

模式 行为 适用
auto（默认） 先查索引；该对象类型在索引里没有数据时回源业务库 大多数场景
index 只读对象索引，索引没有就返回空 明确要物化数据、要全文/过滤
source 只从业务库按主键回源 数据必须实时、不容忍索引延迟

对象服务默认使用已发布版本的定义；对象页的草稿预览可以点名某个草稿版本。它不认识图库、索引表或业务表的实现细节，换中间件只替换来源实现。

6.4 对象索引#

对象索引是派生数据：任何时刻都可以从已发布快照重建，索引坏了不影响本体版本正确性。

当前实现落在 PostgreSQL ontology_platform.object_entries：

能力 说明
全文检索 tsvector，支持中文分词能力取决于 PostgreSQL 配置
模糊检索 pg_trgm；缺扩展时降级为全文或属性过滤
向量检索 pgvector + HNSW；当前还没有 embedding 提供方，向量通道暂不可用
属性过滤 EQ / NE / CONTAINS / GT / LT / IN / EXISTS
分页 检索上限 200 条，偏移最大 100000

GET /api/object-search?targetId= 会返回能力与统计：

  • available：索引是否可用；
  • fullText / trigram / vector：各通道能力；
  • embeddingDim：向量维度，未配置时为 null；
  • entries 与 byLabel：索引条目数和按对象类型的分布。

物化与增量同步#

操作 接口 说明
发布 发布流程内部调用 按发布快照整体同步索引；prune=true，以快照为权威
单条/批量增量同步 POST /api/objects/index 给主键只同步这几条；不删已有数据
取进草稿 POST /api/objects/materialize 把业务库对象取进草稿快照，供编辑或动作使用
重建索引 POST /api/object-search/reindex 从版本快照整体替换索引，安全、可重复执行
对象检索 POST /api/object-search 全文 + 模糊 + 属性过滤；可带向量
按主键取对象 GET /api/objects 走对象服务，可指定 origin=auto/index/source

增量同步只 upsert 不 prune；发布才是权威路径。索引坏了、换后端、扩展缺失，都可以重建，不需要改本体版本。

来源隔离：索引行带 origin —— SNAPSHOT（手工 / 动作 / 取进草稿）与 MATERIALIZED（从业务库整份物化）。 发布与「重建索引」只替换 SNAPSHOT，不会清掉物化数据；整份物化只动 MATERIALIZED。

默认读法（entityTypes[].indexPolicy，2026-10-12）：AUTO（默认，索引有就用、没有回源）/ INDEXED（只读索引， 没物化就明确提示、不静默回源）/ FEDERATED（不进索引，每次直接读业务库，能力受限并如实标注）。老快照没有这个字段，读出来是 AUTO。

物化按当前打开的版本（2026-10-12）：面板的可读性与取数都按「有草稿就是草稿」的那一版，汇总栏标出「物化版本 v2 草稿」； 不带版本号会退回已发布版本，于是出现"面板说能读、点下去说读不了"。断点续跑同时带 kind（对象类型 / 关系类型）。

整份物化是后台任务：一个任务 = 一个类型（对象类型或关系类型），服务端串行执行，默认不限制行数（读到源读完）； 入队立刻返回任务，进度可在对象页「索引与物化」里看（每页更新一次）。可取消（排队中立刻取消；运行中先标「取消中…」， 等当前这一页读完才转 CANCELLED）。失败 / 取消 / 中断只是任务状态展示，不需要清理：在该行直接点「重试物化」或「继续物化」，服务端会从已读断点接着跑 （断点连游标一起存，所以哪怕表有几千万行、中间被取消或服务重启过，也能接着翻页继续，不用从头再来一遍）。 任务状态与历史落在 ontology_platform.materialization_jobs：进程重启后遗留的 QUEUED/RUNNING 会被标成 INTERRUPTED（物化幂等，重新排队即可）。 半份必须报数：撞到单次上限（调用方显式传 maxRows）会停止、不 prune，并写进物化清单 materialization_manifests。

大表怎么物化（2026-10-14 起）：物化是"读一页、写一页"的，内存只跟页大小有关，不跟表的大小有关 —— 所以几千万行的表也能跑，不会把服务撑爆。面板上的「每页」就是每次从业务库读多少行：

  • 默认 5000 行（这也是上限：数据源连接器单次读取的硬上限，填更大也只按 5000 走）；
  • 页越大，往返次数越少、整体越快（实测 7034 行的表：500 行/页 15 页 16 秒；2000 行/页 4 页 8 秒；5000 行/页 2 页 7.6 秒）；
  • 页越大，单次查询在业务库那侧也越重 —— 业务库忙的时候把每页调小（面板上可选 100 / 500 / 2000 / 5000）。
  • 中途取消或失败不会丢数据：已经写进去的留着，没读到的部分等下次续跑 / 重跑补齐。 这时索引里是"本次新读的 + 上一次剩下的"混合状态，面板会如实说明。

主键重复折叠也要报数（2026-10-13）：整份物化读完之后，用 countTypeObjects(targetId, 对象类型, MATERIALIZED) 数一下索引里真正落下几个对象，scanned - 对象数 就是被主键折叠掉的行数，随清单写进 materialization_manifests.folded。 大于 0 时对象页「索引与物化」在该类型那一行挂「主键重复折叠 N 行」，面板底部再给一条红字说明 （哪个类型：源里 X 行 → Y 个对象 → 折叠 Z 行），并写明两条出路：改主键（或换成组合键）、或在取数口径里先去重。 只有「从头读完、没截断、没取消、没卡住」的那一次才算得准；syncObjectsToIndex 的「补一批」路径不算（记 0）。 计数走索引的一条 COUNT，不在内存里攒对象键的 Set（大表会把内存撑爆）。 当前口径是报数不拦：物化照常完成，把折叠摊开给用户看，由用户决定改主键还是改口径。

少读了几行也要说（2026-10-13）：主键在源数据里不唯一时，主键游标翻页会在页边界跳过同一主键的其它行 （k > 上一页最后一个 k 永远够不到重复值）。物化读完之后拿源侧报过的总数对账（total > scanned）， 对不上就报「源里共 N 行，这一趟只读到 M 行…」并给两条出路（改用取数口径 / 换真正唯一的主键）。 实测：GISTOOLS.TB_MK_GRP_LINE_LIST_DAY 源里 1690 行、物理物化只读到 1688 行 —— 差的 2 行就是这么丢的。

两条配套口径：

  • 整份物化自己在翻页，不报"页被截断"：ObjectQuery.paging = true 时不报「命中行数超过 N 行」—— 那是下一页会接着读的常态，报出来只会刷一排假告警（实测一次物化刷 3 条）。
  • 后台任务的告警要写进 job.message：materialize-jobs 以前只存取消 / 截断 / 失败三种 message， 物化返回的 warnings（折叠多少行、少读几行）整条丢掉。现在完成时把 warnings 并进 message， 对象页「索引与物化」那一行才看得到。

对象类型的数据来源有两种形态（2026-10-13）：

形态 字段 读什么
PHYSICAL（默认，老快照都是这一档） schema + view 库里现成的表 / 视图
DERIVED sql（一段只读 SELECT） 取数口径的结果 —— 去重 / 聚合 / 拼装写在 SQL 里
  • 口径在执行时被包成子查询（SELECT … FROM (<口径>) "t" WHERE …），过滤 / 排序 / 主键游标翻页全都照旧； Oracle 没有 OFFSET，用 ROWNUM <= n + skip 多读几行、由内存丢掉。
  • 只读是硬闸门：assertReadOnlySql 守在两处 —— 发布前（validateEntitySources，写语句挡发布）与执行前（连接器里再验一次）。
  • 口径必须输出主键列；主键没配只提示、不拦（建模中途允许先搭结构）。
  • 补充来源暂不支持口径，只支持表 / 视图；校验里明确报出来，不静默当表用。
  • 语句生成走 derivedRowsStatement / derivedCountStatement（src/lib/datasource/sql-guard.ts，纯函数、有单测）： 值一律绑定参数、列名一律走驱动转义 —— 口径 SQL 只允许出现在连接器适配器里。
  • 界面上在哪配：「编辑对象类型 → 数据来源」主来源顶部有 表 / 视图 ↔ 取数口径 切换（view-switcher）。 切到口径档时给一个 SQL 框 + 主键列（逗号分隔）+ 显示名；SQL 的只读校验用与后端同一个 assertReadOnlySql， 边写边给结论（通过是绿字，写语句当场报「取数口径只能执行只读查询：…」）。切到口径档会清空表名，避免留下半套绑定。
  • 不会写 SQL 就用「按规则生成」（src/lib/ontology/dedupe-sql.ts，纯函数 + 单测）：口径档里选 「分组键（一个对象一行）+ 取值依据（哪一列）+ 取最新 / 最早」，一次生成确定的口径，并把分组键顺手写回对象主键。
    • 候选列只认日期 / 时间：类型是 DATE / TIME 的，或名字以 DATE / TIME / DAY / TIMESTAMP / _TS / _DT 结尾的 （很多表的日期是 VARCHAR2 存的，只看类型会漏）。光 TS 结尾不算 —— STATS 那种状态列会被误判（实测踩过）。
    • 参考表里一个日期列都没有：不生成 SQL，直接给两条出路 —— 把主键换成真正唯一的键（那就根本不需要去重）， 或按业务条件筛一行（「状态 = 有效」这种，规则由业务定）。
    • DERIVED 来源的 view 是「参考表」：它不参与取数（取数走 sql，口径优先），但要留着 —— 界面按它拿真实列清单来生成口径。没留参考表时只给指引，不猜 FROM 子句。
  • 报警之后必须给路（2026-10-13）：「索引与物化」面板里 folded > 0 的那一行下面挂一个「怎么去重？」出口， 展开给三样东西 —— ① 换主键（并显示当前的去重键是哪几列）；② 这张表能当「取哪一行」依据的候选列 （按参考表的真实列清单挑，与对象类型编辑器同一个 orderCandidateColumns）；③ 按该类型主键生成好的口径 SQL
    • 一键复制（同一个 dedupeSql）。一个候选都没有时如实说「这张表没有日期 / 时间列」，把人引回 ①。 面板只做只读诊断：不写任何定义，改动仍回编辑器里做。
  • 口径的生成参数（sources[].rule）是可选元数据（2026-10-13）：按规则生成时把 { keyColumns, orderColumn, direction } 一起存下来。作用有三： ① 界面回显人话（「按 CUST_ID 取最新一行（依据 STATIS_DATE）」），不用让人读 SQL 才知道口径是什么； ② 按规则可以重新生成（改一列不用从零选）； ③ 平台能判「存下来的 SQL 和这条规则还是不是一回事」—— 对不上时在编辑器里给红字警告（手改过）。 手写 SQL 就是 rule: null（逃生舱一直留着）。发布前只做结构校验：有规则但缺分组键 / 缺取值依据 → 挡发布； 「SQL 与规则是否一致」要按数据源方言重新生成才知道，所以判断放在编辑器（那里知道 kind），不放进定义层校验。

关系类型的数据来源（2026-10-12）：形态由两端键映射决定 —— 任一端填了「连接列」就是连接表式（多对多）， 必须给出连接表与数据资源；两端都只填「属性」就是外键式（多对一 / 一对一），可以整块不配：外键在哪一端按 键映射推断（一侧填该端主键、另一侧填非主键属性），表和数据资源取外键所在端对象类型的主来源。 两端键映射都空 = 只在类型层声明，不报错也不出实例。

读不出的关系类型在这张面板上要看得见：关系类型那段只列读得出的（判据与后端同源 —— 都走 planLinkSource， 不另写一套），读不出的（键映射空、或连接表式没选连接表）不进表格，收成表尾一条黄色提示：还有几条读不出、 本份本体共几条、为什么、去哪儿补（到「本体建模」点开关系类型补两端键映射；悬停能看到前几条的具体原因）。 这样"这一段是空的"不会被误读成"这份本体没有关系类型"。 物化的任务状态并进类型表的那一行（进行中带进度、失败带原因），不单开任务列表；一个类型只保留最近一条任务记录， 已完成的靠「索引（物化）」那一列表达。表上方的筛选分两行：第一行可读性 + 完成度（全部 / 未完成 / 已完成，各带数量），第二行是每页与排队动作；默认「全部」。 每个对象类型行同时显示当前主键（未配主键会标黄）；对象类型名称本身可点，直接打开该类型的配置，不用再回到建模页逐项查找。

关系（边）的物化（2026-10-12）：关系类型也能整份物化，任务形态与对象侧完全对等（进度 / 取消 / 断点续跑 / 清单）。 一条边存一行：(关系类型, 起点对象键, 终点对象键) 是唯一键，双向共用一个方向不限（读的时候两个方向都查）， prune 只在这个关系类型里生效。取数走关系类型绑定的 linkSource（连接表 + 两侧键映射），整份读连接表。 两端对象类型没物化也能先物化边，但图上要两端都在这一屏里才画得出边，不在就如实报数。

源侧分页（2026-10-12；2026-10-14 补漏读兜底）：整份物化按 pageSize 逐页回源。有主键且主键唯一时用主键游标翻页 —— 按主键升序排， 下一页只取"排序键 > 上一页最后一个键"的行（键集翻页），每页等价于点查、offset 恒为 0，不受 Oracle 深翻页上限影响。 第一页也要带排序列（只是不带游标值）；Oracle 上有序取行要先排序再限量（外包一层子查询用 ROWNUM 截断）。 主键没配全或断点续跑时退回 offset 翻页。回源默认顺带 COUNT(*) 报总数，物化只在第一页要它（ObjectQuery.count = false 关掉），避免每页一次 COUNT。

主键在源数据里不唯一时，严格的主键游标会在页边界跳过重复主键的后续行。整份物化现在会在游标读完后拿源侧总数对账： 一旦发现 total > scanned，自动从 0 改用 offset 重读；如果 offset 也不能读全（例如 Oracle 超过 5000 行的深翻页上限）， 任务直接失败，不会把半份写成"物化完成"。相邻两页读到的对象若完全相同（分页没前进），也会立即停止并说明，绝不空转。

「索引与物化」面板那一行会同时显示：当前对象数（实时从对象索引统计，不拿物化清单的写入条数冒充）、 最近一次物化的源表行数、折叠行数和是否需要重试的扫描状态。物化清单里的 rows 只表示这次提交/写索引的条目数； 历史清单不承担“当前对象数”这个语义。

当前限制#

  • 没有 embedding 提供方；向量列和索引可以建，但生成向量的模型服务尚未接入。
  • 索引是最终一致的派生副本；业务库刚更新的数据，索引要等同步或发布才出现。
  • 对象索引落在 ClickHouse（列存检索副本）；数据量上来之后，如果要换 OpenSearch/Solr，只需实现对象索引接口。
  • Oracle 按 offset 浏览有深翻页上限（ORACLE_MAX_OFFSET = 5000）；超过上限后普通 offset 查询会明确报错， 不再静默重复同一段数据。主键唯一时整份物化走游标，不受这个上限影响；主键不唯一且 offset 兜底也读不全时，物化任务失败并给出改主键 / 改取数口径的出路。
  • 实例图谱已发布视图走对象服务（对象索引 + 边索引）；草稿视图读这一版草稿快照；索引里一条数据都没有时才退回图库并如实说明。 边要单独物化（见「物化与增量同步」），而且两端对象类型也要物化，点上才画得出边 —— 另一端不在这一屏时界面会报数。
  • 对象页「全部标签」也走对象服务：跨对象类型读索引（回源必须知道是哪张表，全部标签没有单一来源可回）； 选了具体对象类型才能在「已物化 / 业务库」之间切。
  • pgvector 缺失时向量检索会明确报错或按能力返回不可用，不会静默降级成假结果。

  4. 有权限限制时，界面会提示先补 ontology.write / instance.write，而不是给一个空白页。

第一次定义业务操作，请先看常见任务教程中的“定义一个业务动作”和“给动作加规则”。本章是完整参考。

7.1 为什么要有动作#

平台把“写入业务本体”的权限收口到动作这一种入口：

  • 智能问答与 MCP 全部只读；
  • REST 的对象/关系接口只允许写草稿快照；
  • 业务写入不在定义层随意发生，而是通过预定义的动作模板；
  • 动作的参数、编辑步骤和规则都在本体定义里，模型或调用方不能自己编造写操作。

动作不是“用自然语言写库”，而是“平台里不存在的动作，就没有对应的写入口”。存在的动作，写法是固定模板。

7.2 动作的概念模型#

一次动作 = 把声明的操作模板套到当前图上：

选择动作
  → 选择主对象（动作作用的那个对象）
  → 填入参数
  → 在内存中计算执行后的图
  → 用挂在动作上的规则检查结果
  → 全部通过才落盘到草稿快照
概念 说明
动作（Action） 定义在某个对象类型上的写操作
主对象（Subject） 执行时选中的对象，动作作用在它身上
参数（Param） 入参，可以是值，也可以是另一个对象的引用
编辑步骤（Edit） 按顺序执行的写操作模板
规则（Rule） 挂在动作上的 BLOCK / WARN / HIDE 条件
决策记录（Decision） 每次干跑、执行、被拦截留一条审计

动作类型是本体的一等公民，不是某个对象类型的私有字段；一个动作可以跨多个对象类型写入。

7.3 动作定义#

入口：本体建模 → 动作，或在对象类型详情里跳到相关动作。

动作编辑页有四个阶段：

阶段 内容
定义 动作名称、说明、作用对象类型、参数、编辑步骤
规则 挂在动作上的拦截、提示、隐藏条件
运行 选择主对象、填参数、干跑或正式执行
决策 查看最近的动作执行 / 干跑 / 被拦截记录

7.3.1 基本字段#

字段 说明
名称 动作显示名
代码 稳定标识，供接口和审计使用
说明 这个动作解决什么业务操作
作用对象类型 动作定义在哪个对象类型上；执行时必须选一个属于它的对象
参数 入参定义，见下节
编辑步骤 写操作模板，按顺序执行

7.3.2 参数#

参数有两种：

类型 说明
VALUE 普通值参数，例如金额、状态、日期
ENTITY_REF 对象引用参数，必须指向一个对象类型

参数代码（code）在同一个动作内必须唯一。参数失踪、类型不匹配、引用不存在的对象时，动作执行前会被拦下。

7.3.3 编辑步骤#

平台支持三种编辑操作：

操作 说明 典型用途
CREATE_ENTITY 新建一个对象；必须给别名，后续步骤才能引用 创建工单、创建任务
SET_PROPERTY 修改某个对象的一个或多个属性 更新状态、更新时间
CREATE_RELATIONSHIP 在起点和终点之间新建一条关系 把任务挂到客户上

对象引用可以来自：

引用来源 说明
SUBJECT 执行时选中的主对象
PARAM 入参中的对象引用
EDIT 前一步创建出来的对象，通过别名引用

赋值可以来自常量、参数或前一步创建的对象。编辑步骤按顺序执行，任何一步不符合契约或必填，整次动作都不写库。

7.3.4 动作与对象类型 / 关系类型的关联#

动作与类型的关联不是单独维护的关联表，而是从参数和编辑步骤推导出来的：

  • 入参引用了哪个对象类型 → 标记为“入参”；
  • CREATE_ENTITY 新建哪个对象类型 → 标记为“新建”；
  • SET_PROPERTY 修改哪个对象类型 → 标记为“修改”；
  • CREATE_RELATIONSHIP 创建哪条关系类型 → 标记为这条关系的两端。

这样动作改了，关联就跟着变，不会因为手工维护关联表而漂移。

7.4 规则#

规则挂在动作上，有三种处置：

处置 效果 适用
BLOCK 命中后拒绝执行，把原因与证据返回给用户 硬性业务门槛
WARN 命中后照常执行，只提示原因 软性提醒、异常但允许
HIDE 命中后这个动作不出现在符合条件的主对象上 适用性判断，例如状态不允许时根本不展示

7.4.1 规则字段#

字段 说明
名称 规则显示名
说明 / 提示消息 命中后展示给用户的文字
处置 BLOCK / WARN / HIDE
绑定动作 规则作用于哪个动作；HIDE 必须绑定具体动作
优先级 多条规则命中时的排序依据
启用状态 可临时停用而不删除
条件 一组条件表达式，支持逻辑组合

7.4.2 条件主体#

条件可以看：

  • 主对象（SUBJECT）：动作还没执行时就能看到的数据；
  • 入参对象（PARAM）：调用方传入的对象；
  • 前一步创建或修改的对象（EDIT）：执行过程中产生的对象；
  • 对象属性；
  • 关系类型与相关对象。

7.4.3 HIDE 的特殊限制#

HIDE 是“动作在这个对象上出不出现”的问题，必须在动作执行前算得出来，所以：

  • HIDE 必须绑定到一个具体动作；
  • HIDE 的条件只能看主对象；
  • HIDE 条件不能引用入参或执行中新建出来的对象；
  • 发布校验会检查这些限制。

这是有意为之：动作还没执行时，入参和新建对象都还不存在，不能拿它们判断动作该不该显示。

7.5 干跑与正式执行#

干跑（Dry Run）#

  • 完整计算动作结果、执行规则检查；
  • 返回会创建的实体、会写入的步骤、命中的拦截/警告/隐藏；
  • 不落盘，不改变草稿快照；
  • 适合上线前验证一个动作在当前对象上是否真的能执行。

正式执行#

  • 先检查规则；
  • 全部通过后，把执行结果写入草稿快照；
  • 被 BLOCK 规则命中时，图保持原样，只留决策记录；
  • 执行结果显示创建的实体、主对象、步骤和警告。

对象只存在于数据源时#

动作作用在草稿快照上；如果主对象或入参对象只存在于业务库，平台会先按主键把它取进草稿，再执行动作。这一步是幂等的，不会重复创建对象。

写回业务库（可选，默认关闭）#

动作默认只写平台草稿快照（本体里的副本）。要让它改业务库那一行，在「运行」阶段把「写回业务库」勾上再执行。

  • 干跑永远不写库：勾上写回后干跑会把"这次会写哪张表、按什么键、改哪几列"作为计划列出来，供你点执行之前核对。
  • 写哪张表：对象类型的主来源（表 / 视图）。主来源是取数口径（DERIVED）时写不回去 —— 口径是算出来的结果，没有可以改的那一行；界面会直接说清并给出路。
  • 按什么键：主来源的主键列（复合主键按多列）。主键列必须都映射到属性、且这个对象上都有值，少一列就拒绝。
  • 只改已有行：动作新建的对象没有源行，不参与写回（当前不支持 INSERT）。
  • 主键不能改：主键是对象的身份，用动作改它等于换一个对象，会被拒绝。
  • 键必须唯一命中一行：连接器写之前先按键回读，0 行（行不在了）或 2 行以上（键不唯一）都拒绝，绝不盲写。
  • 要么全写，要么都不写：一次动作里只要有一处写不回去，整批不执行，业务库与草稿都保持原样；界面上逐条列出"哪一处、为什么、去哪儿改"。
  • 写完要确认：语句发出后会回读那几列比对，确认不到就回滚（Oracle 等驱动不给影响行数，一律靠回读算）。
  • 先写库、后落草稿：权威在业务库，草稿只是副本。极端情况下（业务库已改、草稿没落上）接口会明说这一点，重新执行一次即可对齐。

看得到的地方：运行阶段的写回报告（计划 / 结果 / 拒绝理由）、决策记录里「已写库 N 处」的状态牌、审计详情里的写回清单与实际语句。

7.6 决策记录与审计#

每次动作执行都会落一条审计：

审计动作 时机
ACTION_DRY_RUN 干跑
ACTION_EXECUTED 正式执行成功
ACTION_BLOCKED 被 BLOCK 规则拦截

决策记录里包含：

  • 动作 id / 代码 / 名称；
  • 主对象；
  • 干跑与否；
  • 判定 PASSED / BLOCKED；
  • 拦截原因、警告、隐藏命中；
  • 执行步骤；
  • 新建的实体；
  • 是否为主对象补了物化；
  • 写回业务库的清单：这次要写 / 已写哪张表的哪几列、旧值 → 新值、实际语句；写不回去的逐条原因。

查看入口：

  • 动作页的“决策”阶段显示当前草稿最近的决策；
  • 设置 → 审计记录，筛选“动作记录”看完整流水。

7.8 一个完整例子#

目标：把一条专线标记为“已开通”。

  1. 定义对象类型：专线，主键 线路编号，属性含 状态。
  2. 定义动作：开通专线，作用对象类型 = 专线，参数无。
  3. 定义编辑步骤：SET_PROPERTY，主体 = 主对象，属性 状态 = 已开通。
  4. 定义规则：
    • BLOCK：主对象 状态 已经是 已开通 时拒绝，提示“这条专线已经开通”；
    • WARN：主对象 欠费金额 大于 0 时提示“存在欠费，仍允许开通”；
    • HIDE：主对象 是否注销 = 真时隐藏动作。
  5. 干跑：选一条未开通专线，确认步骤和规则命中。
  6. 正式执行：写入草稿快照；要让业务库也变，勾上「写回业务库」—— 它会按主键改源表那一行，并把「旧值 → 新值」记进决策记录与审计。
  7. 决策记录：在动作页和审计里看到这一条 ACTION_EXECUTED。
  8. 发布：把草稿发布成新版本，动作结果进入新的已发布视图。

7.9 当前限制#

  • 写回只支持 UPDATE 已有行：不支持 INSERT / DELETE，也不支持跨表事务；要删要建得走数据源自己的作业。
  • 写回只认主来源的表 / 视图：取数口径来源、补充来源上的属性都不写回。
  • 写回一次只改一条键命中的那一行：批量改一批对象要逐个执行动作（动作本来就是"一次业务动作"的模板）。
  • 不被写回的部分照旧只进草稿快照（动作仍然可以只做本体层的事）。
  • 动作只能在草稿版本上执行；没有草稿时先创建草稿。
  • 没有触发器、定时任务、外部 API 调用等“副作用步骤”；编辑步骤限定在三类图写操作。
  • 规则条件只覆盖定义层可见的主对象、参数、编辑对象、属性和关系，不执行任意函数或脚本。
  • 动作执行不会绕过必填/主键/端点契约；任何一步失败，整次动作不落盘。

第一次接入业务数据库，请先跟着从零跑通第一个本体。本章详细说明连接、绑定、列画像和读取保护。

8.1 数据资源和本体存储不是一回事#

这是平台里最容易混淆的一组概念：

概念 回答的问题 入口 存什么
数据资源 对象的业务数据从哪张表来？ 平台 → 数据资源 外部关系库的连接与结构缓存
本体存储 / 图引擎连接 发布后的本体落在哪个图库？ 设置 → 图引擎配置 内置图或 Jena/Fuseki 连接

简单说：

  • 数据资源是业务系统的事实来源，平台只读访问；
  • 本体存储是本体发布后的投影，平台可重建；
  • 两者可以分别配置，但对象类型只有在绑定数据资源之后才能回源取数、物化索引和做列画像。

8.2 支持的数据来源#

当前支持三种关系库：

类型 连接形态 容器 默认端口
PostgreSQL 主机 + 端口 + 数据库 + 模式 模式（schema），可留空 5432
MySQL 主机 + 端口 + 数据库 库名即容器 3306
Oracle 主机 + 端口 + 服务名 + 模式 模式 / 用户，可留空 1521

规划中的非关系来源包括 Elasticsearch、REST 接口、文件集合；它们当前不可用，不要在实施计划里当作已交付能力。

Oracle 兼容性提示：

  • Oracle 11g 及更早的服务端需要 Thick 模式；
  • Docker 镜像已内置 Linux Instant Client，并把 ORACLE_CLIENT_LIB_DIR 指向 /opt/oracle/instantclient；
  • 源码运行时需要自行提供 Instant Client 目录；
  • 结构清单走数据字典（all_tables、all_tab_columns 等），不依赖 ORM 的 getTables()。

8.3 登记数据资源#

入口：平台 → 数据资源。

操作步骤#

  1. 点“新建数据资源”，选择类型（PostgreSQL / MySQL / Oracle）。
  2. 填写连接字段：主机、端口、数据库 / 服务名、模式、用户名、密码。
  3. 点“试连”。试连使用表单里的参数，不落库；确认能连再保存。
  4. 保存后，在资源卡片上可以：
    • 测试已保存连接；
    • 浏览表与视图清单；
    • 查看字段结构和若干行数据预览；
    • 刷新结构缓存；
    • 编辑连接、启用/停用、删除。
  5. 需要被对象类型绑定时，到本体建模的对象类型编辑里选择资源、表/视图和列映射。

凭据安全#

  • 数据资源密码使用 TARGET_ENCRYPTION_KEY 加密后保存；
  • API 返回给前端的资源对象绝不包含密文或明文密码；
  • 修改连接信息时，密码留空表示不修改；
  • 换掉 TARGET_ENCRYPTION_KEY 会导致已有密文解不开，必须重新登记连接。

8.4 表 / 视图浏览与结构缓存#

结构清单#

GET /api/data-sources/:sourceId/views：

  • schema=* 表示看全库所有模式；
  • search= 按表名过滤；
  • limit= 返回条数上限（缓存里最多 5000 条）；
  • refresh=1 强制回源库重读，否则默认读平台库里的缓存。

返回里带 fetched_at 和 from_cache，界面可以明确告诉你这份结构是什么时候读回来的。

单表结构与预览#

GET /api/data-sources/:sourceId/views/:viewName：

  • 返回字段名、类型、是否可空、主键、唯一、注释、序号；
  • 返回若干行数据预览（只读）；
  • 同样支持 refresh=1；预览行数会进缓存键，20 行和 100 行是两份不同快照。

两层缓存#

层 行为 失效时机
服务端 结构清单按“连接 + 容器”缓存 60 秒，命中时不建连接、不查库 超过 60 秒，或请求带 refresh=1
前端 资源清单、结构清单、字段与预览按 key 存在会话内存 改连接信息（整条丢弃）、超出缓存条数上限、整页刷新

单表读取走精确路径：Oracle 按 owner + 表名 定位，再取列与预览，不为了看一张表扫整库。

8.5 把对象类型绑定到数据资源#

绑定写在对象类型上，而不是逐个对象上。参照 Palantir 的模型：

绑定项 含义
数据资源 + 表 / 视图 这份来源读哪张表
主键字段（可复合） 主来源里，这几列构成一个对象的身份
显示名字段 对象在列表与图谱上的标题
属性映射 类的属性取自哪一份来源的哪个列

单来源绑定#

  1. 打开对象类型编辑。
  2. 选择数据资源。
  3. 选择 schema / 表或视图。
  4. 从表字段中选择主键列；可多列构成复合主键。
  5. 选择展示属性对应的列。
  6. 为每个属性选择来源列；不映射的属性表示暂时不取数。
  7. 保存草稿。

多来源绑定（column-wise MDO）#

一个对象类型可以挂多份来源：

  • sources[0] 是主来源：决定对象身份和标题；
  • 后续来源是补充来源：主键列按顺序与主来源的主键列一一对齐，作为连接条件，用来补齐属性；
  • 属性通过 sourceId 指回来源，通过 sourceField 指向具体列；
  • 补充来源连接键的列数必须和主来源主键列数一致，否则拦发布。

校验口径#

情况 处理
补充来源选了表却没有连接键、连接键列数和主键对不上、属性指向一份已不在对象类型上的来源 拦发布，配置自相矛盾
主来源未选表 / 未指定主键、补充来源未选表、同一张表挂两次 提醒，不拦发布；允许先搭结构

导入后的补绑定#

从 bkn 或外部本体包导入时，来源可能只有 SCHEMA.TABLE，没有数据资源 id。导入后：

  • 平台会按表名在本机资源里尽量自动匹配；
  • 匹配不到的进入“待补绑定”清单；
  • 用户在弹窗里逐个选资源，保存后写入草稿，不重新导入。

相关接口：GET/POST /api/ontologies/:ontologyId/bind-sources。

8.6 列画像#

列画像解决的问题是：模型回答“状态正常的互联网专线”这类问题时，必须先知道某个列里到底有哪些取值、对应哪个码值。没有列画像时，模型只能一轮轮手写 GROUP BY 去探。

列画像不是精确统计，而是低成本采样。

采样规则#

规则 数值 / 行为
采样范围 只对被对象类型绑定的表做；未绑定表不采
采样行数 前 1000 行（Oracle 用 ROWNUM，PG/MySQL 用 LIMIT）
采样列数 单表最多 40 列，避免 SELECT 列表过长
低基数列 采样中取值种数 ≤ 50，直接给取值清单
高基数列 取值种数 > 50，按高基数列处理，不存取值
空值比例 记录采样中的空值比例
日期覆盖 对 DATE / DATETIME 列记录采样覆盖的日期范围与每日行数
缓存 写入 column_profiles 表，按天复用；默认 24 小时内直接读缓存

成本红线#

  • 不做全表 COUNT(DISTINCT)，因为 Oracle 大表上非常贵；
  • 只采样、不精确统计；返回里必须如实写 cached、sample_size 和采样说明；
  • 只有 get_table_ddl 带 refresh: true 或缓存过期时才回源库重采；
  • 采样结果的 distinct 是采样里的取值种数，不是全表 distinct，不能当精确统计使用。

模型怎么用列画像#

  • search_schema 的取值命中会返回列画像里的取值，并给出落点 bound_table / source_column / data_source；
  • get_table_ddl 会把列画像内联进表结构，模型拿到 DDL 就能看到码值与空值情况；
  • 模型按“表只能通过对象类型到达”的原则使用数据，不直接枚举未绑定的表。

8.7 只读 SQL 护栏#

平台不把业务库连接直接暴露给模型或前端；run_sql 与对象服务走同一套只读护栏。

词法闸门#

  • 语句必须以 SELECT / WITH / SHOW / DESC / DESCRIBE / EXPLAIN / VALUES / TABLE 开头；
  • 语句里不能出现写操作关键字：INSERT、MERGE、UPSERT、TRUNCATE、DROP、ALTER、CREATE、RENAME、GRANT、REVOKE、CALL、EXEC、COMMIT、ROLLBACK、LOCK、INTO、OUTFILE、COPY 等；
  • 一次只允许一条语句，多语句用分号分隔会被拒绝；
  • 注释和字符串字面量会在检查前剥离，防止利用注释绕过。

执行层保护#

  • PostgreSQL / MySQL / Oracle 各自开启只读事务；
  • 驱动起不了只读事务时，返回 read_only_transaction=false 与警告，如实暴露风险；
  • PostgreSQL 支持事务内 statement_timeout，MySQL 尝试 MAX_EXECUTION_TIME，Oracle 这一层没有等价开关；
  • 行数上限全链路统一：默认 100 行，最大 5000 行，超过必须标 truncated=true，不静默截断。

8.8 常见操作#

新增一个业务库#

  1. 平台 → 数据资源 → 新建。
  2. 选择类型，填连接参数，先试连。
  3. 保存后点“刷新结构”，确认能看到表和视图。
  4. 打开某张表，确认字段和预览正常。
  5. 到对象类型编辑里绑定这张表。

对象页提示“还差绑定的来源”#

说明对象类型有来源记录，但 dataSourceId 为空或指向已不存在的资源。处理：

  1. 打开对象类型编辑；
  2. 重新选择数据资源；
  3. 确认表 / 视图、主键、展示属性、属性映射；
  4. 保存草稿并发布。

更新表结构缓存#

  • 服务端缓存：请求带 refresh=1，或等 60 秒；
  • 前端缓存：在界面点“刷新结构”，或改一次连接信息让整条缓存失效；
  • 列画像：只有 get_table_ddl 带 refresh: true 或超过 24 小时才会重采。

删除数据资源#

删除前先确认：

  • 没有对象类型绑定它；
  • 没有关系类型的数据来源指向它；
  • 删除后相关对象类型会变成“绑定缺失”，需要重新选择来源。

8.9 当前限制#

  • 只支持 PostgreSQL / MySQL / Oracle 三种关系库；Elasticsearch、REST、文件仍在规划。
  • 平台只读访问业务库；动作执行结果不会回写业务库。
  • 列画像是采样，不是精确统计；低基数值清单只适合做码值提示，不适合做严谨报表。
  • 结构缓存有 60 秒服务端有效期；刚改完表结构时点一次“刷新结构”再操作。
  • 未绑定对象类型的表不参与列画像，也不能通过模型工具直接枚举。
  • 数据资源密码与 MCP 令牌依赖 TARGET_ENCRYPTION_KEY；换密钥必须重新登记。

第一次提问请先看常见任务教程中的“用智能问答问业务问题”。本章详细解释后台运行、工具、证据和边界。

9.1 智能问答是什么#

智能问答是平台内让模型基于已发布本体回答业务问题的能力。它不是一个直接写 SQL 的聊天框，而是“模型选只读工具 → 工具读本体与数据 → 结果回灌 → 模型组织答案”的服务端工具循环。

核心特征：

  • 只读：查询定义、表结构、业务数据和对象实例，不做写操作；
  • 只认已发布版本：工具侧读定义时只读 status = PUBLISHED；
  • 服务端运行：一轮问答由服务端跑，不挂在某条浏览器连接上；
  • 工具可关：管理员可以按全局或按本体关闭某些工具；
  • 运行有记录：问答、工具调用和证据进入历史与审计。

9.2 使用前提#

前提 说明
已配置 LLM LLM_BASE_URL、LLM_API_KEY、LLM_MODEL 三项齐全；否则页面明确提示模型未配置
已有发布版本 工具只认已发布本体；没有发布版本时先发布一次
有权限 进入页面与调用工具需要 reasoning.use
数据资源可读 要查业务数据时，对象类型必须绑定可连接的数据资源
工具已开启 某些工具出厂默认关闭，需要到 MCP 调试页按全局或按本体打开

检查模型是否配置：GET /api/reasoning/status 返回 configured、model 和 endpoint。

9.3 界面使用#

入口：能力验证 → 智能问答。

区域 / 操作 说明
提问框 输入自然语言问题；支持多行
图片按钮 / 拖拽 附着图片一起提问；浏览器侧先压缩，历史里记录张数与尺寸

  • 只有点“停止”才会真正取消；
  • 正在跑的轮次会出现在对话历史里；完成后自动落进历史；
  • 如果一轮已经落库，画面按“发起时归属的会话 + 落库后归属的会话”两个键认，不会因为落库而跳走或消失。

时间与 token 展示#

  • 耗时用浏览器时钟算，从“我按下发送”到“看到结论”；不用服务端时间显示；
  • 时间单位随量级变：812ms、4.9s、1分52秒、1小时05分、2天03小时；
  • token 分两个数：
    • 上下文 5.0k · 输出 239 tokens：最后一步这次调用的用量，表示模型当时看到的上下文与写出的内容；
    • 累计 1.1M：所有模型调用相加，工具循环每步都会重发上下文，这是计费口径。
  • 旧运行记录没有“最后一步”字段时，只显示累计。

9.4 后台运行机制#

平台把“起一轮”和“看这条流”拆开：

POST /api/reasoning/runs
  → 服务端立刻返回 runId，后台开始跑
  → 浏览器用 GET /api/reasoning/runs/:runId/events?after=N 接上
  → 断开连接只是不看了，运行照常推进
  → POST /api/reasoning/runs/:runId/cancel 才是真正停止

相关接口：

方法 路径 用途
POST /api/reasoning/runs 起一轮后台问答，返回 runId
GET /api/reasoning/runs?targetId= 当前本体上还在跑或刚跑完未落库的运行
GET /api/reasoning/runs/:runId/events?after=N 接上这一轮（SSE，按游标补看 + 增量）
POST /api/reasoning/runs/:runId/cancel 停止这一轮
POST /api/reasoning/stream 起一轮并就地看完（SSE，给脚本用）
POST /api/reasoning/run 非流式运行，给脚本与调试用

SSE 事件#

每一帧的形状是：

data: {"i": 12, "e": { ...event... }}

事件类型：

事件 含义
thinking 思考文本增量
answer 正文文本增量
answerReset 这段文本其实是“要调工具”的过渡语，界面把它清出正文
step 一次工具调用与结果
context 多轮上下文准备状态：start / compressing / ready
done 运行完成，带完整 ReasoningRun
saved 落库完成，带对话 id；失败时带 warning
error 运行失败

after 游标包含端点：游标那一条会重发一次，因为它可能刚被合并进更多文本。服务端先订阅再补看，避免正好在两步之间结束的运行漏掉 done / saved。

边界#

  • 运行登记在内存里；进程重启或容器重建会丢掉正在跑的运行，已经落库的历史不受影响；
  • 服务端登记处保留已结束记录约 10 分钟，供刚跑完再接回；
  • 取消只对正在跑的运行有效；
  • 别人的运行一律按不存在处理；接口会校验运行归属。

工具 说明

9.5.5 工具输出约定#

工具结果是喂给模型的，token 花在这里会影响每一次推理，因此有明确约定：

  • 紧凑 JSON，不缩进；
  • 同一信息不重复出现；
  • 列表按固定列序用位置数组表示，列序写进工具 description 并有单测；
  • 表结构把注释内联进列定义；
  • 真超上限时写明“原长多少、截到哪里”，不静默截断；
  • 列清单（映射列、字段清单、对话历史、列画像日期覆盖）默认给全；
  • 检索类结果默认前 50 条、最多 1000 条，并返回 total_matched / omitted；
  • 工具会返回耗时，便于判断哪次查询贵。

9.5.6 关掉一个工具意味着什么#

管理员在「MCP 调试」里关掉某个工具（按全局或按本体）之后，平台内智能问答与外部 MCP 都不会再看到它。 要同时做到三件事，缺一件都算没关干净：

  1. 不进工具清单：发给模型的工具定义里没有它，调了会直接报「没有这个工具」；
  2. 不进系统提示词：提示词里「本轮可用工具」一节按这一轮真正开着的工具生成，关掉的工具名不会出现；
  3. 不出现在别的工具的返回正文里：不会再有「要真实数据就调 xxx」这种指路话，把模型引向一个不存在的工具。

所以关掉之后，模型不该再尝试调用它。已经在历史里落库的旧轮次不受影响 —— 如果那里还留着 AI_NoSuchToolError: Model tried to call unavailable tool '...' 这类的失败步骤，那是改之前跑出来的记录，新一轮不会再有。

开关影响新发起的一轮；正在跑的那一轮用的是发起时的清单。

9.6 问答配置#

配置 范围 默认 说明

9.9 回答的可信性#

工具证据#

每次工具调用会从结果中抽取“证据”，例如：

  • OBJECT / RELATIONSHIP：真实对象或关系；
  • OBJECT_TYPE / RELATION_TYPE：对象类型与关系类型；
  • ACTION / INTERFACE / METRIC / GROUP：定义层概念。

界面上“依据”一行会展示这些证据；有 instance.read 权限时，对象证据可以点回对象页核对。

回答边界#

  • 模型只读已发布版本；草稿内容不会作为答案依据；
  • 模型只能通过工具访问数据，不能自己编造表名、列名或 JOIN 条件；
  • run_sql 有行数上限和只读保护，返回被截断时会明确标记；
  • 指标是可引用口径，临时聚合会产生“未引用已定义指标”的 warning；
  • 证据来自工具结果，不等于业务事实本身；关键结论仍应通过对象页或源表核对。

9.12 当前限制#

  • 需要外部 OpenAI 兼容模型端点；平台不内置模型。
  • 运行态在内存里，进程重启会丢掉正在跑的运行；已落库历史不受影响。
  • 问答与 MCP 全部只读；不能通过问答写业务数据。
  • 查询 DSL（run_query）出厂默认关闭；打开后结构化问数优先走它，DSL 暂不支持或需要排障时才用 run_sql，两者都保留。
  • 动作定义、查询 DSL、对象实例查询与关系子图查询出厂默认关闭，需要管理员显式打开。
  • 向量检索没有 embedding 提供方；search_schema 当前主要依赖名称、描述、取值画像和关键词。
  • 智能问答的配置保存在浏览器本地，不同机器、不同浏览器不共享。

2.1 部署前要知道的三件事#

平台运行时依赖三类外部系统，职责不能混：

系统 是否必需 作用 由谁部署
PostgreSQL 平台库 必需 存本体台账、版本定义与实例快照、用户角色、审计、对象索引、列画像 你现有的 PostgreSQL
图存储 内置图开箱可用；Jena/Fuseki 可选 存发布后的本体投影，供实例读写和 SPARQL 查询 用 Jena 时自行部署 Fuseki，否则不用

Docker Compose 默认只部署平台本体（app 容器）。PostgreSQL、Fuseki 和业务库都不进编排；这意味着你可以复用现有数据库和中间件，不必把生产数据库搬进平台。

2.5 Docker Compose 部署#

准备配置#

cp .env.docker.example .env.docker
# 编辑 .env.docker：DATABASE_URL 用 host.docker.internal 指向宿主机或外部 PostgreSQL

Docker 环境里最容易踩的坑：

  1. 容器里的 localhost 是容器自己。 连宿主机的 PostgreSQL 要用 host.docker.internal；compose 已经加了 host.docker.internal:host-gateway，Linux 上也能这样写。
  2. Jena 端点若登记为 http://localhost:3030/...，容器默认会通过 GRAPH_ENDPOINT_HOST_ALIAS 改写成宿主机地址。远端 Jena 请直接登记可达地址。
  3. .env.docker 既给容器注入变量，也给 compose 做变量替换。 APP_PORT / NODE_IMAGE 也写在这个文件里；手动执行 docker compose up 时要带 --env-file .env.docker。

启动与常用命令#

pnpm docker:up      # docker compose --env-file .env.docker up -d --build
pnpm docker:logs    # 跟平台日志
pnpm docker:down    # 停止并删除平台容器
pnpm docker:config  # 打印合并后的编排，排查变量问题

平台数据都在 PostgreSQL 平台库里，docker compose down 不会删除本体定义和版本快照。图存储中的数据是发布投影，真的丢客户端也能从已发布快照重新发布恢复。

健康检查#

compose 给 app 容器配了健康检查：请求 http://127.0.0.1:3000/，返回 2xx 即为健康。你可以用：

docker compose --env-file .env.docker ps
docker compose --env-file .env.docker logs --tail=200 app

排查时优先看三类信息：平台库能否连接、迁移是否执行成功、应用是否进入了 NEXT 的监听状态。

2.6 升级与数据迁移#

正常升级#

  1. 备份平台库（至少备份 ontology_platform Schema）。
  2. 拉取新代码，重新构建镜像或重新安装依赖。
  3. 启动应用；服务端自动执行增量迁移。
  4. 检查“设置 → 图引擎配置”的连接测试，检查“数据资源”的连通性。

旧磁盘快照迁移#

旧部署可能把版本快照放在 .data/ontology-versions。当前版本已经把定义与实例快照统一放进平台库 ontology_platform.ontology_versions：

  • 服务端第一次访问版本数据时，会把磁盘上的历史版本迁进平台库，然后删除磁盘副本；
  • 只有旧机器上还有未迁移目录、且你要换机器时，才需要挂载或指定 ONTOLOGY_VERSION_DIR / VERSION_SNAPSHOT_DIR；
  • 全新部署不需要该目录，也不需要多实例共享它。

迁移 内容

0002-audit-version-column 审计记录增加版本维度
0003-column-profiles 列画像缓存表
0004-rbac-roles-and-permissions RBAC 角色与权限点

3.1 登录与会话#

平台使用 Bearer 令牌作为登录态，不使用 Cookie：

Authorization: Bearer <平台会话令牌>
项目 行为
登录接口 POST /api/auth/login，请求体是邮箱和密码
令牌形状 无状态 JWT，HS256 签名，密钥来自 AUTH_SECRET
有效期 8 小时；响应体会返回 expiresInSeconds
前端保存 浏览器 localStorage；刷新页面仍保持登录，多个标签页共用
服务端校验 每次请求先验签，再按 sub 回平台库核对用户、角色和权限
登出 POST /api/auth/logout 是空操作；前端清掉本地令牌就算登出
改密码 POST /api/auth/password，需要验证当前密码，不要求用户管理权限

因为服务端每次都回库核对用户，所以：

  • 停用账号、删除账号、修改角色后，旧令牌会立刻失去对应权限；
  • 删除用户不会删除他的历史审计记录；审计中的操作人会变空，并另有一条 USER_DELETED 记录邮箱；
  • 不要把令牌写进前端静态配置或用长期有效的方式分发；8 小时过期是刻意的保护。

状态码口径#

状态码 含义 典型处理
401 令牌不认、过期或用户已不存在 重新登录
403 登录有效，但当前账号缺少权限点 找管理员补权限，或换有权限的账号
400 请求格式或业务参数不合法 按错误信息修正
404 资源不存在 检查 id、版本或本体是否已删除
409 状态冲突，例如导入后重复初始化、图存储被两个本体占用 按提示先处理冲突状态

401 和 403 要分清：401 是“你是谁不认”，403 是“你是谁认了，但你不能做这个”。

界面隐藏只是体验；把按钮藏起来不等于安全边界，真正的边界在服务端。服务端怎么判，见下面一节。

服务端怎么判：一处执行、一处声明#

权限判断分两层，分工固定（2026-10-14 起）：

层 判什么 在哪
粗筛（middleware） 只判"有没有带凭据"：没带 Authorization: Bearer 的 /api/** 直接回 401 src/middleware.ts
细判（路由守卫） 这个接口要哪个权限点：没有权限回 403，没登录回 401 src/lib/platform/route-guard.ts

每个接口在导出处声明一次它要什么，执行只在那一个文件里：

export const POST = withPermission("ontology.write", async (request, _context, user) => { … });

四种声明，含义不同，别混：

包装器 含义
withPermission("权限点", …) 必须拥有这个权限点；handler 里能直接拿到已登录的用户
withUser(…) 只要求登录（例如"先登录再点允许"的授权同意）
withPublic(…) 按设计谁都能调（登录、登出、会话探测、首次初始化、OAuth 的两个匿名端点、免令牌的技能 MCP）
withOwnAuth(…) 自带鉴权（MCP 端点同一个 Authorization 头要认两套凭据）

为什么中间件不判权限点：它拿不到"这个请求要动哪个本体 / 哪个资源"，也拿不到接口的声明。在那里硬造一张"路径 → 权限点"的表就是第二个真相，两个地方一旦不一致，要么是权限洞、要么把有权限的人挡在外面。所以粗筛只认"有没有令牌"，权限点只声明一次。

两条自动闸门（改代码时会被它们拦住）：

  • 每个接口方法都必须包在上述四种之一，漏包当场红 —— 覆盖测试按方法粒度扫语法树，不再只是"这个文件里出现过守卫"；
  • 免鉴权的方法必须恰好等于名单里那几个，想加一个公开接口就得先改名单，评审看得见。

日常使用不受影响：401 仍然表示"令牌不认了/没登录"，403 仍然表示"登录了但没这个权限"。

10.1 平台提供两个 MCP 服务#

平台把两类能力分别发布成两个独立的 MCP 服务端，职责与鉴权都不同，不要混用：

本体数据 MCP 建模技能 MCP

提供什么 本体定义、表结构、只读数据查询、可选对象实例查询 三套建模技能的 Markdown、参考文件与出包脚本
鉴权 平台会话令牌，或 MCP 访问令牌 免令牌
能力 tools tools + prompts
数据敏感性 含本体定义与业务数据入口，必须鉴权 仅仓库内公开文档，不含凭据与本体数据

两个服务端都是 Streamable HTTP JSON 响应形态，协议版本 2025-06-18。

10.2 本体数据 MCP 的两种地址#

平台级端点：/api/mcp#

  • 一个端点覆盖平台上所有本体；
  • 每次调用由参数 ontology_id 决定查哪个本体；
  • tools/list 按全局默认工具策略返回；
  • 适合“还不知道要查谁、先列本体”的客户端。

本体级端点：/api/mcp/<本体 id>#

  • 地址把本体钉死；
  • tools/list 按这个本体生效的工具开关过滤；
  • tools/call 自动注入 ontology_id，客户端不用也不该自己填；
  • initialize 的说明里会写明绑定的本体名称与 id；
  • 配置片段一眼能看出这条 MCP 查的是哪个本体。

10.3 鉴权#

本体数据 MCP 支持三种 Bearer：

方式 来源 用途
平台会话令牌 平台登录接口返回的 JWT 平台内“MCP 调试”页、脚本、已有平台账号
MCP 访问令牌 平台生成、可多条、可撤销 外部 Agent / IDE；一条令牌配一个客户端
OAuth 访问令牌 走下面的授权码流程换来（1 小时过期，自动刷新） 支持 OAuth 的客户端：不用手工贴令牌

每条令牌代表一个账号#

访问令牌不是“万能钥匙”，它必须绑定一个平台账号：

  • 生成令牌时选“代表哪个账号”，默认就是你自己；
  • 调工具时服务端按那个账号当前的角色权限判断 —— 账号被停用、删除或改了角色，令牌下一次请求就跟着失效；
  • 那个账号要有“用智能问答与 MCP”（reasoning.use）权限，否则客户端能连上、但调不了工具；
  • 令牌清单里每条都会写明代表哪个账号；不能用的会直接标出原因和下一步。

补充规则：

  • .env.local 的 MCP_API_TOKEN 仍然认，但必须再配 MCP_API_TOKEN_USER=<账号邮箱> 指明它代表谁，否则它用不了；
  • 生产环境推荐在“MCP 调试 → MCP 接入”里生成平台管理的令牌；
  • 明文令牌加密保存，只有具备 mcp.token.manage 权限的管理员可以查看和撤销；
  • 平台管理令牌支持多条，撤销哪条只断哪条；
  • 换掉 TARGET_ENCRYPTION_KEY 会导致已有令牌解不开，需要撤销后重新生成。

权限#

操作 权限
进入 MCP 调试页、调用 MCP 数据工具 reasoning.use
生成 / 查看 / 撤销访问令牌 mcp.token.manage
修改工具开关 mcp.token.manage

用 OAuth 接（支持 OAuth 的客户端自动接上）#

支持 OAuth 的客户端不用手工贴令牌：它连 /api/mcp 拿到 401 之后，会按标准流程自己把接入做完。

  1. 读 /.well-known/oauth-protected-resource：知道令牌该找谁要；
  2. 读 /.well-known/oauth-authorization-server：拿到授权 / 令牌 / 注册三个地址；
  3. 调到 POST /api/oauth/register 自助注册（回调地址只收 https；本机 localhost 允许 http）；
  4. 把浏览器打开到 /oauth/authorize?...：这就是平台上的授权同意页 —— 你先登录平台账号，再点「允许」。 页面上会写明“是哪个客户端、用哪个账号、它能做什么”；
  5. 浏览器带着授权码跳回客户端，客户端用 POST /api/oauth/token 换成访问令牌（1 小时）与刷新令牌（30 天，自动轮换）。
端点 用途
GET /.well-known/oauth-protected-resource 受保护资源元数据：资源地址与授权服务器
GET /.well-known/oauth-authorization-server 授权服务器元数据：三个端点与支持的参数
POST /api/oauth/register 客户端自助注册（公开客户端，没有密钥）
GET /api/oauth/authorize 同意页开屏查询（给页面显示用）
POST /api/oauth/authorize 提交「允许 / 拒绝」（要登录）
POST /api/oauth/token 换访问令牌 / 用刷新令牌续期

要点：

  • 只支持授权码 + PKCE（S256）；回调地址必须与注册时一字不差（不支持通配）；
  • 访问令牌代表点「允许」的那个账号：他能看到的数据才看得到；账号被停用或改了角色，访问立刻跟着变；
  • 它拿到的权限和 MCP 一样是只读（同意页上写明了）；
  • 在「MCP 调试 → MCP 接入 → OAuth 客户端」里能看到注册过的客户端、复制三个标准地址、删掉不认识的 （删除会连同它的授权码与刷新令牌一起作废）。

想自己看一遍这条流程：在仓库里跑 pnpm oauth:demo（默认连 http://localhost:3000， 可以加 --platform=<地址>）。它会扮演一个真实客户端把上面五步走完，中间把浏览器打开到授权页让你亲手点一次， 然后把"换令牌 → 调 MCP → 刷新"的结果打在终端上。演示完那个客户端会留在清单里，可以随手删掉。

10.5 协议能力#

本体数据 MCP 实现以下 JSON-RPC 2.0 方法：

方法 说明
initialize 返回协议版本、服务名、能力与使用说明
notifications/initialized 客户端初始化通知；服务端不返回响应
ping 连通性检查
tools/list 按当前策略返回可用工具
tools/call 调用工具；错误放在 result.isError，让模型能自我纠正

其他行为：

  • 支持单条和批量 JSON-RPC 请求；
  • 全是通知时返回 202，无响应体；
  • GET 返回 405：本实现不做服务端主动推送；
  • OPTIONS 返回 CORS 预检响应；
  • 工具返回 MCP 标准的 content 文本与 structuredContent。

10.11 安全与审计#

  • 本体数据 MCP 是只读，写操作只能通过平台内动作；MCP 不提供写工具；
  • 工具只读已发布版本，草稿不会暴露给外部客户端；
  • 访问令牌逐条加密保存，查看与撤销需要权限；
  • 令牌错误与未配置令牌是两种情况，调试页会分别提示；
  • 工具开关变更写 REASONING_TOOL_POLICY_UPDATED 审计；
  • MCP 的工具调用会随智能问答的 REASONING_RUN 或图查询写入审计；
  • CORS 允许跨域，因此令牌就是实际边界，必须妥善保管。

11.1 本体技能是什么#

本体技能不是平台运行时依赖，而是一套随平台下发的建模方法，由 Markdown、参考文件和 Node 脚本组成。它们帮助模型或人按统一流程完成“从业务材料到可导入本体包”的工作。

三套技能按建议顺序使用：

阶段 技能 id 中文名 何时用 主要产物
1 ontology-requirement 需求澄清 材料散、口径未定、范围未划清 01-需求澄清.md：对象类型 / 关系类型 / 接口 / 动作 / 规则候选 + 待确认问题
2 ontology-builder 本体设计 已有建模清单或业务材料，需要定粒度、命名、主键、类型、关系与约束 02-建模方案.md + *.blueprint.json 初稿
3 ontology-bundle 出包与交付 方案已定，要产出可直接导入平台的本体包 <标识>.ontology.json + 导入 / 校验 / 发布说明

也可以单用第 3 条，把已有方案编成 JSON。

11.2 两种使用方式#

方式一：下载技能整包#

入口：本体模型 → 本体技能 → 获取 Skills。

  • 页面只展示技能清单：名称、适用场景、主要产物、文件列表；
  • 正文不在页面里展开，避免页面一打开就传几百 KB；
  • 下载接口只有整体下载：GET /api/skills/archive，得到一个 zip；
  • 解压后得到 ontology-requirement/、ontology-builder/、ontology-bundle/ 三个目录。

安装位置：

Codex：~/.codex/skills/<技能名>/SKILL.md
通用 Agent Skills：~/.agents/skills/<技能名>/SKILL.md

重启会话后生效。

方式二：免令牌 MCP 直连#

平台把同一套技能发布为免令牌 MCP 服务：

http://<平台地址>/api/skills/mcp

它提供：

能力 说明
tools list_ontology_build_skills、get_ontology_build_skill、get_ontology_build_skill_file
prompts 每套技能一个提示词，客户端里就是斜杠命令

工具名自带 ontology_build_skill，与本体数据 MCP 的工具一眼分得开。

推荐取用顺序：

list_ontology_build_skills
  → get_ontology_build_skill(skill_id)
  → get_ontology_build_skill_file(skill_id, path)   # 取 references/ 或 scripts/ 里的文件

技能 MCP 是公开文档，不含凭据和本体数据，因此免鉴权；但不要往 skills/ 目录放敏感内容。

11.3 出包工作流：清单 → 编译#

模型和人不直接手写最终包，而是先写一份结构化清单（blueprint），再用脚本编译成平台可导入的本体包（bundle）。

业务材料
  → 01-需求澄清.md
  → 02-建模方案.md + *.blueprint.json
  → node scripts/build-bundle.mjs <清单.json>
  → <标识>.ontology.json
  → 平台导入（停在草稿）
  → 校验 → 发布

为什么分成两步：

  • 清单里引用一律写名字，不写 UUID；脚本负责解析引用、生成 id、补默认值；
  • 手写 UUID 和格式字段最容易错，错一个就整包报错；
  • 编译脚本会当场校验引用能不能解析、结构对不对，并列出合法名字帮助修复。

常用命令#

# 只校验，不产出包
node scripts/build-bundle.mjs <清单.json> --check

# 产出 <标识>.ontology.json
node scripts/build-bundle.mjs <清单.json>

# 指定输出路径
node scripts/build-bundle.mjs <清单.json> --out ./交付/xxx.ontology.json

# 输出到标准输出
node scripts/build-bundle.mjs <清单.json> --stdout

# 手写包的结构自检
node scripts/check-bundle.mjs <包.json>

Windows / Linux / macOS 一样，需要 Node 18+；脚本只用内置模块、不装依赖、不联网。路径带空格就加引号。

脚本返回码#

结果 含义
退出码 0 编译成功；可能有 ⚠ 提醒，但不挡编译
退出码 1 清单有问题：未知名字、重名、枚举写错、必填缺失
退出码 2 用法错误或文件读不了

⚠ 提醒使用平台建模体检的规则码，导入后平台会说同样的话，便于对齐。

11.4 清单格式要点#

清单顶层结构（详见 skills/ontology-bundle/references/blueprint-format.md）：

{
  "format": "ontology.blueprint",
  "formatVersion": 1,
  "ontology": { "name": "专线服务本体" },
  "objectTypes": [],
  "relationTypes": [],
  "interfaces": [],
  "groups": [],
  "metrics": [],
  "actionTypes": [],
  "rules": [],
  "dataSources": []
}

编写规则：

  • 引用一律写名字：对象类型名、关系类型名、接口名、分组名、动作名、数据资源名；
  • ontology.name 必须有；其它字段大多有默认值；
  • 属性上的 source 是本类型内那份来源的局部 id，默认 primary；
  • 数据资源在 sources[].dataSource 上按名字引用，只写连接坐标，绝不写账号密码；
  • 不确定的字段宁可不写，不要编造表名和列名；
  • 属性 dataType 必须与真实数据一致：金额用 DECIMAL、时间用 DATETIME、文本用 TEXT 等。

可照抄的完整示例：

skills/ontology-bundle/references/example.blueprint.json
skills/ontology-bundle/references/example.bundle.json

11.5 出包前检查清单#

编译通过不代表语义正确。交付前人工过一遍：

  • 接口里 required 的每个属性，实现方都有同名或显式映射的属性。
  • 接口里 required 的关系约束，实现方都有一条“起点 = 自己、终点 = 约束目标”的方向正确的关系类型。
  • 动作的 scope 是业务上真正接受这个动作的对象类型。
  • 规则条件里的 property 在主对象类型上存在；处置档位选对，拒绝用 BLOCK，只提示用 WARN。
  • 名称是业务语言，没有 tb_ 前缀、没有直接拿中文列名当属性名。
  • 属性数据类型与真实列一致。
  • 表名、列名来自材料，没有凭空编造。
  • 交付说明写明“导入后先校验再发布”，以及哪些对象类型还需要重新选表。
  • 交付说明提醒平台会做建模体检，并按规则码自查过一遍。

11.6 导入与交付#

导入路径#

平台界面：总览 → 导入本体包 → 选择文件 → 选择存储资源 → 导入。

导入后一定停在草稿：

  1. 处理待补的数据资源绑定；
  2. 运行发布校验，处理违规；
  3. 运行建模体检，按优先级处理建议；
  4. 发布；
  5. 到对象页、实例图谱、智能问答验证。

大文件交付#

几百 KB 的 bkn 知识网络（几十个对象类型、上千个属性）建议使用命令行导入：

node scripts/import-ontology.mjs "<文件.json>" --dry-run --email admin@example.com --password '******'
node scripts/import-ontology.mjs "<文件.json>" --storage-target "内置类型图" --name "客户账务网络 v6"

先干跑确认“会导入什么、会丢什么”，再正式导入。详情见第 5 章。

交付说明应该包含#

  1. 文件名与 ontology.name；
  2. 结构规模：对象类型 / 关系类型 / 接口 / 动作 / 规则数量；
  3. 导入路径与导入后的两步（校验 → 发布）；
  4. 已知待确认项：未绑定来源的对象类型、未实现的接口、待确认的表和列；
  5. 数据资源坐标匹配情况；
  6. 是否包含指标、概念分组、接口约束等高级结构。

12.1 为什么需要图存储抽象#

平台的上层能力（本体建模、版本发布、实例图谱、问答工具）不应该依赖某一种图数据库。因此平台定义了一层统一的图存储契约 GraphStore：

  • 上层只调用语义化方法，不直接写某种查询语言；
  • 每种后端实现一个适配器，由注册表按 target.kind 分派；
  • 换图后端时，API 路由、发布流程和界面组件不需要改；
  • 新增后端只需要登记类型、补连接表单元数据、实现适配器并注册。

当前支持两种后端：

后端 kind 说明
内置类型图 EMBEDDED 平台自带，PostgreSQL 持久化快照，N3.js / Comunica 提供只读 SPARQL，Graphology 类型图；无需单独部署服务
Apache Jena / Fuseki JENA RDF / OWL / SPARQL 1.1；通过 Fuseki SPARQL 端点读写三元组，支持推理机

Neo4j 已经整体移除；neo4j_targets 到 graph_targets 的历史迁移保留，只服务于老部署升级。

12.2 存储职责#

平台有三类存储，职责不同：

存储 存什么 是否权威 丢了怎么办
PostgreSQL 平台库 本体台账、版本定义与实例快照、概念索引、用户角色、审计、对象索引、列画像 权威 必须从备份恢复
图存储（内置 / Jena） 发布后的本体投影 派生 从已发布版本快照重新发布
业务库（PG/MySQL/Oracle） 对象与关系的真实业务数据 业务权威 按业务系统自身备份恢复

关键结论：

定义与版本在平台库，图库只是投影；业务数据在业务库，平台只读访问。

因此：

  • docker compose down 或删图库数据，不会丢平台版本；
  • 图库损坏可以从已发布快照重建；
  • 业务库数据变化不会自动改本体版本；
  • 对象索引也是派生数据，可以重建。

12.3 内置类型图#

内置图存储是平台的默认后端，适合不需要外部图服务的部署。

组成#

组成 作用
PostgreSQL embedded_graphs 持久化发布视图，按受管目标 id 隔离
Graphology 类型图与图算法视图
N3.js / Comunica 只读 SPARQL 查询

隔离方式#

  • 内置后端由受管目标 id 隔离；
  • 新建或导入具体本体时，平台持久化独立的受管目标；
  • GRAPH_TARGET_KINDS 里的内置选项是虚拟存储选项，不在 graph_targets 中创建根资源记录；
  • 不需要凭据，也不能删除该选项。

能力#

能力 值
schemaVisualization true
strongRules false（强规则不由内置图库落地）
atomicReplace true
查询语言 SPARQL 1.1 只读

使用边界#

内置类型图当前只包含类型级定义和少量手工实例，不适合海量业务对象：

  • 发布视图以 JSONB 视图和进程内 RDF Store 形式存在；
  • 海量业务对象通过对象服务、对象索引和回源业务库读取；
  • 不要把内置图当作生产级对象存储或大规模图计算引擎。

12.4 Apache Jena / Fuseki#

Jena 后端适合需要 RDF / OWL / SPARQL 能力、需要与外部知识图谱互通的场景。

属性图 RDF 形态

隔离方式#

Jena 的隔离单位是命名图，不是“多起一套实例”：

做法 适用 说明
命名图（默认） 一个数据集里一个本体一个命名图 平台自动分配 urn:ontology:<本体 id>，同一 Fuseki 上可并存多个本体
多 dataset 按环境 / 租户再分一层 一个 Fuseki 下配多个 dataset，登记存储时选不同数据集
独立实例 资源或权限硬隔离 单起一套 Fuseki / TDB2；日常使用不需要

同一个“数据集 + 命名图”不能登记两个本体存储，否则两边会互相看见数据，发布时互相清空。平台会以 409 拦下并说明怎么改。

容器部署的端点改写#

容器里的 localhost 是容器自己。如果库里登记的是 http://localhost:3030/ds，而 Fuseki 在宿主机上，平台默认通过 GRAPH_ENDPOINT_HOST_ALIAS=localhost=host.docker.internal 改写；远端 Fuseki 直接登记真实可达地址，或在环境变量里覆盖别名。

12.5 发布与原子替换#

GraphStore.replaceGraph() 的硬性契约是：失败时图数据必须保持替换前的状态。能力由 capabilities.atomicReplace 声明，发布流程据此决定失败提示。

后端 原子替换实现
Apache Jena 单个 SPARQL Update 完成“清空 + 插入”；超过 5000 条三元组时先写影子命名图，再一个请求 CLEAR + ADD + DROP 原子切换
内置类型图 PostgreSQL 单行 UPSERT 原子替换发布视图，查询只见旧版本或新版本；Graphology/N3.js 视图按需重建

并发控制：

  • 进程内发布队列；
  • PostgreSQL advisory lock。

两层串行保证多实例部署时不会并发替换同一个本体存储。

12.7 多本体与多实例#

多本体#

  • 内置图：受管目标 id 隔离；
  • Jena：命名图隔离，一个本体一个命名图；
  • 同一数据集 + 命名图不能登记两个本体存储；
  • 新建本体时可选择内置图或已登记的 Jena 连接。

多实例#

平台版本数据在 PostgreSQL 中，所以多实例部署不需要共享文件卷：

  • 所有实例连同一个平台库；
  • 发布通过 advisory lock 串行；
  • 实例本身无状态；对象索引与列画像也在平台库；
  • 旧磁盘快照目录只在一次性迁移时使用，不参与日常运行。

12.8 扩展新后端#

新增图后端的三步：

  1. 在 GraphTargetKind 登记类型，并在 GRAPH_TARGET_KINDS 补连接表单元数据；
  2. 新增实现 GraphStore 的适配器；
  3. 在注册表中注册。

API 路由、版本发布流程和界面组件无需改动。未来的候选后端（如 NetworkX、Elasticsearch 等）保持同一模式；文档里把“规划中”与“已支持”分开写。

同一个原则适用于平台上所有外部存储（对象索引、关系库、搜索、向量、缓存）：先有契约层，业务代码只认契约与注册表，不直链某个实现。换存储 = 新增一个适配器目录 + 注册表登记一行，域代码 / API / 界面 / AI 工具都不动。

对象索引就是这么做的：契约与注册表在 src/lib/framework/object-index/，实现按后端分目录（现在只有 clickhouse/），领域侧的“快照节点 → 索引条目”映射留在 src/lib/instance/object-index/entries.ts。判断标准很简单：SQL、表名、参数格式这些只允许出现在适配器目录里；出了那个目录就只剩契约里的名词。

12.9 迁移与切换后端#

图后端是投影，切换后端的原则是“从平台版本重新发布”：

  1. 确认平台库中的版本记录完整；
  2. 在新图存储上登记一个连接；
  3. 用本体包迁移定义，或直接把现有本体改绑新存储；
  4. 重新发布；
  5. 核对运行时 Schema、对象数和关系数；
  6. 旧图存储确认无人使用后再清理。

注意：

  • 本体包只带结构，不带实例；如果实例只在旧图存储里，需要先确认来源或快照里是否有对应数据；
  • 平台版本快照包含实例数据，可用于历史激活和重新发布；
  • 直接改图库数据不会改平台版本；下次发布会按快照整图替换，手工改动会丢。

12.10 当前限制与演进方向#

  • 内置图适合类型层和少量实例，不是海量对象存储。

  • Jena 的强约束能力为 false；必填 / 主键等规则由平台校验层负责，不由图库硬约束。

  • 发布是整图替换，不是增量发布；数据量大时发布耗时会上升。

  • 对象索引现在在 ClickHouse（列存表 <库>.object_entries）；要不要再加搜索后端只影响适配器，对象服务接口不变。

  • 没有 embedding 提供方；向量检索能力有底座但暂不可用。

  • 查询 DSL 已支持关系 JOIN（外键式 / 中间表式）与同一数据资源内的多来源 MDO JOIN；跨数据资源 JOIN 仍不支持；影子对拍工具已实现，真实业务问题集对拍与验收待完成。详见查询 DSL 附录。

13.1 接口总则#

平台对外的 HTTP 接口是 Next.js App Router 实现，业务逻辑集中在 src/lib，路由只做薄封装。集成时遵循：

  • REST 接口用于平台界面和脚本；
  • 智能问答与 MCP 使用独立的流式 / JSON-RPC 协议；
  • 所有接口默认要求登录，除非明确标注公开；
  • 写操作有权限点校验；
  • 读接口默认只读已发布版本，除非明确允许草稿版本；
  • 接口字段的最终事实来源是 /docs（Swagger UI）与代码里的 Zod schema。

动作执行请求体（POST /api/ontology/:versionId/actions）：

字段 必填 说明
actionId 是 动作 id
subjectEntityId / subjectRef 否 主对象（subjectRef 形如 对象类型/主键串；对象只存在于数据源时，平台先按主键把它取进草稿再执行）
inputs 否 入参：{ code, entityId?, entityRef?, value? }
dryRun 否（默认 true） 只算不写：不改草稿快照，也永远不写业务库
writeback 否（默认 false） 是否把改动写回业务库（只对表 / 视图主来源生效；干跑时只产出"会写什么"的计划）
  • 写回只支持改已有行（UPDATE），按对象类型主来源的主键列定位；键命中 0 行或 2 行以上一律拒绝（不盲写）。
  • 一次动作里只要有一处写不回去，返回 409 且整批不执行，响应里带逐条原因与出路。
  • 响应里的 writeback 分四态：OFF（没勾）/ PREVIEW（干跑出的计划）/ APPLIED（已写库，带旧值 → 新值与实际语句）/ REFUSED（被拒，整批没执行）。

创建草稿示例：

  -H 'Content-Type: application/json' \

14.1 安全模型#

平台的安全边界分四层：

层 机制
身份 登录接口发 8 小时 HS256 JWT；每次请求回库核对用户、角色与权限
授权 14 个模块级权限点；角色 = 权限集合；服务端每个写入/敏感接口执行 requirePermission
数据访问 业务库只读事务 + 词法 SQL 护栏；图库和平台库只由服务端访问；前端不接触密码和主密钥
写入边界 业务写只能通过动作，且只写草稿快照；原生查询一律只读；发布必须走校验和整图替换

关键原则：

  • 界面隐藏按钮只是体验，真正的边界在服务端 requirePermission；
  • 401 与 403 分开：401 是身份不认，403 是权限不够；
  • 凭据用 TARGET_ENCRYPTION_KEY 加密保存；密钥丢了数据解不开；
  • 导入流程不信任外部文件，一律重发 id、停在草稿；
  • MCP 和问答只读，且只认已发布版本。

浏览器端令牌#

  • 令牌存 localStorage，前端每个请求附加 Authorization: Bearer；
  • 换来的是免 CSRF、Postman / curl 直接可调；代价是 XSS 能读走令牌；
  • 缓解措施：8 小时过期、服务端每次回库验证、前端不做不可信 HTML 注入；
  • 不要在生产环境把令牌打进日志、前端静态文件或公开配置。

14.7 明确边界与后续方向#

当前明确未做或未开放的能力：

  • get_property_values：按列查询取值；用户口径是先不做，取值走列画像。
  • list_tables / search_columns：明确否决；表只能通过对象类型到达。
  • 同义词 / 别名层、分区键与表行数、run_sql 结果缓存与 dry-run。
  • 对象与关系实例层的大规模存储方案；对象索引当前在 PostgreSQL，数据量上来后再选型。
  • 查询 DSL：run_query 已实现，出厂默认关闭（在「MCP 调试」里打开后是结构化问数的优先入口；关系 JOIN、同一数据资源内的 MDO JOIN 已实现）；跨数据资源 JOIN 仍不支持，真实业务问题集对拍与验收仍在推进。
  • 动作定义、查询 DSL、对象实例查询与关系子图工具出厂默认关闭。
  • 向量检索缺少 embedding 提供方。
  • 动作写回业务库尚未实现。

后续演进方向：

  • DSL 多来源与真实问题集对拍；
  • 对象索引替换为独立搜索后端（如 OpenSearch / Solr）；
  • embedding 提供方接入，启用向量检索；
  • 图存储更多后端（NetworkX、Elasticsearch 等）；
  • 运行态持久化，让问答跨重启继续；
  • 更细的权限点或数据级权限策略。

14.8 运维原则#

  1. 平台库和密钥一起备份。
  2. 图库可丢、可重建；平台库不可丢。
  3. 任何写入口只在草稿，发布才切换已发布视图。
  4. 不要直接改图库，否则下一次发布会按快照整图替换。
  5. 凭据只走加密存储，不要写进本体包、技能文档或前端配置。
  6. MCP 令牌一条一客户端，撤销和轮换要可追踪。
  7. 排障先看审计，再看连接测试和日志；审计是平台自己的“事实流水”。
  8. 变更先干跑 / 先校验：动作先干跑，导入先 dry-run，发布先校验。

面向模型与程序的逻辑查询协议、字段规范、关系查询和安全边界。

1. 目标与定位#

查询 DSL 是智能问答和外部 MCP 客户端访问业务数据的统一逻辑查询协议。

它解决的问题是：

  • 模型不再直接生成 SQL
  • 模型不再关心物理表名、列名、连接方式
  • 业务口径从本体定义层统一解析
  • SQL 只由后端编译器生成
  • 未来可以继续接 Elasticsearch、知识库检索等后端

DSL 的基本链路：

用户自然语言
  ↓
LLM
  ↓
run_query / query-dsl JSON
  ↓
Schema 校验
  ↓
语义解析 Resolve
  ↓
LogicalPlan / AST
  ↓

  ↓
SQL 编译器
  ↓

  ↓

核心原则：

  1. DSL 以对象类型、属性、关系类型、指标为中心，不暴露物理表。
  2. LLM 不能提供 SQL、表名、列名或任意表达式片段。
  3. 所有值使用参数绑定，不拼接到 SQL 字符串。
  4. 不能保证语义等价的查询必须明确拒绝，不做静默近似。
  5. 指标负责表达业务口径；临时聚合允许，但必须标记为 ad-hoc。
  6. 关系 JOIN 只能通过本体关系类型产生，不能由模型自由编造 JOIN 条件。
  7. 关系放大风险默认 fail-closed：聚合查询遇到可能重复计数的关系时拒绝执行。

2.3 本体 SQL（SQL 形状的表层，2026-10-14 落地）#

用户口径（2026-10-14 拍板）：表层用 SQL 形状、内核仍是本体语义。理由很简单 —— 模型和人都会 SQL， 不必为平台再学一门自创语法；而"保证"（基数 fail-closed、跨数据资源拒绝、指标口径、只读闸门） 全部来自内核，与表层无关，所以换表层一条都不会丢。

两种表层产出同一份 QueryDsl：本体 SQL 解析 + 绑定之后，与 JSON DSL 共用 resolveQueryDsl → 执行路由 → 编译 / 只读执行。不存在"两套语义"，改校验或改编译只需要改一处。 执行路由只换“从哪里读”，不换解析、校验、指标口径、JOIN 语义或基数保护：

  • 查询涉及的对象类型和关系类型都已有“完整跑到源尾”的物化清单 → 编译到 ClickHouse 对象索引（object_entries / object_links）；
  • 任意一处没物化、只物化了一部分或清单已清掉 → 沿用原来的业务库 SQL 执行链；
  • 路由结果通过 data_source / data_source_kind 返回（例如 ClickHouse 对象索引 / CLICKHOUSE，或 oracle-test / ORACLE），不把“到底查了哪边”藏起来。

run_query 工具只收本体 SQL（sql + parameters）：一个工具只留一种表层，模型才不用在两套语法之间挑。 JSON DSL 仍在代码里（executeQueryDsl，程序化构造与影子对拍用），只是不出现在工具入参上。

层 文件 职责
词法 / 语法 src/lib/query-dsl/sql-surface/parse.ts 文本 → 语法树（SqlQueryAst）；不认识本体
语义绑定 src/lib/query-dsl/sql-surface/bind.ts 语法树 + 本体定义 → QueryDsl；判属性 / 指标、判别名、判 kind
执行入口 src/lib/query-dsl/execute.ts executeOntologySql（本体 SQL）与 executeQueryDsl（JSON DSL）

语法子集（v0）

SELECT 输出项 [AS 列名] [, …]
FROM 对象类型 [AS 别名]
[[LEFT] JOIN 关系类型 [AS 别名] [FORWARD | BACKWARD | BOTH]] …
[WHERE 条件]
[GROUP BY 属性, …]
[ORDER BY 输出列名 | 属性 [ASC | DESC], …]
[LIMIT n]
  • 输出项：属性 / 别名.属性 / 指标名 / COUNT(*) / COUNT(DISTINCT 属性) / SUM|AVG|MIN|MAX(属性) / LABEL(属性)。 裸名字先按当前实体的属性找，再按指标找 —— 两个都不是就把"两条路 + 候选名字"写进错误里。
  • 条件：= <> > >= < <=、IN / NOT IN、BETWEEN … AND …、IS [NOT] NULL、 LIKE '%值%'（也支持 '值%' / '%值'，其余模式拒绝并提示改用 =）、 LABEL(属性) = '枚举标签'（按码值的中文标签过滤）、AND / OR / NOT 与括号。
  • 日期属性（DATE / DATETIME）不能用 LIKE 取"某一天"：某一天写 统计日期 >= '2026-09-13' AND 统计日期 < '2026-09-14'， 区间写 BETWEEN … AND …。别写 = '当天' —— 列里带时分秒时它会静默返回 0 行，比报错更危险。 踩过：模型在日期属性上写 LIKE '2026-09-13%'，被拒之后连撞 3 次；现在这条错误里直接给出上面两种写法。
  • 参数：:名字，取值走 parameters —— 与 JSON DSL 的 {"param":"名字"} 是同一套机制。
  • 关系遍历：JOIN 只能写关系类型，不给写 ON 条件（连接的读法由关系类型与它的键映射决定）； LEFT JOIN = 可选（对不上也保留左边这一行）。FORWARD（默认）/ BACKWARD / BOTH 是本方言 唯一的语法扩展：SQL 没有"边方向"这个概念，而本体关系是双向的一条定义。
  • kind 不用手写：有指标或聚合就是 aggregate，否则 records。
  • 不接受：SELECT *、子查询、CTE（WITH）、UNION、窗口函数、任意函数、跨数据资源 join —— 一律如实报错，不做静默近似；这些情况用 run_sql 兜底。
  • 主来源是取数口径（DERIVED）时也能查：口径本身就是来源（view 只是给界面拿列清单的参考表）， 编译出来是 (口径) 别名 子查询。口径只能当主来源；放到补充来源上（MDO 合并）会被拒绝。

3. DSL v1.0 规范#

3.1 顶层结构#

{
  "version": "1.0",
  "kind": "records",
  "from": {
    "object_type": "对象类型名",
    "alias": "root"
  },
  "relationships": [],
  "where": {},
  "select": [],
  "group_by": [],
  "order_by": [],
  "limit": 100,
  "parameters": {}
}

字段说明：

字段 必填 说明
version 否 默认 "1.0"，当前只接受这一版；它指 DSL 语法版本，与本体的已发布 / 草稿版本无关（本体版本由运行上下文决定，query 里不用也不能传）
kind 是 records 或 aggregate
from.object_type 是 本体里的对象类型名
from.alias 否 默认 root
relationships 否 受控关系遍历列表
where 否 递归过滤表达式
select 是 输出字段、指标或聚合
group_by 否 聚合维度
order_by 否 排序
limit 否 默认 100，最大 5000
parameters 否 查询参数值

3.2 字段引用#

{ "alias": "root", "property": "统计日期" }
  • alias 默认是 root
  • property 必须是对象类型上的属性名
  • 属性由 Resolver 映射到物理列，模型看不到物理列

3.3 过滤表达式#

逻辑组合：

{ "and": [ ... ] }
{ "or": [ ... ] }
{ "not": { ... } }

条件：

{
  "field": { "alias": "root", "property": "业务状态" },
  "op": "eq",
  "value": "A"
}

支持的操作符：

操作符 语义 备注
eq 等于 通用
ne 不等于 通用
gt / gte 大于 / 大于等于 数值、日期
lt / lte 小于 / 小于等于 数值、日期
in / not_in 集合包含 / 不包含 值数组
contains 字符串包含 编译为参数化 LIKE，处理通配符转义
starts_with 前缀匹配 参数化 LIKE
ends_with 后缀匹配 参数化 LIKE
is_null 为空 不接受比较值
is_not_null 非空 不接受比较值
enum_label 按枚举标签比较 由属性 enumValues 解析到实际码值；本体 SQL 里写 LABEL(属性)，它也能当输出 / 分组维度（见 3.4）
in_range 闭区间 值必须是 [from, to] 两个元素

contains / starts_with / ends_with 只作用于文本属性；日期属性按天过滤请用范围比较（见 2.3 节）。

参数写法：

{
  "op": "eq",
  "value": { "param": "date" }
}

对应：

{
  "parameters": {
    "date": "2026-09-13"
  }
}

3.4 select#

字段输出：

{
  "field": { "alias": "area", "property": "地市名称" },
  "as": "地市"
}

指标输出：

{
  "metric": "专线条数",
  "on": "root",
  "as": "条数"
}

标签输出（把码值翻成中文标签）：

{
  "label": { "alias": "root", "property": "业务状态" },
  "as": "状态"
}
  • 编译成 CASE WHEN TRIM(列) = '码值' THEN '标签' END（Oracle 的 CHAR 列是空格填充的，先按既有口径去空格）； 认不出的码值给 NULL，与 LABEL(属性) = '标签' 的过滤语义一致。
  • 要求该属性配了 enumValues；没配就如实拒绝 —— 错误里会带上这一列真实的取值（来自列画像）， 可以直接改成按码值筛。
  • 聚合查询里标签维度要写进 group_by：GROUP BY LABEL(属性)（分组的是它下面那一列，标签只是显示形态）。 在对象索引（ClickHouse）那条路上，SELECT 与 GROUP BY 用的是同一个标签表达式。

临时聚合：

{
  "aggregate": "SUM",
  "property": "税后优惠后收入",
  "on": "root",
  "as": "收入"
}

聚合枚举：

  • COUNT
  • COUNT_DISTINCT
  • SUM
  • AVG
  • MIN
  • MAX

语义：

  • COUNT 且不填 property：数行数，编译为 COUNT(*)
  • COUNT 且填 property：统计非空值
  • COUNT_DISTINCT：必须填 property
  • SUM / AVG / MIN / MAX：必须填 property

临时聚合会在结果里产生 warning，表示它没有引用已定义指标。

3.5 指标口径#

优先使用本体指标：

{
  "metric": "专线条数",
  "as": "条数"
}

指标解析会展开：

  • 作用对象类型
  • 聚合方式
  • 被聚合属性
  • 固定过滤
  • 可用维度
  • 单位
  • draft / verified 状态

指标固定过滤不会无条件塞进全局 WHERE。如果多个指标固定过滤不同，编译器会生成条件聚合：

COUNT(CASE WHEN 产品名称 LIKE :p1 THEN 1 END)
SUM(CASE WHEN 状态 = :p2 THEN 收入 END)
COUNT(DISTINCT CASE WHEN 口径成立 THEN 客户编号 END)

如果所有指标过滤条件相同，后续可以优化为统一 WHERE 下推；当前优先保证语义正确。

draft 指标允许执行，但结果带 warning。以后可以配置为直接拒绝 draft。

3.6 关系引用#

关系引用只能引用本体中已有的关系类型：

{
  "alias": "area",
  "type": "归属地市",
  "from": "root",
  "direction": "forward",
  "optional": true
}

规则：

  • alias 必须唯一
  • from 必须指向已经声明的别名
  • direction 支持 forward / backward
  • 当前 SQL 编译器不接受一个关系同时向两个方向展开
  • optional: true 编译为 LEFT JOIN
  • optional: false 编译为 JOIN
  • 连接列来自关系类型的 key mapping 与 planLinkSource()
  • 模型不能提供 JOIN 条件
  • 关系涉及的数据资源必须与根查询一致；跨数据资源默认拒绝

3.7 排序与分页#

{
  "order_by": [
    { "ref": "条数", "direction": "desc" }
  ],
  "limit": 100
}
  • ref 优先匹配 select[].as
  • 也支持对象属性名
  • 聚合查询的排序字段必须能解析成输出列或分组字段
  • limit 由执行器传递到只读查询上限，不拼接到模型可见内容

4. 内部 AST / LogicalPlan#

DSL JSON 不是编译器直接消费的形状。解析后生成类型化计划：

LogicalPlan
  Root Scan
  Relationship Joins
  Where
  Select
  GroupBy
  Aggregate
  OrderBy
  Limit

主要类型：

  • ResolvedEntity：对象类型、主来源、物理表、主键、属性映射
  • ResolvedField：逻辑字段到物理列
  • ResolvedExpr：过滤表达式树
  • ResolvedMetric：指标展开后的聚合、过滤、维度
  • ResolvedRelationship：关系方向、连接计划、基数
  • ResolvedSelectItem：字段、指标、临时聚合
  • LogicalPlan：完整逻辑计划

设计原因：

  • 让解析、校验、规划、编译解耦
  • 便于未来增加 Elasticsearch、知识库等后端
  • 避免每个后端各自重新解释 DSL

5. Resolver 语义#

Resolver 负责把 DSL 从“名字”解析成“可执行逻辑”。

校验包括：

  • 对象类型是否存在
  • 对象类型是否绑定数据资源
  • 属性是否存在
  • 属性是否映射到主来源
  • 指标是否存在
  • 指标作用对象是否匹配
  • 指标过滤属性是否存在
  • 指标维度是否允许当前 group_by
  • 关系类型是否存在
  • 关系方向是否合法
  • 关系端点是否匹配
  • 关系连接计划是否完整
  • 关系数据资源是否与根对象一致
  • 聚合字段是否都在 group_by 中
  • kind=records 不允许指标或聚合输出
  • kind=aggregate 至少要有一个指标或聚合输出

6. 关系与基数安全#

关系类型有一个方向性基数：

  • ONE_TO_ONE
  • ONE_TO_MANY
  • MANY_TO_ONE
  • MANY_TO_MANY

这里的基数回答的是：

从起点端走一次到终点端，会不会把一个对象放大成多行。

编译聚合查询时：

  • MANY_TO_ONE / ONE_TO_ONE：通常可以安全聚合
  • ONE_TO_MANY / MANY_TO_MANY：可能重复计数，默认拒绝
  • 基数未标注：聚合查询默认拒绝或要求显式收敛
  • 记录查询允许执行，但必须保留 warning

这条规则的目标是：

宁可拒查，也不静默算错。

6.1 多来源对象类型（MDO）#

对象类型可以有多份来源：

  • sources[0] 是主来源，决定对象身份、主键和标题。
  • 后续来源是补充来源，按主键列逐列对齐连接到主来源。
  • 属性通过 sourceId 指定自己来自哪份来源。
  • 主来源物理别名使用对象类型别名；补充来源使用稳定别名，例如 line__src1。
  • 编译器为补充来源生成 LEFT JOIN：补充来源的连接键 = 主来源主键。
  • 补充来源和主来源必须落在同一个数据资源；跨数据资源 MDO 当前拒绝。
  • 补充来源的 primaryKey 数量必须和主来源一致；不一致时拒绝。

MDO 不改变逻辑对象身份：模型仍然只引用对象类型和属性名，物理来源拆分由编译器和 Resolver 处理。

7. SQL 编译器#

当前支持：

  • PostgreSQL
  • MySQL
  • Oracle

编译规则：

  • 表名和列名使用方言标识符引用
  • 值全部走命名参数
  • 字符串匹配转义 %、_ 和转义符
  • 枚举标签先在 Resolver 中解析成实际码值
  • COUNT(*) 与 COUNT(column) 语义分开
  • COUNT_DISTINCT 使用 COUNT(DISTINCT ...)
  • 指标固定过滤生成条件聚合
  • group_by 编译成显式分组
  • order_by 使用输出列别名或已解析字段
  • 行数上限由连接器执行器统一处理

编译器输出：

type CompiledSqlQuery = {
  statement: string;
  parameters: Record<string, string | number | boolean | null>;
  dataSourceId: string;
  columns: string[];
  limit: number;
  warnings: string[];
};

编译后的 SQL 和参数只存在于服务端执行链路与审计记录中，不返回给模型。

8. 执行与结果#

执行入口：

executeQueryDsl(definition, dsl, deps?)

执行过程：

  1. 解析 DSL
  2. Resolver 生成 LogicalPlan
  3. 检查查询涉及的对象类型与关系类型是否有完整物化清单
  4. 已完整物化 → 编译到 ClickHouse 对象索引并只读执行；否则按根对象解析数据资源
  5. 未完整物化 → 根据数据资源类型选择业务库 SQL 编译器并调用连接器只读执行
  6. 归一化结果，并回传实际执行侧的 data_source / data_source_kind

结果形状：

{
  "data_source": "数据资源名称",
  "data_source_kind": "ORACLE",
  "columns": ["地市编码", "条数"],
  "rows": [["371", 5]],
  "returned": 1,
  "row_limit": 100,
  "truncated": false,
  "elapsed_ms": 86,
  "warnings": []
}

安全：

  • 只读事务
  • 词法只读检查
  • 参数绑定
  • 超时
  • 行数上限
  • 截断必须明确返回
  • 查询结果不作为本体实例证据

8.1 影子对拍#

为避免直接切换造成口径回归，提供内部对拍函数：

compareQueryDslWithSql(definition, dsl, referenceSql, deps?)

它会在同一个数据资源上：

  1. 解析并编译 DSL
  2. 执行 DSL 编译结果
  3. 执行人工参考 SQL
  4. 按列和行逐项比较
  5. 返回结构化差异

该能力只用于开发和验证，不暴露给模型。模型默认仍然不能提供 SQL。

  4. P1：已开放 run_query（出厂默认关闭），提示词写明「工具清单里有它才优先用 DSL」
  5. 长期：不删除、不禁用 run_sql

不允许在 DSL 失败时自动静默回退 run_sql；模型应根据明确错误显式选择 DSL 或 run_sql 兜底。

  • 错误码
  • 人话原因
  • 修复建议
  • 必要的可用属性 / 维度 / 关系清单

11. 知识库融合方向#

知识库不是 SQL 编译器的替代品，而是未来规划器中的另一类数据源。

建议位置：

LogicalPlan
  ├─ 结构化子计划 → SQL 编译器
  └─ 非结构化子计划 → 知识库检索适配器

未来可以增加：

{
  "retrieve": {
    "source": "knowledge_base",
    "text": "互联网专线带宽口径",
    "top_k": 5
  }
}

融合步骤：

  1. 知识库检索返回文档或片段
  2. 通过实体键、对象引用或元数据映射回本体对象
  3. 与 SQL 子计划做受控融合
  4. 查询结果和知识片段分别标记来源
  5. 不能等价的融合明确拒绝或降级，不静默假装等价

这项能力依赖后续的 embedding provider、向量索引和权限策略；当前不提前耦合。
