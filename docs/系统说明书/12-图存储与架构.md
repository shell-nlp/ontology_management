# 第 12 章 · 图存储与系统架构

## 12.1 为什么需要图存储抽象

平台的上层能力（本体建模、版本发布、实例图谱、问答工具）不应该依赖某一种图数据库。因此平台定义了一层统一的图存储契约 `GraphStore`：

- 上层只调用语义化方法，不直接写某种查询语言；
- 每种后端实现一个适配器，由注册表按 `target.kind` 分派；
- 换图后端时，API 路由、发布流程和界面组件不需要改；
- 新增后端只需要登记类型、补连接表单元数据、实现适配器并注册。

当前支持两种后端：

| 后端 | `kind` | 说明 |
| --- | --- | --- |
| 内置类型图 | `EMBEDDED` | 平台自带，PostgreSQL 持久化快照，N3.js / Comunica 提供只读 SPARQL，Graphology 类型图；无需单独部署服务 |
| Apache Jena / Fuseki | `JENA` | RDF / OWL / SPARQL 1.1；通过 Fuseki SPARQL 端点读写三元组，支持推理机 |

Neo4j 已经整体移除；`neo4j_targets` 到 `graph_targets` 的历史迁移保留，只服务于老部署升级。

## 12.2 存储职责

平台有三类存储，职责不同：

| 存储 | 存什么 | 是否权威 | 丢了怎么办 |
| --- | --- | --- | --- |
| PostgreSQL 平台库 | 本体台账、版本定义与实例快照、概念索引、用户角色、审计、对象索引、列画像 | 权威 | 必须从备份恢复 |
| 图存储（内置 / Jena） | 发布后的本体投影 | 派生 | 从已发布版本快照重新发布 |
| 业务库（PG/MySQL/Oracle） | 对象与关系的真实业务数据 | 业务权威 | 按业务系统自身备份恢复 |

关键结论：

> **定义与版本在平台库，图库只是投影；业务数据在业务库，平台只读访问。**

因此：

- `docker compose down` 或删图库数据，不会丢平台版本；
- 图库损坏可以从已发布快照重建；
- 业务库数据变化不会自动改本体版本；
- 对象索引也是派生数据，可以重建。

## 12.3 内置类型图

内置图存储是平台的默认后端，适合不需要外部图服务的部署。

### 组成

| 组成 | 作用 |
| --- | --- |
| PostgreSQL `embedded_graphs` | 持久化发布视图，按受管目标 id 隔离 |
| Graphology | 类型图与图算法视图 |
| N3.js / Comunica | 只读 SPARQL 查询 |

### 隔离方式

- 内置后端由**受管目标 id** 隔离；
- 新建或导入具体本体时，平台持久化独立的受管目标；
- `GRAPH_TARGET_KINDS` 里的内置选项是虚拟存储选项，不在 `graph_targets` 中创建根资源记录；
- 不需要凭据，也不能删除该选项。

### 能力

| 能力 | 值 |
| --- | --- |
| `schemaVisualization` | true |
| `strongRules` | false（强规则不由内置图库落地） |
| `atomicReplace` | true |
| 查询语言 | SPARQL 1.1 只读 |

### 使用边界

内置类型图当前只包含类型级定义和少量手工实例，**不适合海量业务对象**：

- 发布视图以 JSONB 视图和进程内 RDF Store 形式存在；
- 海量业务对象通过对象服务、对象索引和回源业务库读取；
- 不要把内置图当作生产级对象存储或大规模图计算引擎。

## 12.4 Apache Jena / Fuseki

Jena 后端适合需要 RDF / OWL / SPARQL 能力、需要与外部知识图谱互通的场景。

### 连接配置

| 字段 | 说明 |
| --- | --- |
| `uri` | Fuseki 服务地址，例如 `http://host:3030`；也接受 `/ds/query`、`/ds/sparql` |
| `database_name` | 数据集名 |
| `username` / `password` | 可选；写入通常需要管理员凭据 |
| `options.namedGraph` | 可选；写入 / 读取指定命名图；不配时使用默认图 |

平台给每个本体自动分配命名图 `urn:ontology:<本体 id>`。

### RDF 与属性图映射

| 属性图 | RDF 形态 |
| --- | --- |
| 节点标签 | `?s rdf:type ?t` |
| 节点属性 | 字面量三元组 |
| 关系 | 资源三元组 |
| 关系自身属性 | 用 `urn:bkn:Relationship` 具体化表达，同时保留一条直接三元组 |

“关系自身属性”同时保留直接三元组，是为了让外部 SPARQL 工具仍然能直接查关系；具体化表达用于保留平台需要的关系属性。

### 隔离方式

Jena 的隔离单位是**命名图**，不是“多起一套实例”：

| 做法 | 适用 | 说明 |
| --- | --- | --- |
| 命名图（默认） | 一个数据集里一个本体一个命名图 | 平台自动分配 `urn:ontology:<本体 id>`，同一 Fuseki 上可并存多个本体 |
| 多 dataset | 按环境 / 租户再分一层 | 一个 Fuseki 下配多个 dataset，登记存储时选不同数据集 |
| 独立实例 | 资源或权限硬隔离 | 单起一套 Fuseki / TDB2；日常使用不需要 |

同一个“数据集 + 命名图”不能登记两个本体存储，否则两边会互相看见数据，发布时互相清空。平台会以 `409` 拦下并说明怎么改。

### 容器部署的端点改写

容器里的 `localhost` 是容器自己。如果库里登记的是 `http://localhost:3030/ds`，而 Fuseki 在宿主机上，平台默认通过 `GRAPH_ENDPOINT_HOST_ALIAS=localhost=host.docker.internal` 改写；远端 Fuseki 直接登记真实可达地址，或在环境变量里覆盖别名。

## 12.5 发布与原子替换

`GraphStore.replaceGraph()` 的硬性契约是：失败时图数据必须保持替换前的状态。能力由 `capabilities.atomicReplace` 声明，发布流程据此决定失败提示。

| 后端 | 原子替换实现 |
| --- | --- |
| Apache Jena | 单个 SPARQL Update 完成“清空 + 插入”；超过 5000 条三元组时先写影子命名图，再一个请求 `CLEAR + ADD + DROP` 原子切换 |
| 内置类型图 | PostgreSQL 单行 UPSERT 原子替换发布视图，查询只见旧版本或新版本；Graphology/N3.js 视图按需重建 |

并发控制：

- 进程内发布队列；
- PostgreSQL advisory lock。

两层串行保证多实例部署时不会并发替换同一个本体存储。

## 12.6 图存储相关操作

入口：**设置 → 图引擎配置**。

| 操作 | 说明 |
| --- | --- |
| 测试连接 | 按保存的连接发起连通性测试 |
| 查看运行时 Schema | 读取图库中已有的类型与统计 |
| 新建 Jena 连接 | 填端点、数据集、可选凭据、命名图 |
| 编辑 / 删除连接 | 修改连接信息或删除登记；图库数据与平台版本不一起删除 |
| 清空图数据 | 二次确认后清空图库节点与关系；平台版本与快照保留 |
| 重置本体存储 | 重置该存储的运行时状态 |

相关接口：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` / `POST` | `/api/targets` | 列表 / 登记图引擎连接 |
| `PATCH` / `DELETE` | `/api/targets/:targetId` | 更新 / 删除 |
| `GET` | `/api/targets/:targetId/schema` | 运行时 Schema |
| `POST` | `/api/targets/:targetId/test` | 连接测试 |
| `GET` / `POST` | `/api/targets/:targetId/clear` | 查看清空预览 / 清空图数据 |
| `POST` | `/api/targets/:targetId/reset` | 重置存储状态 |

## 12.7 多本体与多实例

### 多本体

- 内置图：受管目标 id 隔离；
- Jena：命名图隔离，一个本体一个命名图；
- 同一数据集 + 命名图不能登记两个本体存储；
- 新建本体时可选择内置图或已登记的 Jena 连接。

### 多实例

平台版本数据在 PostgreSQL 中，所以多实例部署不需要共享文件卷：

- 所有实例连同一个平台库；
- 发布通过 advisory lock 串行；
- 实例本身无状态；对象索引与列画像也在平台库；
- 旧磁盘快照目录只在一次性迁移时使用，不参与日常运行。

## 12.8 扩展新后端

新增图后端的三步：

1. 在 `GraphTargetKind` 登记类型，并在 `GRAPH_TARGET_KINDS` 补连接表单元数据；
2. 新增实现 `GraphStore` 的适配器；
3. 在注册表中注册。

API 路由、版本发布流程和界面组件无需改动。未来的候选后端（如 NetworkX、Elasticsearch 等）保持同一模式；文档里把“规划中”与“已支持”分开写。

## 12.9 迁移与切换后端

图后端是投影，切换后端的原则是“从平台版本重新发布”：

1. 确认平台库中的版本记录完整；
2. 在新图存储上登记一个连接；
3. 用本体包迁移定义，或直接把现有本体改绑新存储；
4. 重新发布；
5. 核对运行时 Schema、对象数和关系数；
6. 旧图存储确认无人使用后再清理。

注意：

- 本体包只带结构，不带实例；如果实例只在旧图存储里，需要先确认来源或快照里是否有对应数据；
- 平台版本快照包含实例数据，可用于历史激活和重新发布；
- 直接改图库数据不会改平台版本；下次发布会按快照整图替换，手工改动会丢。

## 12.10 当前限制与演进方向

- 内置图适合类型层和少量实例，不是海量对象存储。
- Jena 的强约束能力为 false；必填 / 唯一等规则由平台校验层负责，不由图库硬约束。
- 发布是整图替换，不是增量发布；数据量大时发布耗时会上升。
- 对象索引当前在 PostgreSQL；数据量上百万后可以考虑独立搜索后端，但对象服务接口不变。
- 没有 embedding 提供方；向量检索能力有底座但暂不可用。
- 查询 DSL 已支持关系 JOIN（外键式 / 中间表式）与同一数据资源内的多来源 MDO JOIN；跨数据资源 JOIN 仍不支持；影子对拍工具已实现，真实业务问题集对拍与验收待完成。详见查询 DSL 附录。
