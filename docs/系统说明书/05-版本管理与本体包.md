# 第 5 章 · 版本管理与本体包

## 5.1 版本是什么

平台里的一个版本不是“只存类型定义的历史”，而是一份**不可拆分的完整快照**：

| 内容 | 说明 |
| --- | --- |
| 本体定义 | 对象类型、关系类型、接口、指标、动作、规则、概念分组 |
| 实例快照 | 对象节点、关系边与画布位置 |
| 版本元数据 | 版本号、状态、对象数、关系数、内容哈希、发布时间 |
| 概念检索索引 | 从定义拍平出来的一行行概念，供 `search_schema` 检索 |

版本记录统一存在平台库 `ontology_platform.ontology_versions`：

- `definition` 是 jsonb，一行一个版本的完整定义；
- `snapshot` 是 jsonb，一行一个版本的实例快照，历史激活时用它整图回滚；
- 版本元数据在同行其它列；
- 图库（内置图或 Jena）里存的是**发布后的投影**，不是定义本身；
- 磁盘上不再有本体版本数据；旧部署的 `.data/ontology-versions` 只在一次性迁移时读取。

## 5.2 版本状态与生命周期

版本有三种状态：

| 状态 | 含义 |
| --- | --- |
| `DRAFT` | 草稿，可编辑；同一时间一个本体存储最多存在一个草稿 |
| `PUBLISHED` | 当前已发布版本，问答和 MCP 只认它 |
| `ARCHIVED` | 历史版本，可查看、可激活（前提是它有实例快照） |

标准生命周期：

```text
创建草稿
  → 编辑草稿（定义 + 对象 + 关系 + 画布位置）
  → 建模体检（建议）
  → 发布校验（门禁）
  → 发布：整图替换 + 版本状态切换
  → 需要回滚时：激活历史版本
```

### 创建草稿

- 优先复制当前发布版本；没有发布版本时复制空白定义；
- 从图库导出当前数据形成实例快照；
- 此后所有写操作都要求携带草稿的 `versionId`。

### 编辑草稿

- 类型、对象、关系、属性、画布位置的修改只影响这条草稿记录；
- 发布之前，已发布版本继续对问答、MCP 和只读查询生效；
- 草稿可以反复保存、校验、查看体检结果，不要求一次成型。

### 校验

校验同时检查定义和实例：

- 必填 / 唯一属性；
- 实例类型与关系类型的端点契约；
- 关系两端引用是否合法；
- 补充数据来源的连接键；
- 接口的属性、关系、动作约束；
- 指标与动作规则的硬性错误。

校验结果分“违规”和“提醒”；违规会阻断发布，提醒只提示。

### 发布

发布由后端图存储适配器执行**整图替换**，要求原子：

- 成功：新版本整体生效，旧发布版本归档；
- 失败：图数据保持发布前的状态，版本仍是草稿；
- 图库失败但索引已经写入：平台会把版本留在草稿，并给出“重新发布以恢复一致”的提示。

发布成功后，平台会：

1. 将新版本状态改为 `PUBLISHED`，记录发布时间；
2. 将旧发布版本改为 `ARCHIVED`；
3. 重建概念检索索引；
4. 同步对象索引（按发布快照物化）；
5. 对账平台创建的约束和索引。

### 激活历史版本

- 只有存在实例快照的历史版本可以激活；
- 存在草稿时禁止激活历史版本，必须先发布或删除草稿；
- 激活走与发布相同的整图替换流程；
- 旧归档版本若没有实例快照，不能用当前图数据伪造历史状态，会明确报错。

## 5.3 发布的原子性与并发

`GraphStore.replaceGraph()` 有硬性契约：**失败时图数据必须保持替换前的状态**，由 `capabilities.atomicReplace` 声明能力。

| 后端 | 原子替换实现 |
| --- | --- |
| Apache Jena | 单个 SPARQL Update 完成“清空 + 插入”；超过 5000 条三元组时先写影子命名图，再用一个请求 `CLEAR + ADD + DROP` 原子切换 |
| 内置类型图 | PostgreSQL 单行 UPSERT 原子替换发布视图；Graphology/N3.js 视图按需重建 |

同一个本体存储的发布在两层串行：

1. 进程内发布队列；
2. PostgreSQL advisory lock。

因此多实例部署时也不会出现两个实例同时替换同一个本体存储。

发布过程会写三条审计：

| 审计动作 | 时机 |
| --- | --- |
| `VERSION_PUBLISH_STARTED` | 发布开始，含后端类型与 `atomicReplace` 能力 |
| `VERSION_PUBLISHED` / `VERSION_ACTIVATED` | 发布/激活成功 |
| `VERSION_PUBLISH_FAILED` | 发布失败，含 `graphReplaced`，用于判断图是否已被改动 |

## 5.4 稳定标识

- 图库的 `elementId()` 在重新导入后会变化，不能作为长期引用；
- 快照为对象和关系分配稳定 UUID；
- 发布时 UUID 只在事务内用于连边，完成后从节点属性中移除，不污染业务属性；
- 对象身份在对象服务层优先使用“对象类型 + 业务主键”；
- 导出到本体包时所有 id 会重新分配，**不要用 id 做跨环境引用**。

## 5.5 本体包：导出与导入

版本快照是平台内部形态，id 都是本机 UUID。要在人和环境之间传播，使用**本体包**：一个单文件 `.ontology.json`。

### 5.5.1 本体包结构

```json
{
  "format": "ontology.bundle",
  "formatVersion": 1,
  "exportedAt": "2026-09-14T06:58:39.413Z",
  "generator": { "name": "ontology-management", "version": "0.1.0" },
  "ontology": {
    "identifier": "m3-1789283543253",
    "name": "客户账务网络",
    "description": "...",
    "color": "",
    "tags": ["m3"]
  },
  "statistics": {
    "objectTypes": 3,
    "relationTypes": 1,
    "actionTypes": 0,
    "rules": 0,
    "objects": 3,
    "relationships": 0
  },
  "dataSources": [
    {
      "id": "<导出端的数据资源 id>",
      "kind": "ORACLE",
      "host": "39.164.136.34",
      "port": 1251,
      "databaseName": "orcl",
      "schemaName": "GISTOOLS"
    }
  ],
  "definition": {
    "groups": [],
    "interfaces": [],
    "metrics": [],
    "entityTypes": [],
    "relationshipTypes": [],
    "actionTypes": [],
    "rules": []
  }
}
```

### 5.5.2 三条不变量

1. **`definition` 就是平台内部的 `OntologyDefinition`。** 不另造一套形状，避免“两份定义各说各话”。
2. **包里绝不写凭据。** 数据资源只记连接坐标（类型 / 主机 / 端口 / 库 / 模式），导入端按坐标匹配本机已登记的资源。
3. **导入一定停在草稿。** 别人的文件不能绕过版本边界；校验和发布仍走平台流程。

### 5.5.3 导出

入口：**总览 → 本体卡片 → 导出**，或“本体建模”页头。

- 导出当前已发布版本的结构定义；
- 输出单文件 `.ontology.json`；
- 不包含实例数据，不包含业务库账号密码。

### 5.5.4 导入

入口：**总览 → 导入**，支持平台本体包与 bkn 知识网络。

导入时平台会做三件事：

| 步骤 | 行为 |
| --- | --- |
| 换 id | 包里的 UUID 全部重发新号，接口与实现、关系端点、动作作用域、规则条件一起改写 |
| 接回数据资源 | 按 `kind + host + port + 库 + 模式` 五项全等匹配；只差模式时放宽一次并提醒；找不到就留空并点名是哪个对象类型需要重新选表 |
| 建本体 + 写草稿 | 本体名可改；标识被占用就自动加序号；导入后对象数是 0，因为实例不在包里 |

导入不会静默丢绑定。接不上的来源会在弹窗里列出，用户到对应对象类型里重新选表即可。

### 5.5.5 bkn 知识网络导入

导入入口同时识别 bkn-foundry 导出的知识网络（`module_type: knowledge_network`）。服务端先把它转成标准本体包，再走同一条导入路径。

转换能搬的都搬：

- 对象类型、关系类型、概念域分组、指标；
- 属性带 `display_name`（中文名）与 `comment`（说明）；
- `primary_keys` 落到来源绑定的主键上；
- 没有数据来源的对象类型，主键改记成“必填 + 唯一”，并给提醒。

装不下的会**逐条列出**，不会静默丢，例如：

- 关系的连接规则 `mapping_rules`；
- 平台不认识的属性类型；
- bkn 只写 `SCHEMA.TABLE`、不带数据库连接的来源——导入后需要自己选一次数据资源。

### 5.5.6 命令行导入

大文件（几十个对象类型、上千个属性）建议用命令行，避免浏览器上传超时或内存压力。

```bash
# 先干跑：只解析、不落库，看清文件里有什么、会丢什么
node scripts/import-ontology.mjs "你的文件.json" --dry-run --email admin@example.com --password '******'

# 正式导入：默认停在草稿
node scripts/import-ontology.mjs "你的文件.json" --storage-target "内置类型图" --name "客户账务网络 v6"

# 一步到位：导入并发布（会真正重建图数据）
node scripts/import-ontology.mjs "你的文件.json" --publish
```

常用参数：

| 参数 | 说明 |
| --- | --- |
| `--dry-run` | 只解析和规划，不落库 |
| `--email` / `--password` | 登录账号；也可用环境变量 `ONTOLOGY_EMAIL` / `ONTOLOGY_PASSWORD` |
| `--token` | 直接给平台会话令牌，跳过登录 |
| `--storage-target` | 指定本体存储名；省略时若只剩一个未占用存储会自动使用 |
| `--name` | 导入后的本体显示名 |
| `--publish` | 导入后直接发布；默认不发布 |

导入响应带有 `timings`（解析 / 规划 / 绑定 / 建快照），慢的时候能一眼看出慢在哪。

三种输入都支持：bkn 知识网络、平台 `ontology.bundle`、技能工具导出的本体包。

## 5.6 版本与包的边界

| 问题 | 答案 |
| --- | --- |
| 本体包能替代版本快照吗？ | 不能。包只带结构；版本快照还包含实例、画布位置和内容哈希 |
| 导出的包能在另一台机器直接发布吗？ | 可以导入并发布，但数据资源必须在本机重新绑定；实例数据不会带过去 |
| 历史版本能回滚实例吗？ | 有实例快照的历史版本可以激活并整图替换；没有快照的旧归档版本不行 |
| 删图库数据会删版本吗？ | 不会。图库是投影，版本与快照在平台库 |
| 发布失败会留下半成品吗？ | 后端声明 `atomicReplace=true` 时不会；不支持的旧后端会明确提示风险 |
| 两个实例同时发布同一本体存储会怎样？ | 进程内队列 + PostgreSQL advisory lock 串行化，不会并发替换 |
| 导入时会保留原 id 吗？ | 不会，全部重发新 id；跨环境引用一律用名字或重新查 id |

## 5.7 操作手册摘要

### 发布一个新版本

1. 打开本体建模，确认页面显示当前版本与草稿状态。
2. 编辑模型；每次改动自动保存到草稿。
3. 点“建模体检”，按 WARN / INFO 逐条处理。
4. 点“校验”，处理所有违规。
5. 点“发布”，等待图重建和索引同步完成。
6. 到实例图谱、对象页、智能问答分别验证。
7. 在“设置 → 审计记录”确认发布记录。

### 回滚到历史版本

1. 确认当前没有未发布草稿；有草稿先发布或删除。
2. 打开版本记录，选择目标历史版本。
3. 确认它有实例快照。
4. 点“激活”，等待整图替换完成。
5. 用对象页和问答验证；激活记录写审计。

### 导出与交付

1. 在本体卡片或建模页头点“导出”。
2. 得到 `.ontology.json`。
3. 在目标环境导入，停在草稿。
4. 处理数据资源绑定提醒。
5. 校验、发布、验证。

## 5.8 当前限制

- 一个本体存储同时只能有一个草稿。
- 历史激活不是“合并”，而是用历史快照整图替换；不会保留当前实例的增量修改。
- 本体包不携带实例数据，也不携带凭据；跨环境迁移实例需要另行物化或从业务库回源。
- 旧归档版本如果没有实例快照，无法激活。
- 版本快照内容哈希用于完整性校验；如果快照被外部改写，读取或激活会失败。
- 发布过程中的对象索引同步失败不会回滚已替换的图数据，而是把版本留在草稿并提示重新发布，以确保数据最终一致。
