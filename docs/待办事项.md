# 项目待办事项（Backlog）

这个文件是项目唯一的详细待办清单。`AGENTS.md` 只说明“有 Backlog、Backlog 在哪里、条目必须怎么写”，不在这里展开具体事项。

## 记录规则

每个待办条目至少写清：

- **编号**：稳定引用，不随优先级变化
- **状态**：未开始 / 进行中 / 部分完成 / 已完成待验收 / 已关闭
- **前因后果**：为什么会出现这个问题，为什么现在要做
- **功能作用**：做完以后系统获得什么能力，用户 / 模型 / 运维得到什么
- **设计细节**：协议、数据结构、边界、关键取舍、依赖关系
- **已完成**：已经落地并验证过的部分
- **未完成**：还缺什么，下一步具体要做什么
- **验收标准**：怎样才算真正完成
- **影响范围**：涉及哪些模块、接口、工具、文档
- **关联文档**：系统说明书、历史决策、ADR、提交或测试位置

原则：**待办不是一句 TODO；没有前因后果和验收标准的条目，不算有效条目。**

用户说「先不做，后面有需要了再做」时，同样按上面十项写全，并在 `AGENTS.md` 的「待办事项（Backlog）位置与规则」一节登记一条指针 —— 目的是几个月后回来能直接开工，所以**细节记得够全**比条目写得短重要。

### B-VIRTUAL-OBJ-01 虚拟实例查询与 ODS 源表层

- **状态**：本次改造范围已实现；服务契约与浏览器交互持续回归。历史采集按区间快照交付，不承诺跨源事务一致；千万行性能指标需在有权限的环境另做基准。
- **前因后果**：每个版本把所有对象写入 ClickHouse 会让存储量按版本数线性增长，切换版本还需要重写或清理整版数据；大数据量下成本高、速度慢，也容易出现快照/物化/版本混用。
- **功能作用**：版本只保存对象类型、属性映射、主键和关系键；查询时把业务数据实时投影为对象实例。普通版本切换不再复制整版实例，CH 只作为可选分析/搜索加速层。
- **设计细节**：
  - 新对象类型默认 `FEDERATED`；`AUTO` 虚拟优先、显式点名索引才读索引；`INDEXED` 只读物化索引。
  - 对象查询流程：当前版本定义 → 解析对象类型/主键/来源 → 下推过滤、排序、分页、字段裁剪 → 数据源执行 → 行映射成 `ObjectRecord`。
  - 关系查询按关系类型两端键映射实时生成；多跳必须有跳数/数量上限。
  - CH ODS 一张源表一份，不按版本复制；只同步映射需要的列，并记录 `_source_id`、`_source_updated_at`、`_sync_batch`、`_is_deleted`。
  - 可选 `INDEXED` 类型记录 `definition_version_id` / `definition_hash` / `mapping_hash`；版本定义变化后索引失效。
  - 普通版本切换不创建 CH 全量副本；精确历史回放使用压缩快照或源库时间维度。
- **已完成**：对象类型默认策略改为 `FEDERATED`；`AUTO` 改为虚拟优先；对象列表查询下推、多来源批量补齐、复合主键图谱邻域和有界多跳；ODS 配置与任务落平台库；列裁剪、复合主键、全量/增量、手动全量校准、自动定时校准、取消、重启恢复；全量影子表原子替换、增量水位追平与真实 ClickHouse 契约；对象来源支持 `AUTO / DIRECT / ODS`；查询 DSL / `run_query` 支持完整 ODS 过滤、聚合、MDO 与关系 JOIN，并按本次查询实际引用列校验裁剪。
- **收尾实现**：图谱提供 1～3 跳显式选择；PG 版本编辑层保存源基线/本地对象/删除标记并提供恢复源数据；物化定义与映射指纹驱动读前失效；独立历史采集任务按页 gzip 存 PG 并提供冻结定义回看、删除、取消与预热；OpenSearch 接入评估结论为暂不新增部署，未来独立 SearchIndex 端口扩展。
- **后续验证与边界**：千万行吞吐/延迟基准及跨源事务一致时点并非当前验证结论；增量取消有已写入页时不能宣称镜像完全没变化。详细范围与验证命令见 `docs/虚拟实例改造验收.md`。
- **验收标准**：同一源表在 CH 只存一份 ODS；切换 v1/v2 时 CH 行数不因版本增加；对象列表只返回当前版本映射属性；版本切换后查询立即使用新定义；未显式物化的类型不读旧索引；清晰区分“当前源数据 + 旧定义”和“历史时点快照”。
- **影响范围**：`instance/object-service`、`datasource`、`query-dsl`、`version-publication`、`infrastructure/object-index`、对象页/图谱页、系统说明书。

### B-QUERY-DSL-05 本体 SQL 表层（SQL 形状的查询语法）

- **状态**：第一版已落地（2026-10-14）：解析 + 绑定 + 执行入口 + `run_query` 工具改用本体 SQL；表达力扩展与真实业务验收待做
- **前因后果**：JSON DSL 对模型不友好（LLM 的训练数据里 SQL 极多、JSON 结构化查询极少），一次生成正确率低、错误难懂；要表达"按天分组 + 窗口 / 子查询"这类分析，只能不断发明新的 JSON 结构。用户 2026-10-14 拍板：**表层用 SQL 形状、内核仍是本体语义** —— 通用性在表层，表达力在 IR，正确性在校验，三件事分开做。
- **功能作用**：模型和人用熟悉的 SQL 语法问数（对象类型当视图、属性当列、指标当函数），平台照旧保证"不跨数据资源乱 join、基数放大 fail-closed、指标口径统一、只读"；`run_query` 的入参从"必须写对 JSON DSL"变成"写一句本体 SQL"。
- **设计细节**：
  - 两种表层产出**同一份 `QueryDsl`**：本体 SQL 走 `parseOntologySql`（文本→语法树，不认识本体）→ `bindOntologySql`（语法树 + 本体 → QueryDsl，判属性/指标、判别名、判 kind）→ 与 JSON DSL **共用** resolve → 编译 → 只读执行。**工具只暴露本体 SQL**，JSON DSL 只留在代码里。
  - 代码在 `src/lib/query-dsl/sql-surface/`（`parse.ts` / `bind.ts` / `index.ts`）；执行入口 `executeOntologySql`。
  - 子集：SELECT / FROM 对象类型 [AS 别名] / [[LEFT] JOIN 关系类型 [AS 别名] [FORWARD|BACKWARD|BOTH]] / WHERE / GROUP BY / ORDER BY / LIMIT；`:名字` 参数；`LABEL(属性) = '标签'` 走枚举标签；LIKE 只收 `%..%` / `..%` / `%..`。
  - 不支持（一律如实报错）：SELECT *、子查询、CTE、UNION、窗口函数、任意函数、跨数据资源 join。
- **已完成**：词法/语法分析（中文标识符、三种引号、注释、`>=` / `<>` 等）；语义绑定（裸名字判属性 vs 指标、别名表含对象类型名与关系类型名、kind 自动判定、ORDER BY 认输出列名与属性）；与既有 resolve/编译器打通（测试断言：编译出的物理 SQL 与 JSON DSL 完全等价 —— 同表、同列、同绑定参数）；`run_query` 工具重设计（**只收本体 SQL**：`sql` 必填 + `parameters`；不再暴露 JSON DSL 入参）+ 提示词与 MCP 标题改口径 + MCP 调试页「自动填参」给本体 SQL 模板；21 条单测（含"假连接器一路走到执行"）。
- **未完成**：① 表达力扩展（表达式 → 窗口函数 → 子查询 → 集合运算），**扩 IR 而不是收下 SQL 语法**；② 真实业务问题验收（拿现网问题写成本体 SQL 跑一遍，与 `run_sql` 参考结果对拍）；③ 前端的查询入口（对象页 / 本体建模里给一个"写本体 SQL"的面板，现在只有 Agent 能用）；④ `run_query` 出厂默认仍是关闭（口径未变，要不要改由用户定）；⑤ 与影子对拍工具（`shadow.ts`）打通，把本体 SQL 纳入对拍样本。
- **验收标准**：一批真实问题用本体 SQL 与等价的 JSON DSL 跑出的结果逐格一致；编译出的物理 SQL 与手写参考 SQL 结果一致；不支持的语法返回带出路的错误；基数放大、跨数据资源、只读这三条保证与 JSON DSL 完全一致。
- **影响范围**：`src/lib/query-dsl/sql-surface/*`、`src/lib/query-dsl/execute.ts`、`src/lib/reasoning/tools/registry.ts`（run_query 描述与入参）、`src/lib/reasoning/tools/dispatch.ts`、`src/lib/reasoning/mcp.ts`、`src/lib/reasoning/prompt.ts`、`tests/lib/query-dsl-sql-surface.test.ts`、`docs/系统说明书/查询DSL.md`、`AGENTS.md`。
- **关联文档**：`docs/系统说明书/查询DSL.md`（2.3 本体 SQL）、`AGENTS.md`（查询表层口径）。

### B-ACTION-WRITEBACK-01 动作写回业务库

- **状态**：第一版已落地（2026-10-13），后续能力按下面「未完成」逐个排
- **前因后果**：动作此前只写**平台草稿快照**，业务库里一个字节都不动 —— 「动力模型」立不住，也回答不了"这个动作到底改没改生产数据"。用户口径是「动作是平台里唯一的业务写入口」，所以动作必须能真的落到源表，而且**每一次写都要留下可核对的痕迹**。
- **功能作用**：动作在写草稿快照之外，可以**按对象主键改业务库的那一行**：写哪张表、按什么键、改哪几列在点执行之前就能看到；写完给「旧值 → 新值」；写不回去的逐条说明原因与出路。
- **设计细节**：
  - 计划与执行分家：计划是纯函数（`src/lib/ontology/action-writeback.ts`：`actionWritebackDiffs` / `planActionWriteback` / `describeWritebackPlan`，浏览器可用），执行在 `src/lib/instance/object-service/writeback.ts`，SQL 全在数据源连接器的 `updateRows`（`src/lib/datasource/sql.ts`）。
  - 用**前后对拍**算改动（不是读动作定义）：同一处属性被多步改到、或被规则拦住，都以"最后真的变了什么"为准。
  - 只支持**主来源 = 表 / 视图**、**UPDATE 已有行**、**按键命中恰好一行**；主键列不能改。
  - 契约在 `DataSourceConnector.updateRows`（`DataSourceRowUpdate` / `DataSourceWriteResult`）：只有键列 / 赋值列 + 值，没有 SQL 字面量；语句由 ORM QueryBuilder 生成、值走绑定参数。
  - 接口：`POST /api/ontology/:versionId/actions` 带 `writeback`（默认 false）；响应 `writeback` 四态 `OFF / PREVIEW / APPLIED / REFUSED`；有写不回的即 `409` 且整批不执行。

- **已完成**：契约 + Oracle / PG / MySQL 共用实现（写前按键回读确认唯一、写后回读确认生效、确认不到就回滚）；纯函数计划与单测；接口与审计留痕（含实际语句）；动作页「运行」阶段的写回开关与写回报告（计划 / 结果 / 拒绝理由）、「决策」记录「已写库 N 处」状态牌；真库契约用例 `tests/lib/datasource/sql-writeback.contract.test.ts`（Oracle 测试环境实测：原地写同值成功、键 0 行拒绝、键多行拒绝）。
- **未完成**：① INSERT / DELETE（动作新建对象落库、按对象删源行）；② 一次动作改**多行**与跨表事务；③ 取数口径（`DERIVED`）来源的写回 —— 要先有落地层 `ods_*`，写完重算口径；④ 动作级独立权限（现在复用 `instance.write`；Palantir 是独立的 action execution 权限）；⑤ 写回的**提交校验**（submission criteria）与审批流；⑥ Agent / MCP 侧执行动作（`list_actions` 出厂关闭，也还没有 `run_action` 工具）；⑦ 从对象详情直接触发动作时的写回入口（现在只在动作工作台）。
- **验收标准**：任选一个绑了真实业务表的对象类型，配一个「改属性」动作：干跑能看到写回计划；执行后业务库那一行的值真的变了，决策记录与审计能查到「旧值 → 新值」与实际语句；键不唯一 / 主键缺失 / 口径来源三种情况下都不写库并给出可执行的下一步。
- **影响范围**：`src/lib/datasource/sql.ts`（`updateRows`）、`src/lib/datasource/types.ts`（契约）、`src/lib/ontology/action-writeback.ts`、`src/lib/instance/object-service/writeback.ts`、`src/app/api/ontology/[versionId]/actions/route.ts`、`src/components/action-studio.tsx`、`src/lib/shared/client/api-client.ts`（失败也带 payload）、系统说明书第 7 / 13 章、`AGENTS.md` 的「动作写回业务库」一节。
- **关联文档**：`docs/系统说明书/07-动作与规则.md`（7.5 写回业务库）、`docs/系统说明书/13-接口与集成参考.md`（动作请求体）、`AGENTS.md`（写回口径）。

### B-QUERY-DSL-01 查询 DSL 中间层与 run_query

- **状态**：部分完成，已开放基础能力，真实业务验收待做
- **前因后果**：智能问答原先直接依赖 `run_sql`，模型必须理解物理表名、列名和 SQL，容易产生多次探查、日期 / 码值口径漂移、跨表重复计数和难以审计的问题。需要把“用什么逻辑概念回答”和“落到哪个数据库怎么执行”分开。
- **功能作用**：让模型用对象类型、属性、关系类型、指标生成稳定 DSL；由后端统一校验、规划、编译和执行。这样既保留 SQL 能力，又让常见问数不依赖模型手写 SQL。
- **设计细节**：DSL v1 使用 `version / kind / from / relationships / where / select / group_by / order_by / limit / parameters`；内部经过 `LogicalPlan/AST`，再编译为 PostgreSQL / MySQL / Oracle SQL。关系 JOIN 必须来自本体关系类型和 `planLinkSource()`，不允许模型提供连接条件。指标固定过滤优先编译为条件聚合。跨数据资源和基数不安全的聚合默认拒绝。
- **已完成**：DSL Schema、Resolver、AST、SQL 编译器、只读执行器；records / aggregate；指标展开；枚举标签；参数绑定；外键式与中间表式关系 JOIN；forward / backward；MDO 补充来源 JOIN；关系基数保护；跨数据资源拒绝；操作符与聚合类型校验；与参考 SQL 的影子对拍工具；`run_query` 已开放但出厂默认关闭（打开后模型可用）；`run_sql` 保留为兜底和排障工具。
- **未完成**：用真实业务问题和真实数据资源跑影子对拍，统计 DSL 生成成功率、编译成功率和结果一致率；根据对拍结果补 Prompt、错误提示和字段级能力；灰度上线后观察真实问答的 DSL 命中率与失败分布。
- **验收标准**：一批真实问题在 DSL 与参考 SQL 上结果逐格一致；不支持的能力返回明确错误；聚合不会因关系放大重复计数；`run_sql` 仍可用且不会被删除。
- **影响范围**：`src/lib/query-dsl/`、Agent 工具目录、提示词、MCP 工具列表、系统说明书查询 DSL 章节。
- **关联文档**：`docs/系统说明书/查询DSL.md`。

### B-QUERY-DSL-03 跨数据资源查询

- **状态**：未开始
- **前因后果**：当前 DSL 要求一次查询的物理表来自同一数据资源。跨库对象或关系一旦被问到，只能拒绝，无法给出结果。
- **功能作用**：支持跨数据源的受控联邦查询或两阶段取数，让本体关系不因物理存储位置而中断。
- **设计细节**：优先做“单侧下推 + 结果归一化 + 受控内存 JOIN”，严格控制行数与内存；不能下推的查询明确标记为两阶段执行，禁止静默近似。
- **已完成**：跨数据资源关系的明确拒绝和错误码。
- **未完成**：规划器、跨源执行策略、行数 / 内存限制、权限和审计。
- **验收标准**：跨源关系在受控条件下可执行；超限或语义不等价时明确拒绝。
- **影响范围**：查询规划、数据资源连接器、执行器、权限与审计。
- **关联文档**：`docs/系统说明书/查询DSL.md`。

### B-SEC-01 对象级 / 属性级权限（行级 + 列级）

- **状态**：未开始。2026-10-11 记录，用户口径「先不做，但要把这些信息记录清楚，后面有需要了再做」→ **未获明确授权前不要实现**。
- **前因后果**：用户先问「Palantir 的权限到底是对象类型级还是对象级」，核官网后确认 Palantir 是**两层叠加** —— 资源层（对象类型 / 关系类型 / 动作类型的 schema）+ 数据层（对象与关系的行、列）。平台现在只有模块级 RBAC（13 个权限点），既没有 per-对象类型的资源 ACL，也没有对象级 / 属性级过滤，所以「同一个对象类型，不同人看到不同对象 / 不同属性」这类需求目前表达不了。
- **功能作用**：让同一个对象类型对不同人给出不同数据 —— 不同角色 / 部门只看得到自己有权的对象（行）与属性（列）。这是把平台从「功能级授权」推进到「数据级授权」的唯一路径，也是对 Palantir 两层权限模型的第一步对齐。
- **Palantir 官方口径（摘要，出处见「关联文档」四页）**：
  - 两层定义：**ontology resources**（对象类型、关系类型、动作类型的名称、属性名、数据类型、描述；**不含属性值与主键值**）与 **objects and links**（真实属性值 / 主键）。「能看这个类型」和「能看这个对象」是两件独立的事。
  - 资源层现在由 **Compass 项目权限**（项目 / 文件夹 / 角色）承担，取代了旧的 ontology roles 与「继承数据源权限」那套。
  - 看**类型**只需对象类型的 View 权限，**不需要**数据源 View；看**对象**需要对象类型 View **加上**数据访问权，两个都要。
  - 编辑同样是资源级：改**关系**要求「关系类型 + 两端对象类型」都有 edit 权限；改**动作**要求「动作类型 + 它编辑到的所有资源类型」都有 edit 权限。
  - 数据层有两条实现路径：
    1. **Object and property security policies**（官方推荐）：对象上配 object security policy（决定看得见哪些对象 = 行），属性上配 property security policy（决定看得见哪些属性 = 列）；与底层数据源解耦，配置简单、**近实时生效**，支持流式数据源与 Global Branching。**由动作创建、没有数据源的对象类型必须配 object security policy。**
    2. **受限视图 RV**：行级控制在数据集层配置，对象继承（官方原话大意：ontology objects inherit the granular permissions defined in the restricted view policy）。改对象属性**不会**改变 RV —— 官方例子：按 `Assignee` 列的组成员关系决定能不能看到这行，改了 `Assignee` 之后原组成员看不到这个对象了，但数据集里的行还在。代价是策略变更需要**重建 pipeline** 才生效；数据集在 Ontology 之外也被消费（例如 Code Workspaces）时 RV 仍然必需。
  - **只做读时拦截**：官方明确写了行 / 列粒度「filter what a user can read. These controls do not extend to downstream outputs or exports.」—— 不跟着下游输出 / 导出走。要保护下游（导出、派生数据集）得另外叠加 marking 或 CBAC。
- **我们的现状（2026-10-11 逐条核实过）**：
  - 权限点是代码常量：`src/lib/platform/permissions.ts` 的 `PERMISSIONS`（13 个，模块 × 动作）。角色 = 一组权限点；内置 admin / editor / viewer 不可改不可删，可自建角色；`effectivePermissions()` 对 `admin` 直接短路成「全部权限」。
  - 守卫覆盖：`src/app/api/**/route.ts` 共 68 个，61 个走 `requirePermission(...)`；7 个例外是公开或自鉴权 —— `auth/login`、`auth/logout`、`auth/password`（自己校验当前密码）、`bootstrap`（首次初始化）、`/api/mcp`、`/api/mcp/[ontologyId]`（认平台会话 JWT 或 `mcp_…` 令牌）、`/api/mcp/skills`（免令牌技能）。`tests/lib/authz-coverage.test.ts` 扫源码兜底：整个 route 漏守卫、或权限点拼错，都会红。
  - 资源层：有 `ontology.read / ontology.write / ontology.publish`，但粒度是**全平台模块** —— 拿到 `ontology.write` 就能改**任意**本体，库里没有任何 per-对象类型 ACL。
  - 数据层：**行级、列级都没有**。`src/lib/instance/object-service/index.ts` 的 `resolveObjectContext / getObject / queryObjects / ensureObjectInDraft` 都没有「调用者」入参；读路径（`/api/instances/entities`、`/api/instances/graph`、`/api/instances/neighbors`、`/api/objects`、`/api/object-search`）只校验 `instance.read` 然后读全量；`src/lib/instance/object-index/postgres.ts` 也没有按用户过滤。
  - 动作：执行由 `instance.write` 管；规则在 `src/lib/instance/action-engine.ts`（`runAction` / `evaluateRule`），但 `RuleContext = { nodes, relationships, refs }` **没有执行人** —— 规则只能比对象自身属性与邻域属性，表达不了「只有本人 / 本部门能改」。
  - 对外 MCP：**令牌不绑用户**。`src/lib/reasoning/mcp-endpoint.ts` 的 `authorization()` 认平台会话 JWT 或平台库里的 `mcp_…` 令牌；拿到令牌 + 工具开关放开，就有只读查询能力。工具开关两层：全局 `reasoning.toolPolicy` + 按本体覆盖 `reasoning.toolPolicy:<ontologyId>`（`src/lib/reasoning/tool-policy.ts`）。
  - 用户档案：`users` 表只有 `id / email / password_hash / role_id / disabled_at / created_at`（`src/lib/infrastructure/persistence/postgres/entities.ts` 的 `PlatformUserEntity`）—— **没有任何可被行过滤表达式引用的用户属性**（部门、组织、岗位都没有）。这是做行级过滤的前置缺口。
- **设计细节（将来要做时的最小可用形态，尚未评审）**：
  1. **行过滤表达式挂在对象类型上**（对齐 Palantir 的 object security policy）：一个表达式，可引用对象属性 + 执行人属性，例如 `owner_id = :user.id`、`dept_code = :user.dept`；语法复用现有规则条件那套（property + operator + compareValue），不要另造一门 DSL。
  2. **一处注入、所有读路径共用**：实例列表、实例图谱、neighbors、对象检索（索引与回源）、动作的 subject 解析（`resolveObjectContext` / `ensureObjectInDraft`），以及模型侧的 `query_object_instance` / `query_instance_subgraph`（这两个工具出厂默认关，做的时候要一起接上）。
  3. **列级**：属性上挂「可见角色」（或权限点），序列化对象时按调用者掩码；先做「整列不可见」，不做值级掩码。
  4. **用户属性是前置**：`users` 加 jsonb `attributes`（部门 / 组织 / 岗位…），或引入用户组表；表达式引用 `:user.*`。没有这一步，行过滤只能引用对象自身的属性。
  5. **只做读时过滤**：不把 ACL 写进数据、不改索引结构（索引表照存全量，读时按表达式过滤）—— 与 Palantir 的 read-time enforcement 一致，且比 RV 轻（RV 要重建 pipeline）。
  6. **边界**：导出 / 下游不继承（与 Palantir 同样的限制，导出侧要另加校验）；`admin` 仍短路全权；**没配表达式的类型保持「谁都可见」**（与现状一致，避免上线即锁死）；动作的可见性（HIDE 规则）接同一套过滤。
  7. **本条目暂不做**：per-对象类型 ACL（资源层细粒度）与 marking / CBAC 分级 —— 等行级闭环跑通再谈。
- **已完成**：无（本条目只记录信息，未改任何代码）。
- **未完成**：设计评审、排期，以及全部实现与验证。
- **验收标准**：
  - 同一个对象类型，两个角色 / 用户属性不同的用户，实例列表与图谱只返回各自可见的对象；
  - 按主键直取（`/api/instances/entities/[elementId]`）、对象检索、回源取数都取不到不可见的对象；
  - 不可见属性不出现在任何读接口与模型工具的结果里；
  - `admin` 与「没配策略的类型」的行为与现在一致；
  - 每条读路径都有注入单测；`docs/系统说明书/`（权限相关章节、09-智能问答、13-接口与集成参考）同步更新。
- **影响范围**：`src/lib/platform/permissions.ts`（可能新增权限点）、`src/lib/platform/db`（users 属性 + 迁移 + 表 / 字段注释）、`src/lib/instance/object-service`、`src/lib/instance/object-index`、`src/lib/instance/action-engine.ts`、`src/app/api/instances|objects|object-search|ontology`、`src/lib/reasoning/tools`（实例工具）、`src/components`（对象类型编辑面板加行过滤表达式、用户管理加属性）、`docs/系统说明书`。
- **关联文档**：Palantir 官网四页 —— `object-permissioning/overview`、`managing-object-security`、`configuring-rv-access-controls`、`ontologies/ontology-permissions`；`docs/系统说明书/13-接口与集成参考.md`、`docs/系统说明书/09-智能问答.md`；本文件 `B-QUERY-DSL-03`（跨数据资源查询）与 `B-KNOWLEDGE-01`（知识库融合）都提到「权限」，做的时候要一并考虑（跨源查询的行过滤要在执行器里注入同一套表达式）。

### B-OBJ-IDX-01 对象索引后端换 ClickHouse（列存对象存储）

- **状态**：**第一版已实现（2026-10-11）**。选型与落地口径都已按用户决定执行：ClickHouse 列存 + 中间层 + 删掉 PostgreSQL 的索引表。
- **前因后果**：对象实例的数量会远大于本体定义，现有对象索引落在 PostgreSQL 的 `object_entries`（`tsvector` 全文 + `pg_trgm` 中文子串 + `jsonb` 过滤 + `pgvector` 向量，见 ADR 0018 与本文件 S1–S3），量级上去以后行存的写放大、聚合与过滤会先顶住。Palantir 的答案是把对象索引放进**专用对象数据库**（OSv1 = Phonograph、OSv2 = Funnel + 专用对象数据库），并且官方明确「索引数据是 ephemeral、权威在数据源」—— 我们要的是同一个形态，只是产品换成开源自托管的一档。
- **选型核对（为什么是 ClickHouse）**：① 对象属性重复度极高（类型 / 区域 / 状态 / 码值），列存压缩比通常 5–10 倍；② 点查 + 过滤 + 聚合同一套引擎，`WHERE object_type=… AND area_code IN (…)` 是它的主场；③ `ReplacingMergeTree` 按对象键去重，天然匹配现在的「按对象键 upsert」语义；④ 按对象类型分区 + 主键排序就能水平扩。许可证：ADR 0018 当初否掉 Elasticsearch 是因为 SSPL / ELv2 / AGPLv3 对闭源分发有风险，**ClickHouse 是 Apache-2.0，不踩这条**；将来若为搜索再引 OpenSearch / ES，许可证问题要重新评估。Doris / StarRocks 是同档替代（国产化与运维偏好时）。
- **功能作用**：对象量级从千万级推到亿级时，点查、属性过滤、聚合、分页仍然可用；上层（对象服务、界面、AI 工具、MCP）一行不改就能换后端；索引依旧可以随时从数据源 / 已发布快照全量重建。
- **设计细节**：
  1. **分层与边界**：权威在数据源（Oracle / PG / MySQL…，不搬）；PG 留平台元数据 + 未来的用户编辑层；**ClickHouse 只放对象索引**（派生、ephemeral、可重建）；搜索型需求（相关性排序 / 高亮 / facets）后期再叠 OpenSearch；图遍历先做「边表 + 应用层多跳」，本条目不引图库。
  2. **接入方式**：在 `src/lib/instance/object-index/` 下新增 `clickhouse/` 实现 `ObjectIndex` 契约，由 `getObjectIndex(kind)` 按 kind 分派（注册表已存在）—— 换后端是**新增实现**，不是重写上层。
  3. **表设计**：按对象类型分区；`ReplacingMergeTree` 按 `(target_id, object_type, object_key)` 幂等 upsert；排序键 `(object_type, object_key)`；**只索引会被查询 / 过滤 / 展示的属性**（附件、媒体、超长文本只存引用 —— Palantir 的 media reference 同一个思路）；领域类型映射（日期用 Date / DateTime64、金额用 Decimal，别一律塞字符串）。
  4. **检索能力要对齐，不能悄悄降级**：PG 版现在给的是全文 + 中文子串 + 属性过滤 + 向量 + 类型过滤五件事。CH 侧要用倒排索引 / token bloom / ngrambf 覆盖前两件，向量用 CH 的 HNSW（或先留空、回退 pgvector），**能力对不上的地方必须在返回里如实标注**（沿用「静默截断 = bug」那条口径）。
  5. **切换与回填**：先「双写 + 对拍」再按 kind 切换；一次全量回填 + 增量同步（发布路径与 `POST /api/objects/index` 两条都要接）；对拍口径是同一查询在两后端结果**逐格一致**（含分页顺序与总数）。
  6. **降级**：CH 不可用时回退 PG（或明确报错并说明索引可重建）；索引空时 `POST /api/object-search/reindex` 能全量重建。
  7. **不采用**：Neo4j 当对象主存（属性过滤与聚合弱、集群贵）；MongoDB（聚合与全文两头不讨好）；单机 PG 硬扛上亿（分库分表比换存储更痛）。
- **已完成（2026-10-11）**：

  2. **ClickHouse 适配器**：`clickhouse/{config,client,plan,index}.ts` —— 命名参数绑定、`ReplacingMergeTree(version)` + 读时 `FINAL`、`JSONExtract*` 过滤、token bloom + 子串双通道、向量暴力余弦、轻量 DELETE（`mutations_sync=1`）。
  3. **共享契约用例**：`tests/lib/object-index/contract.ts` 在真 ClickHouse 26.9.8.3 上 **15/15 通过**（`pnpm test:object-index`，需要 `CLICKHOUSE_URL`）。
  4. **删掉 PG 那条路**：`postgres.ts` / `sql.ts` / PG 契约测试 / `ObjectEntryEntity` / `object_entries` 注释全部移除，迁移 `0007-drop-object-entries` 负责 `DROP TABLE`。

  - **按对象类型选策略（S4）**：`AUTO / INDEXED / FEDERATED`，海量日志型类型允许不入索引；
  - **分区键与排序键调优**：现在统一按 `(target_id, object_key)` 排序，超大本体考虑按对象类型分区；

### 接口类型（Palantir Interface）

记录时间：2026-09-15。用户要求按 Palantir 的接口（interfaces）实现：**接口是抽象契约** ——
它不绑数据、不能被实例化，只描述「实现我的对象类型必须长什么样」。应用按接口统一消费，
于是新加一个实现了该接口的对象类型不用改应用。用户当时的疑问是"接口是不是和父类很像、父类好像没什么用" ——
**第二天就照着这个思路改了：父类删掉，抽象只留接口**（2026-09-16）。现在平台里的抽象机制**只有这一种**：

- **接口（`interfaces` + `entityTypes[].implements`）**：能力与形状的契约。一个对象类型可以实现多个接口；
  实现接口要满足接口的属性与关系约束，否则发布前校验会拦下。
- ~~父类（`parents`）~~：具体类型之间的继承，**已于 2026-09-16 整体删除**（见上面 M3 的废止说明）。
  想要「子类也算父类」的效果，改成让两个对象类型都实现同一个接口。

数据落在定义里（`src/lib/ontology.ts`）：

- `ontologyDefinitionSchema.interfaces: InterfaceType[]`：`{ id, name, description, properties[], extends[], linkConstraints[] }`
  - `properties[]`：接口属性。`required` 的属性，实现方必须有**同名**属性
    （Palantir 是"把现有属性映射到接口属性上"，平台这一版按同名映射 —— 够表达，也不必再维护第二张映射表）。
  - `extends[]`：接口继承接口（可多继承）；属性与关系约束一起继承，同名以更近的接口为准。
  - `linkConstraints[]`：`{ name, targetKind: OBJECT_TYPE | INTERFACE, targetId, cardinality: ONE | MANY, required }`，
    要求实现方有一条「从我出去、终点是目标对象类型（或其子类）/ 实现了目标接口的类型」的具体关系类型。
- `entityTypes[].implements: string[]`：这个对象类型实现了哪些接口。

三条不变量（改这块时别破）：

1. **接口不是对象类型**：不绑数据源、不能实例化、不进实例查询。发布时声明成 `owl:Class` + `urn:bkn:Interface`；
   `jena.ts` 的 `META_TYPES` 必须留着 `BKN_INTERFACE_META`，否则接口会被当成对象混进对象数、标签清单与整图导出。
2. **实现 = 同名属性 + 必填关系约束**：判断口径只有一处 —— `src/lib/ontology/interfaces.ts` 的 `checkImplementations`
   （纯函数、有单测）。发布前校验（`validateVersionSnapshot` → `validateInterfaces` / `validateInterfaceImplementations`）
   与界面提示都走它；校验返回的 message 是**给用户看的界面文案**，按术语约定写「对象类型」。
   **2026-09-16 补**：`validateVersionSnapshot` 里原先只 import 了这两个校验函数却没调用（只有接口页在客户端提示），
   于是"接口页写着还差 2 项"的草稿照样能发布 —— 现在这两条接进了发布前校验，
   `tests/lib/version-snapshot.test.ts` 有「缺必填属性 / 缺必填关系会被拦」的用例。
3. **实现了子接口 = 实现了父接口**：`implementersOf` 把"实现了子接口的对象类型"也算成父接口的实现者；
   图库侧靠 `rdfs:subClassOf` 的类型传播天然成立（按接口筛对象能筛到实现者）。实现同时写 `urn:bkn:implements`，
   读骨架时才能把「实现」与「接口继承」分成两种边（`readSchemaGraph` 的 `implementPairs`）。

界面（配置一处、使用两处）：

- **「本体草稿 → 接口」标签**（`interface-manager.tsx`）：左栏接口清单、右栏接口定义（名称 / 说明 / 继承 / 接口属性 / 关系约束 / 实现情况）。
  接口图标画成**虚线框**（Palantir 用虚线轮廓区分接口与对象类型）；两栏之间是可拖的分隔条（本机键 `interface-split`）。
- **对象类型侧**：`type-edit-dialog.tsx` 的「实现接口」多选会显示「必填属性对上几条、还缺哪些」并给「按接口补齐属性」；
  可视化画布的右栏也显示「实现接口 X」。`TypeEditDialog` 的 `interfaces` 属性在**可视化与「对象类型」清单两个入口都要传**
  （漏传就会变成"草稿里还没有接口"）。
- 工具侧：`list_interfaces`（接口清单 + 属性 + 关系约束 + 实现者），`get_object_type` 带 `interfaces`（接口属性映射状态），
  `search_schema` 与概念清单都能命中接口；MCP 里 `list_interfaces` 归在 `model` 组、标题「接口」。

**实现可以加、也可以摘（2026-09-15）**：Palantir 的文档写得很明确 ——
[Edit an interface implementation](https://www.palantir.com/docs/foundry/interfaces/edit-interface-implementation/) 一节的原话是
「Once implemented on an object, you can update the implementation by **deleting it** or changing the mappings」，
具体做法是「Select the … icon and choose **Remove interface**」再 Save；
另一侧 [Implement an interface](https://www.palantir.com/docs/foundry/interfaces/implement-interface/) 里，
接口总览页也有 `Implementations → + New` 直接挂实现。
所以「实现」在平台里必须是**可加可摘**的一条记录，不是单向的一次性绑定。三处入口：

- 对象类型弹窗（可视化 / 对象类型清单共用）：勾上 = 实现；再点一下 chip 就取消；
  已实现的行尾有「取消实现」，标题行的「全部取消」一次摘掉全部。
  chip 的勾选态画成真方框（蓝底白勾 / 虚线空框），别再退化成看不出来的浅色块。
- 接口页「实现情况」：直接实现项尾巴上的 ✕ 取消；「+ 添加实现…」给还没实现的类挂上
  （选项里直接写「还缺 N 条必填属性」，挂上后 chip 标「还差 N 项」）。
  间接实现（继承子接口来的）故意没有 ✕ —— 得去实现方的对象类型上摘那个子接口。
- 可视化画布右栏「实现接口」：每个接口一个小 chip，点一下就地取消（写草稿）。

三处都只动 `entityTypes[].implements`，不碰接口定义本身，保存走各自页面原有的保存路径。

已知未做（有意留白，别以为漏了）：接口的**动作约束**（Palantir 的 action type constraints、参数映射，本身还在 beta）、
shared properties / struct、接口的 status 与 searchable 元数据、把接口画在可视化画布上（只画在「接口」标签与骨架图里）。

### 对象层（P0 路线：对象身份 → 对象服务 → 检索索引归位）

记录时间：2026-09-19。来源：对照 Palantir Ontology 文档全集（Object Storage V2 / Object Set Service /
Object Views / Object Explorer / Object Monitors）后得出的 P0 结论，用户确认把这一段记进本清单。

**先厘清三样东西**（这条路线的前提，别混）：

| 层次 | 现在有没有 | 规模取决于 |
| --- | --- | --- |
| 对象存储（对象存在哪、身份是什么） | 实质是版本快照里的节点 | 发布快照节点数 |

### 整份物化（S4 第一刀，2026-10-12 用户口径）

用户口径：「不需要只物化一部分 —— 那一部分只是查看用的，而真正存对象实例只有全部去实例化才对」；
「记录并动手」。

**定下来的口径**（以后按这条写代码）：

1. **粒度 = 对象类型**：一个类型要么**整份物化**（全部行走索引），要么**整份联邦**（全部行回源）。**不允许"半份"** ——
   半份会让同一类型里"有的对象搜得到、有的搜不到"，而且 `queryObjects` 的 `auto` 口径是"索引里这个类型 total > 0 就用索引"，
   于是半份会**静默截断**（页面显示 100，实际 10 万）。
2. **截断必须报数**：读满限额就停下，并在结果 / 物化清单里写清"物化了 N 条、源可能更多"（`truncated=true` + 页数 + 扫描条数）。
3. **权威仍在数据源，索引是派生**：整份物化 = 把源的投影**整份**写进对象索引（可重建）；不把索引当第二权威。
4. **来源隔离**：索引行带 `origin`（`SNAPSHOT` 手工 / 动作建的对象；`MATERIALIZED` 从业务库物化的对象）。
   **发布与"重建索引"只替换 `SNAPSHOT` 那一份，不许清掉物化数据**；反之物化只动 `MATERIALIZED` 那一份。
5. **联邦直连仍保留**：上亿行、只做点查的类型允许整份联邦，但要在能力字段里如实标出（不能跨类型 join、多跳不完整、聚合受限）。

`materializeObjectType` 按类型**分页整份物化（默认不限制行数，读到源读完）**，截断报数、写物化清单；
**后台任务**：一个任务 = 一个对象类型，服务端**全局串行**执行，`POST /api/objects/materialize-type` 入队即回 `202 {job}`，

物化任务历史 / 问答历史；审计保留），`deleteOntology` 先清数据再删行；一次性修复写成迁移 **0010**（判据：target 不在 `graph_targets` 且非内置虚拟目标）。
实测：导入一个一次性本体（1 版本 / 27 concepts / 1 任务）→ 删除 → 该 target 残留全为 0，全局只少这一份（4→3 本体、4→3 target、8→7 版本、7656→7629 concepts、17→16 任务）。

**清理记录（2026-10-12）**：清了 3 个孤儿；清了我测试时给 V4 备份物化的数据（649 对象 + 500 边，走「清除物化」接口）；
ClickHouse `object_entries` 现 2528 行（只剩 V5）、`object_links` 0、原始行 = 去重后（无重复）。

**主键游标翻页（2026-10-12 已做）**：有主键（且主键列都映射到属性）就按主键升序做键集翻页，offset 恒为 0，
不再受 Oracle `ORACLE_MAX_OFFSET=5000` 限制；Oracle 上有序取行先用子查询排好序、外层再用 ROWNUM 截断。
第一页也带排序列（踩过的坑：第一页无序 → 游标从键序中间插入 → 837 行的表读成 840 行、索引只剩 759 个对象）。
验证：`集团成员`（837 行）`pageSize=100` → `scanned=837 / rows=837 / pages=9 / truncated=false`，索引去重后 837 条，SQL 形如
`SELECT * FROM (… ORDER BY RTRIM("t"."USER_ID") ASC) WHERE ROWNUM <= 101`。
退回 OFFSET 的两种情况：主键没配全 / 断点续跑（只存了条数，还原不出游标）。

**版本快照哈希口径（2026-10-12 修）**：哈希改成"只认存储值 + `stableStringify`（key 排序）"，
schema 新增默认值不再影响老行；读时若不一致则按当前口径重算写回（一次性自愈，打 `[snapshot-hash]` 日志）。
实测：3 个老本体重新可读（reindex 200），第二次读不再触发自愈；口径写进 `AGENTS.md`。

**仍未做（必须先修，否则续跑是空转）**：**源侧 offset 分页**——`src/lib/instance/object-service/data-source.ts` 的取数只传 `limit`、
不传 `offset`，"翻页"会反复读同一段：大表整份物化会读不全（也可能重复），续跑也省不下来。
修法：Oracle 用 `ROWNUM` 包一层、PG / MySQL 用 `LIMIT/OFFSET`，或改成"按主键 > 上一页最后一个键"的游标翻页（更稳）。
其余：按类型策略的界面已在第二刀做掉；
只物化"身份 + 检索/排序/聚合字段"的列裁剪；源变更的增量同步（CDC / 定时）；编辑层（源 + 编辑合并）；
**任务不落库**（状态在内存，进程重启丢任务与历史，物化幂等可重跑）；面板还没暴露 `pageSize`；
"读到源读完"的进度按**页边界**更新（源里总行数事先不知道，所以进度条是不确定态）。

**验收口径**（做 S2 / S3 时要能拿出这几条）：给一个绑定了业务表的对象类型，表里有 N 万行而快照里没有节点，
仍能按主键取到对象、能检索、能按属性过滤分页；改一行数据后只同步这一行。

### 多本体隔离

**结论：隔离单位是「命名图」，不是「多起一套实例」。** 2026-09-14 之后的实现：

- 新建本体时自动分配 `urn:ontology:<本体 id>`，写进 `graph_targets.options.namedGraph`；
  `createOntology` 走 `createManagedTarget` 开一条受管存储记录，用户不需要理解数据集与命名图。
- 发布是**整图替换**，作用范围就是这个命名图（`jena.ts` 的 `replaceGraph` 清掉目标命名图后重写，
  没配命名图时才是默认图），所以同一个 Fuseki 上可以并存任意多个本体。
- 仍然拦截「同一个数据集 + 命名图」被登记两次（HTTP 409 + 说明怎么改），因为那两边的发布确实会互相清空。
- 要按环境 / 租户再分一层时用**多 dataset**（一个 Fuseki 下配多个 dataset，登记时选不同数据集）；
  需要资源或权限硬隔离时才单起一套 Fuseki/TDB2。

**不变量：用户查询必须按命名图限定数据集。** 2026-09-14 修过一个串数据的 bug：
适配器自己的读路径都套了内联 `GRAPH <命名图>`，唯独 `/api/query`（图谱页的 SPARQL 工作台）
是原样执行用户语句 —— 于是裸 `?s ?p ?o` 打到 Fuseki 的**默认图**，而默认图里放的是
「没配命名图」的那个本体的数据，看起来就是"别的本体的数据跑进来了"。
现在的规则：`execute()` 走 `scopedQueryUrl(endpoints)`，用 SPARQL 协议参数
`default-graph-uri` + `named-graph-uri` 把命名图设成这次查询的默认图（也登记成命名图，
所以 `GRAPH <自己的图>` / `GRAPH ?g` 仍可用，但数据集里只有这一个图）。
没配命名图的存储原样执行 —— 那类存储就住在默认图里，而且它是「看整个数据集」的排查入口。
`tests/lib/graph/jena.test.ts` 有 `scopedQueryUrl` 的单测，改这块别把限定去掉。

（`scripts/neo4j-instance.ps1`，已在 2026-09-14 随 Neo4j 一并删除）。下表的 N1/N3/N4 都是 Neo4j 专属路径，

### 本体一等公民（对标 bkn-studio）

记录时间：2026-09-13。**用户方向：像 bkn-studio 的「知识网络管理」那样，在平台里直接建立不同的本体来做隔离**，
而不是让用户先去理解「本体存储 / 数据集 / 命名图」。

现状的问题是隔离单位错了：现在隔离粒度是**本体存储**（一个连接 = 一个本体，1:1），
于是用户必须先想清楚"存哪"才能建本体，图库的隔离限制就直接暴露在界面上（Neo4j 时代是社区版一个库的限制）。
参照 bkn-studio：`KnowledgeNetworkRecord = { id, identifier, name, description, color, icon, tags,
createTime, creatorName, updateTime, updaterName, statistics, embeddingModelId }`，
对象类型 / 关系类型 / 动作类型全部挂在知识网络 id 下，存储完全不出现在用户面前。

目标形态：

```
本体(ontology) ── 版本(draft/published) ── 对象 / 关系
      └─ 落点：存储(target) + 空间(namespace)
```

| 编号 | 事项 | 现状 | 建议做法 |
| --- | --- | --- | --- |
| O1 | 「本体」成为一等公民 | 隔离粒度是本体存储，版本与快照都按 `target_id` 归类 | 新表 `ontology_platform.ontologies`：id / identifier / name / description / color / tags / created_by / created_at / updated_at / target_id / namespace；版本记录加 `ontology_id`，老数据迁移成一个默认本体（名字取原本体存储名）。快照磁盘结构不动 |
| O2 | 落点自动分配 | **已完成**：新建本体时自动分配 `urn:ontology:<id>` 写成 `target.options.namedGraph`，一个 Fuseki 能承载任意多个本体 | Neo4j 分支已随 2026-09-14 的移除取消，`createOntology` 不再需要"资源被占用"的判断 |
| O3 | 本体列表页 | 左侧是「本体存储」下拉，没有本体概念 | 对标截图：卡片列表（名字 / 描述 / 标签 / 统计 / 创建人 / 更新时间）+「新建 / 导入 / 搜索 / 分页」；顶部「当前本体」选择器取代「当前本体存储」；原「本体存储」页改名「存储资源」，显示每个存储挂了几个本体 |
| O4 | 本体统计 | 无 | 卡片上显示对象类型数 / 关系类型数 / 对象数 / 关系数（`statistics`），数据从版本快照 + 图库统计来 |

**不变量：「当前本体」是主选择，落点必须跟着它走。** 2026-09-13 修过一个 bug：首次加载时
`loadTargets` 从本体列表和存储列表**各自**取第一项，两个列表顺序无关，于是侧边栏显示「本体 A」、
实际加载的却是「存储 B」的草稿与版本（页头、版本条、画布全是 B 的内容）。现在的规则：
`loadTargets` / `loadOntologies` 只从本体列表决定 `targetId`；`loadVersions` 在目标变化时先清空
版本与运行时统计，避免切换的一瞬间显示上一个本体的草稿。改动这块时别把两者再拆成独立取值。

**侧栏「当前本体」的长名字会撑破侧栏**（2026-09-14 修）：`<select>` 在 grid 里默认按 **min-content** 撑宽，
本体名一长（例如「中国移动客户账务订购业务网络V3（含概念域）」）就把 240px 的侧栏顶破、文字压到内容区上。
修法是给 `.target-picker` 和它的 `select` 加 `min-width: 0` + `width: 100%` + `text-overflow: ellipsis`，
并给 select 挂 `title`（鼠标停上去能看到全名）。以后往侧栏里加"用户自己起名的东西"（本体名、标签、数据资源名）
都要按这条处理 —— 名字长度不由我们决定。

**数据来源绑定必须暴露给模型**（2026-09-14 修）：

对象类型绑了哪张表存在 `entityTypes[].sources` 里，但里面只有**数据资源的 id 与来源 id（都是 UUID）**，
模型看不懂；而 `get_object_type` 当时**根本没返回 `sources`**，于是「专线产品用户 绑定了哪个表」只能被答成
"没有数据来源 / 图库里没有数据"。现在的做法：

- `ToolContext.dataSources`（本机已登记的数据资源）由三个入口一起传：`/api/reasoning/run`、`/api/reasoning/stream`、
  `src/lib/reasoning/mcp.ts` 的 `contextFor`（忘记传就会退化成只有 UUID，答不出表名）。
- `get_object_type` 的 payload 增加 `sources`（角色 / 资源名 / schema / 表 / 主键 / 标题列），每个属性增加
  `source_field`（映射到源表哪一列）与 `source_role`（属于哪一份来源），并附一句 `data_source_note` 说明
  "对象是这张表里的一行、图库对象数与是否绑表无关"。
- `search_schema` 的 `haystack` 把**表名**也算进去：问「TB_MK_GRP_LINE_LIST_DAY 是哪张表」能直接命中对象类型，
  候选的 `detail` 里写「绑定 GISTOOLS.TB_xxx（资源名）」。
- `schemaBrief`（system 里的本体概览）顺带带上每个对象类型绑的表，省掉一次 `get_object_type` 往返。

加新工具或改工具返回时守住这条：**给模型看的字段里不许出现裸 UUID**，要么翻成人话，要么别给。

**表名一律写全「模式.表」，拆分只做一次（2026-09-14 修）**：

界面上、`schemaBrief` 里、`get_object_type.sources` 里，表名都是「模式.视图」的写法
（`GISTOOLS.TB_DIC_AREA_CODE`），模型就照着这个写法去调 `get_table_ddl` / `run_sql`。
`get_table_ddl` 在这里踩过一个坑：传进来的名字被原样当成**裸表名**去数据字典里精确比对，
于是"明明有这张表"却报 `数据源里没有表或视图「GISTOOLS.TB_DIC_AREA_CODE」`（2026-09-14 用户报的）。现在的规则：

- 名字的引用与拆分统一在 `src/lib/shared/server/sql-object-name.ts`（纯函数、有单测）：
  `splitObjectName` 认 `模式.表` / `"模式"."表"` / 反引号 / 方括号；`quoteIdentifier`、`qualifiedName`
  也搬到了这个文件，`sql.ts` 只做重导出，别再各写一份。
- 数据资源层在**查字典之前**拆名字，候选模式按优先级：名字里写的 → 调用方给的 → 数据资源登记的
  （`candidateOwners`）。几个候选一起查、再按这个顺序挑（`resolveOracleObject` / `pickNamedObject`），
  所以写 `GISTOOLS.TB_X`、只写 `TB_X`、甚至写错模式都还能落到真实的那张表上。
- Oracle 侧**两边的比较都要 `UPPER()`**（`UPPER(owner) IN (UPPER('gistools'))`）。少一层 `UPPER()`
  会让小写写法查不到 —— 这个坑本轮当场踩到，靠真机验证才发现。
- 查不到时的消息要说清试过哪些模式，并在 Oracle 上补一句"同名对象在别的模式下存在"（`oracleOwnerHint`），
  不要再出现"明明有表却说没有"的排查黑洞。
- 顺带一条已知的**正常现象**：连接用户不是表的所有者时（本机 `sk_ws` 看 `GISTOOLS` 的表），
  `DBMS_METADATA.GET_DDL` 会报 `ORA-31603`，这时按列元数据还原 DDL 是预期路径，
  `get_table_ddl` 的 `ddl_source` 会是 `metadata`，`notes` 里会如实写出原因。

**概念分组与多跳查询（2026-09-14）**：这一版把"分组看得见"和"多跳走得通"补齐，三处要点：

1. **概览里直接给分组成员**：`agent.ts` 的 `schemaBrief` 现在写
   `概念分组：客户域（2 个：客户、用户）；账务域（5 个：…）；未归组：账单`（导出了这个函数，`agent.test.ts` 有单测）。
   用户问"某业务域里有什么"是最常见的一类问题，写在概览里就不必再调工具，也不会出现"分组明明建了、模型说没有"。
   对象类型清单里因此**不再重复**每个类型的分组名（分组清单已经把成员列全了）。
2. **一跳在 `get_object_type`，多跳在 `traverse_object_types`**（`relations` 那个旧字段已换成 `one_hop`）：
   - `get_object_type.one_hop`：`outgoing` / `incoming` 两组，每条带 `relation` + 对方的名字、分组、一句话说明、绑的表。
   - `traverse_object_types`：纯函数 `traverseTypeGraph`（有单测）。起点 `start_type` 留空 = 从全部对象类型出发（等于整张类型图，
     所有节点都是 0 跳）；`hops` 默认 3、上限 5；`object_types` / `relationship_types` 是**白名单**，
     不给就是不限定，起点永远包含在结果里。`nodes[].hop` 是**最短距离**，`edges` 是这些节点之间**全部**关系的诱导子图
     （每条边的 `hop` 取两端里更远的那个），这样"隔两跳能到谁"和"这两类之间还连着哪几条"一次都答得出来。
     起点或白名单里写了本体没有的名字：起点直接抛错（让它先 `search_schema`），白名单里的名字原样进 `unknown_names` 并提醒，**不猜**。
3. **没有合并工具的地址**（`list_concept_groups` 与概览、`get_object_type` 与多跳各留一份是有意的）：
   概览是"一屏看完"，`list_concept_groups` 是**权威清单**（含空分组与未归组，适合"还有哪些没归组"）；
   `get_object_type` 的一跳是读定义时的顺带信息，`traverse_object_types` 才是做路径/范围分析的入口。
   真要把两者合并，就得给"看分组"再编一套参数语义，反而更难被模型用对；这条记录一下，别当成重复实现清理掉。

**流式与思考开关已落地**（2026-09-14）：

- 走的全是流式（`includeUsage: true`，否则流式下统计不到 token）。工具调用分片由 SDK 按 `index` 归并，
  不会拼出半截 JSON。
- `agent.ts` 消费 `ToolLoopAgent.stream()` 的 `fullStream`，往外发 `thinking` / `answer` / `answerReset` /
  `step` / `done`（对应 `reasoning-delta` / `text-delta` / `tool-call` / `tool-result` / `finish`）；
  `/api/reasoning/stream` 再把它们转成 SSE 帧。**校验与权限必须在开流之前做完**，一开流就没法改状态码了。
- **`providerOptions` 只能放在 `new ToolLoopAgent({...})` 构造层**，不能放进 `agent.stream()` 的参数 ——
  `AgentCallParameters`（`stream()` / `generate()` 的入参）没有这个字段，放错会直接 typecheck 失败。
- `answerReset` 的用途：模型调工具前常会先吐一句旁白，那不是结论。界面收到后把它**挪进思考过程**再清空正文 ——
  既不让结论区闪出半句话，也不把这段过程丢掉（关掉思考时模型尤其爱这样旁白）。
- **思考开关**：`thinking: false` 经 `providerOptions` 下发 `thinking.type=disabled`，`reasoning_content` 变空、
  通常更快（实测同一问题 4.6s → 3.8s；迁移到 SDK 后复测 5.9s → 3.5s，思考 197 字 → 0 字）。
  界面在问答页头有个「思考 开/关」，按**每一轮**记录，所以同一会话里开着问一轮、关着问一轮，两轮的展示各自正确。
  注意：`chat_template_kwargs.thinking=false` / `enable_thinking=false` 会被这个端点**静默忽略**（返回 200 但照样有思考）。
- 实测事件流（迁移到 SDK 后复测）：思考 1→53→191→345 字、步骤 0→4、正文 0→95→251→349 字，都是边跑边长出来的；
  收尾后「思考过程 / 求证轨迹」会按设计自动收起（`open = manual ?? live`），展开仍能看到完整内容。

**run_sql 的默认行数与「已被截断」标记**（2026-09-14 修，用户口径"默认限制 100 条，超过就在 JSON 里标已截断"）：

- 默认从 50 改成 **100**（工具层 `DEFAULT_SQL_ROWS`、连接器 `DEFAULT_QUERY_ROWS` 两处一致）；
  模型传了 `limit` 就按它的来，再被「取数行数上限」往下压，最后被 `SQL_ROWS_CEILING = 5000` 兜住。
- **截断检测以前是坏的**：连接器给语句套了 `LIMIT n`（Oracle 是 `ROWNUM <= n`），
  于是返回行数永远不可能超过 n，而判断写的是 `list.length > n` —— 对 SELECT 恒为 false，
  只有 `SHOW` / `EXPLAIN` 这类套不上 LIMIT 的语句才会真的标出来。
  现在按 **`n + 1` 多取一行**当探针，再用 `takeRows()`（纯函数，有单测）切掉那一行并给出 `truncated`。
  `boundedStatement` 的内部硬上限因此是 `SQL_ROWS_CEILING + 1`：正好打在上限时也要能探出第 5001 行。
- payload 里除了 `truncated: true` 还多一句人话 `truncation_note`：
  「结果已被截断：只返回了前 100 行（本次上限 100），表里还有更多行……」——
  只给模型一个 boolean，它很容易把"前 100 行"当成全量。
- 顺带把连接器的硬上限从 500 抬到 5000（`QUERY_LIMIT_MAX = SQL_ROWS_CEILING`）：
  在这之前「取数行数上限」界面上能填 5000、实际最多只给 500，两边对不上。
- 实测（Oracle 测试 1251）：默认 → `returned 100 / row_limit 100 / truncated true`；
  `limit=6000` → 压到 5000 且 `truncated true`；SQL 自带 `ROWNUM <= 100` → 正好 100 行、`truncated false`（不误报）。

- 请求体里**不带**的项就是"不限制"：`/api/reasoning/stream` 与 `/run` 只认这几个字段，
  服务端把步数夹到 100、`run_sql` 的行数夹到 5000。界面页脚也不显示 `x/分母 步` ——
  没设上限时那个分母是兜底值，显示出来会冒充"限制"。
- 起因：步数原本默认 8、硬上限 16，实测一次"按地市分类统计"的分析跑到 8/8 被拦停，
  界面报「步数用满，结论可能不完整」（用户反馈：不要限制）。现在默认不限制，页头开关上
  设过任意一项才挂「已设」角标。
- 抽屉改完**立即生效**并写 localStorage，没有「保存」按钮 —— 这几个数没有"改到一半"的中间态；
  带「恢复默认」，Esc 与点遮罩都能关。

**多轮上下文（连轨迹一起带）+ 上下文压缩**（2026-09-15）：用户先问"模型有历史上下文吗"（当时答案是**没有**，

- **消息本身交给 AI SDK，不自己拼**：每一轮还原成框架的 `UIMessage`（assistant 的 parts 里是 `tool-<名字>`
  调用与结果 + 结论文本，`history.ts` 的 `turnUIMessages`），再交给 `convertToModelMessages()` 与
  `pruneMessages()`（`history-messages.ts`）—— tool-call 与 tool-result 的配对、错误结果、附件都由框架保证，
  自己拼"轨迹文本"既容易踩配对，也比框架差。两条裁剪口径：**思考一律不回放**（`reasoning: 'all'`，
  一轮几千字且信息量最低）；**轨迹只留最近一轮**（`toolCalls: 'before-last-message'`，更早的轮次留结论，
  结论是 assistant 文本，不受裁剪影响）。
- **窗口 + 压缩是我们的策略代码**（框架没有现成的摘要能力）：最近 5 轮原样带（`historyTurns` 可调，
  **0 = 完全不带历史**），滚出窗口的轮次由模型压成一段摘要，**摘要与"压到哪一条消息"一起存回**

- 图**不重放**：历史里的图只在那条用户消息里注明张数（重发像素等于每轮再算一次，接着问图时重新贴一张最省事）。

**智能问答可以中途停止**（2026-09-17）：用户要求"实现模型回答的中断停止功能"。要点：

- **界面**：跑的过程中，输入条上那个主按钮就地变成「停止」（`.qa-compose .action.stop`，取消色，不再是禁用的发送键），
  点它 = 掐断这次 fetch。停的是"继续往下查"，不是把查到的抹掉：已经流出来的思考、步骤与半截结论都留在画面上，
  这一轮末尾挂一条琥珀色的「已停止 —— 这一轮是手动停的，已经跑完的步骤留在上面的轨迹里，结论可能不完整。」，
  输入框立刻恢复可用（不等 fetch 的 finally 回来），随后可以直接问下一句。
- **服务端**：`/api/reasoning/stream` 把"客户端断开"接到一个 `AbortController` 上，两条线都要接 ——
  `request.signal`（Next 挂在 `res.once('close')` 上，且只在响应没写完时才 abort，正常跑完不会误触发）
  与响应流的 `cancel()`（消费端取消）。信号交给 `runReasoning({ abortSignal })`，AI SDK 直接拿它去掐模型请求，
  所以"停止"是真的不再往下跑，而不是前端把字藏起来。`send()` 也加了守卫：客户端走了之后 `controller.enqueue` 会抛，
  别把日志刷满；`controller.close()` 同样包了 try。
- **被叫停的一轮不是失败**：编排层不抛错，把已经跑出来的部分收尾成一份运行记录（`run.stopped = true`），
  上层照常写审计（`REASONING_RUN` 的 details 多一个 `stopped`），回看时能看到它查到哪一步被叫停。
  **AI SDK v7 在 abort 时不一定抛异常** —— 实测它会先往流里发一个 `abort` 片段再正常收尾，
  所以 `agent.ts` 三个信号都认：`abort` 片段、被掀掉的异常、以及"没收到 `finish` 但信号已经触发"。
  第三个是兜底，专门用 `finished` 区分"跑完之后才断开连接"的正常一轮，别把它标成被停。
- **要不要进历史看成色**：`worthKeepingTurn(run)`（`agent.ts` 的纯函数，`agent.test.ts` 钉住）——
  有步骤 / 有思考 / 有真的结论才记，什么都没跑出来就不记（兜底文案 `STOPPED_ANSWER_FALLBACK` 不算结论），
  免得历史里多一条点进去什么都没有的条目。
- **已知边界**：正在跑的 **SQL 拦不住** —— 数据源层没把 signal 传进驱动，那条查询会跑完、结果被丢掉
  （单条语句本身有超时兜底）。要真叫住它，得给 `DataSourceConnector.runReadOnlyQuery` 加 signal 并一路透传到驱动。
  另有一条小落差：若在"最后一个字刚流完、服务端还在写审计 / 落库"的那一瞬间点停止，界面会标「已停止」，
  而库里那条是跑完的正常记录 —— 客户端此刻已经断开，收不到 `done` / `saved`，无从分辨。

**数据来源：只读 SQL 与表结构**（2026-09-14，用户提出）：

本体这一层只有定义，要具体数据就得走"对象类型 → 它绑定的表"。两个工具把这条路接上，
闸门写在 `src/lib/shared/server/sql-guard.ts`（纯函数，有单测），**两道闸是有意重复的**：

- **词法闸门**判断语句"长得像不像查询"：必须以 SELECT / WITH / SHOW / DESC / DESCRIBE / EXPLAIN / VALUES /
  TABLE 开头；多条语句（分号）、`INTO`、INSERT / MERGE / DROP / ALTER / CREATE / GRANT / CALL 等一律拦下。
  判断前先剥掉注释与字符串字面量，所以 `SELECT '删库'` 放行、`/* x */ DROP TABLE t` 照样被拦。
  取值取向是**宁可偶尔误杀**（模型换个写法重来），也不要放过一次写操作。
- **数据库的只读事务**是权威的那道：PG `BEGIN READ ONLY`、MySQL `START TRANSACTION READ ONLY`、
  Oracle `SET TRANSACTION READ ONLY`（都跑在同一个 QueryRunner 上，两次 query 不会跑到不同连接）。
  驱动起不了只读事务时（自动提交模式那类）如实返回 `readOnlyTransaction: false`，工具把它报给模型，
  不让人以为库里有保险。实测这台 Oracle 是 `true`。
- **限量与超时**：SELECT / WITH 会被套一层行数上限（Oracle 用 ROWNUM 包一层，其它用派生表 + LIMIT），
  默认 50、最大 500；PG 加 `SET LOCAL statement_timeout`，MySQL 试 `SET SESSION MAX_EXECUTION_TIME`
  （MariaDB / 旧版不认就算了），Oracle 这一层没有等价开关。
- **DDL**：能拿原始语句就用原始的（MySQL `SHOW CREATE TABLE`、Oracle `DBMS_METADATA.GET_DDL`），
  拿不到就按列元数据还原，并在 `notes` 里写明"差在哪、为什么走了还原这条路"。
  实测这台 Oracle 报 `ORA-31603`（连接用户读不到那个 schema 的元数据），于是输出还原版
  `CREATE TABLE` + `COMMENT ON COLUMN`（注释取自 `all_col_comments`，是真值不是猜的）。
- `data_source` 用**数据资源名**（不是 id、不是图存储连接）；资源清单随 `schemaBrief` 进 system prompt，
  名字写错时错误信息会把当前登记的资源全列出来，模型可以自己改对。

**为什么不用 BM25（2026-10-10，用户口径「就用内存，后面也不用 bm25 了，即使用混合检索也是内存的方式 + 向量」）**

本机 PG 装了 `pg_search`（BM25）、也支持 jieba 中文分词，技术上能用；但在**真实本体**上实测（52 个对象类型 / 2042 条概念 / 22 条标注查询看 top-k 命中）内存打分明显更好：内存 h@5 **91%** / MRR **0.83**，最优 BM25（name 字段 ×5 加权）只有 68% / 0.60，朴素单字段配置 27% / 0.21。两个硬伤：① BM25 没有「名字完全一致优先」这一档，对象类型那条列了 37 个属性的超长 `search_text` 被长度归一化拖累，反而输给短的关系类型文档；② 默认 AND 语义对「统计要客集团成员有多少户…」这类长问句**直接返回空**。而内存打分已经把「名字 100 / 名称包含 70 / 取值命中 45 / 描述命中 30」这些业务优先级编码好，用 BM25 复刻一遍不划算。

**结论：检索排序只用内存打分那套；混合检索 = 内存打分 + 向量。** 将来若要重开 BM25，先重跑对拍、拿数据说话再定。

### 建模体检（建模质量自检）

记录时间：2026-09-18。对着 openBKN 的 `bkn-engineering` 比过一轮之后补的第一块过程能力：
发布前校验只管"能不能发布"，**没人管"建得好不好"** —— 空壳对象类型、孤悬类型、主键列没属性接、
命名打架、接口没人实现，这些一条都拦不住，但会让本体在应用里不好用。

两层分工（**别混在一起**）：

| | 发布前校验 | 建模体检 |
| --- | --- | --- |
| 代码 | `validateVersionSnapshot`（`src/lib/instance/version-validation.ts`） | `reviewOntologyModel`（`modeling-review.ts`） |
| 什么时候跑 | 点「校验」/「发布」 | 点「建模体检」 |
| 档次 | 阻断 + `severity: "WARN"` | `WARN`（该改）/ `INFO`（可以更好），**一条都不挡发布** |
| 管什么 | 来源绑定、端点契约、必填与唯一、接口实现、动作定义 | 建模层面的自洽：粒度、命名、映射完整度、孤立与空壳 |

- **规则码是稳定标识**（`ENTITY_ORPHAN` / `PROPERTY_TYPE_CONFLICT` …）：界面与技能文档共用同一份，
  加规则只加码、不改码。规则在 `src/lib/ontology/modeling-review.ts` 的 `RULES` 数组里，一条一个纯函数；
  **每加一条就在 `modeling-review.test.ts` 里钉一个用例**，那里还有一条"健康本体零结论"的用例，
  用来防规则越加越吵。
- **只有两个出口**（2026-09-18 起**没有 MCP 工具**：用户口径"去掉 review_model 这个工具"，
  外部 Agent 不再能调它，改成照规则码自查）：
  1. 界面：本体草稿 → 页头「建模体检」（按钮上挂"该改"条数的角标）→ `modeling-review-panel.tsx` 的面板；
     每条结论点主体能跳到对应标签页（对象类型 / 关系类型 / 接口 / 概念分组 / 动作）。
  2. 技能：`skills/ontology-builder/references/modeling-rules.md` 第 9 节列出全部规则码，
     外部 Agent 出包前可以照着自查。
  `reviewOntologyModel` 这一层实现**没有删**（界面还在用）；删的只是 `REASONING_TOOLS` 里的工具定义、
  执行分支与 `mcp.ts` 的 `model` 组映射。要恢复就把这三处加回去。
- **刻意不做的事**：不查真实表结构。"绑的那张表里到底有没有这一列"要连库去比，属于「数据资源」那侧的活；
  这一层只保证**定义内部自洽**。
- 实测（2026-09-18，本体「…备份V4」）：一次体检出 9 条 —— 4 条 `ENTITY_ORPHAN`（调账 / 欠费 / 缴费 / 销账
  既不绑数据、不连关系、也没有动作）、2 条 `PROPERTY_TYPE_CONFLICT`（`BOSS_CUST_ID` 一边 TEXT 一边 DECIMAL、
  `OFFER_ID` 一边 DECIMAL 一边 TEXT）、3 条 `RELATION_NO_DESCRIPTION`。前两类都是真的建模问题。

### 概念分组（业务域）

记录时间：2026-09-14。**用户方向：像 bkn-studio 的知识网络详情页那样，把对象类型按业务域（客户域 / 账务域 / 字典域…）
归堆，图谱上按组画框图。** 这一层是"人怎么看这个本体"，不是本体语义。

数据落在定义里（`src/lib/ontology.ts`）：

- `ontologyDefinitionSchema.groups: ConceptGroup[]`，一条是 `{ id, name, color }`；`color` 留空就按它在清单里的位置取
  `GROUP_PALETTE`（6 色，`concept-groups.ts`）。
- `entityTypes[].groupId`：空串 = 未归组。**分组的 id 与对象类型的 id 共用一套 id 空间**：导入时
  `ontology-bundle.ts` 的 `collectDefinitionIds` / `relinkDefinitionIds` 会把两者一起换成新 id，`groupId` 才跟着指对。

三条不变量（改这块时别破）：

1. **分组只影响展示与检索提示**：不写进图库（Jena / Neo4j 侧没有对应三元组）、不参与发布校验、不进推理结论。
   它唯一"进入推理"的地方是检索面与提示词：`schemaConcepts` 把分组名并进 haystack（问「客户域里有什么」能命中成员），
   `get_object_type` 返回 `group`，`schemaBrief` 在每个对象类型后面跟分组名。
2. **分组是对象类型这一层的东西**，不是对象（实例）的属性。实例图谱不画分组框，也不提供布局切换。
3. **归组只有一条路径**：`resolveGroup(groups, name)` —— 去掉前后空格、忽略大小写，重名复用，没有就新建（走这条路径的
   `groupName` 一律来自下拉选项，所以实际都是"复用"）。分组的增删改只在配置页做，别处只能"选"。

界面（配置只有一处，看效果有两处）：

- **概念分组标签**（2026-09-14 从左侧导航移进「本体草稿」页，`concept-group-manager.tsx`）：**唯一的分组配置入口**，是本页一级标签之一（可视化建模 → 概念分组 → 对象类型 → 关系类型 → 接口）（左导航不再有这一项；画布工具栏的「概念分组 N」按钮切到这个标签）。
  左栏是色卡式的分组清单（那道色条就是图上框的颜色），右栏改名 / 换色（6 色调色板 + "按位置自动"，带虚线框预览）/ 点选成员 chip / 删除。
  **一个对象类型最多属于一个分组** —— 点一个已经在别组的 chip 会把它移过来，再点一下就是移出。
  改动先落在右栏草稿里（标题旁出现「未保存」，保存按钮这时才可用），点「保存分组」才写进草稿定义（一次性覆盖，避免两次写互相盖掉）；切换 / 新建分组时若有未保存改动先确认。两栏之间的分隔条可拖（宽度记在本机 `concept-group-split`），与对象页共用 `split-pane.ts` 的 `useSplitPane`。
- **对象类型侧只做"选"**：`type-edit-dialog.tsx` 的「概念分组」是**下拉**（选项来自上面那份分组清单，带"不分组"），
  不再让人随手填一个新名字；可视化的右栏也有同一个下拉，方便边看边调。
- **看效果的入口**：本体建模可视化画布（`ontology-builder.tsx`，工具栏「概念分组 N」切到同页的「概念分组」标签）有 `layout-switcher.tsx` 的布局切换器；图谱页只展示实例。
- **导入自带分组**：bkn 知识网络里的 `concept_groups` 由 `bkn-import.ts` 转成 `groups` + `entityTypes[].groupId`
  （成员写在分组那一侧，转换时反过来铺；一个类型挂多个分组时保留文件里的第一个并报 warning）。
- 布局三种：**默认布局**（按关系铺开）、**圆形布局**、**按逻辑分组**（`groupedLayoutPositions`：
  组内小圈 + 组心大圈 + 未归组最外圈，`orderFramesByEdges` 让连边多的组排相邻）。
- **三种布局都能拖节点**（2026-09-14 修：一开始把后两种的拖动关掉了，用户反馈"节点不能拖了"）。
  后两种的底图是算出来的，但点位取 **「手工覆盖 > 算出来的」**，而手工覆盖**按布局分别记**在本机：
  默认布局沿用老键 `ontology-builder:<存储 id>`，圆形 / 按逻辑分组各用 `…:circle` / `…:grouped`。
  分开记才不会出现"默认布局摆好的位置一切到按逻辑分组就全乱"。拖完不会弹回去 —— 换布局、改定义、重开页面都还在。
- 分组框画在节点下面，按成员的**实时屏幕包围盒**算（`GroupFrameLayer` 挂在 `afterRender` 上），
  所以拖动时框会跟着节点的位置**收缩 / 扩大**，不用等松手。
- 「自动整理」= 清掉**当前布局**的手工覆盖 + 换一个 seed 重新算（后两种布局下就是整圈转一下）。
- 分组框由 `sigma-graph.tsx` 的 `GroupFrameLayer` 画：按成员的屏幕包围盒算虚线圆角框 + 左上角组名，
  `afterRender` / 相机变化时重画；z-index 比边线层低，框永远在点和线下面。
- 布局选择记在 localStorage（`ontology-builder:<存储 id>:layout`）：它属于"我怎么看这张图"，不进草稿。

工具与 MCP：

- `list_concept_groups`（无参数）：返回 `group_count` / `groups[{ name, object_types[], object_type_count }]`
  （**空分组也列**）/ `ungrouped_object_types`（`groupId` 指向已删除分组的类型也算未归组）/ `note`；
  evidence 是 `{ kind: "GROUP", id, label }`。
- **工具读的是已发布定义**（和别的推理工具同一条口径）：刚在草稿里分好组、还没发布时，
  `list_concept_groups` 会说"没有分组"。要让它看到，先发布一次。
- MCP 侧标题「概念分组」，归在 `model` 组（`mcp.ts` 的 `TOOL_TITLES` / `TOOL_GROUP`，漏了会退化成原始工具名 + 默认分组）。

| 编号 | 事项 | 现状 | 建议做法 |
| --- | --- | --- | --- |
| U5 | 旧建议已失效 | 图谱「查看本体」入口已移除，分组可在本体建模中配置并查看效果 | 不再给已移除的图谱类型视图加分组目录；若仍需要目录，另在本体建模页设计 |
| U6 | 分组没进筛选层 | 布局、检索提示、`list_concept_groups` 都用到了分组，但对象页与图谱筛选仍只能按类型 | 等 R1（对象页接检索层）落地后加"按分组筛"：把分组成员展开成类型清单再筛 |
| U7 | 左侧导航不显示计数 | bkn-studio 的导航每个条目都带数量（概念分组 6 / 对象类 18…），平台这边一个都没有 | 要补就一起补（本体、对象类型、关系类型、动作、分组），只补一个会显得突兀；计数从当前草稿的 `definition` 直接数 |
