横切关注点 · 分两层，不是"每个页面各判一遍"
  • 鉴权分两层：proxy 粗筛（有没有凭据）+ 路由守卫细判（要哪个权限点）；权限点只在导出处声明一次，执行只在一处
  • PDP / PEP 分得清：决策内核是 can()（纯函数）；中间件与守卫都只是 PEP。将来做数据级授权（行 / 列）时判断落在领域层 —— 那时把 can() 升级成 authorize(user, action, resource)，别再新起一套
  • 权限点：RBAC 角色 → 权限点；界面按钮可见性与服务端校验共用同一份决策内核
  • 审计：发布、删除、数据资源变更、工具开关、动作决策、问答运行全部留痕
  • 只读闸门：assertReadOnlySql 拦写语句；业务写只走模板化动作
  • 工具开关：按全局 / 按本体关掉的工具，同时不进工具清单、提示词与工具返回正文

四条运行时链路：一次操作到底经过谁

CHAIN 01 · 发布

改完模型，点「发布」之后

  1. 1草稿写入平台库：定义 + 实例快照（Schema 校验：zod）
  2. 2发布前校验：主键重复、必填属性、关系端点契约、接口实现、口径结构
  3. 3投影到图存储：replaceGraph() 原子替换，失败保持原状
  4. 4并发控制：进程内队列 + PostgreSQL advisory lock，多实例也不会撞
  5. 5只有 status=PUBLISHED 才被问答工具与对象服务读到
CHAIN 02 · 物化与读对象

「整份物化」与「查一个对象」

  1. 1入队后台任务（一个任务 = 一个对象类型，全局串行），进度落库、可取消、可从断点续跑
  2. 2回源分页：有完整主键走主键游标翻页，否则 offset
  3. 3读完整份必须对账：源侧总数、折叠行数写进物化清单（源 N 行 → 对象 M 个 → 折叠 Z 行）
  4. 4写入 ClickHouse：对象进 object_entries，边进 object_links
  5. 5读的时候：整份物化过就走索引，没物化回源业务库；半份不算数
CHAIN 03 · 问数

「专线用户有多少」这句问出去

  1. 1先按本体的工具开关算出这一轮能用哪些工具
  2. 2系统提示词按开关生成「本轮可用工具」，工具循环开始（步数上限可配）
  3. 3先定位概念（对象类型 / 指标）再取数：run_query（本体 SQL）优先 —— 指标可以只描述，那种不能出数；能不能算看它的 calculable
  4. 4执行路由：涉及的类型全部物化 → 查 ClickHouse；否则回源业务库
  5. 5结果回灌 → 出结论 + 证据；整轮写审计与对话历史
CHAIN 04 · 鉴权

一个请求怎么被放行

  1. 1proxy 粗筛：不是公开前缀、又没带 Bearer → 直接 401（OPTIONS 放行）
  2. 2进到路由：导出时那句 withPermission("...") 已经声明了这个接口要什么
  3. 3守卫执行：取当前账号的权限集 → 过 can() 决策
  4. 4没登录 401、登录了但没权限 403、通过则把用户注入 handler
  5. 5handler 自己的 try/catch 照旧管业务错误 —— 守卫不吞它，只负责"放不放进来"
